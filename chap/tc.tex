\chapter{Architecture of a Type-Class Solver in \rocqelpi}

Type classes provide an elegant mechanism for implementing ad-hoc
polymorphism~\cite{wadler1989}. They allow the same symbol to be reused in
different contexts while preserving the same mathematical properties. From a
Prolog-like perspective, a type-class problem corresponds to resolving a query
to a predicate that associates its input with an instance solving the
type-class constraint. In \rocq, instances act as rules stored in a database,
which are used to backchain and resolve type-class queries.

To address type-class unification problems, we extended \rocq with an API called
\cI{Class_tactics.register_solver}. This API allows developers to register
custom type-class solvers within the \rocq elaborator. In this way, type-class
resolution can be delegated to a meta-language: the custom solver computes a
solution (if it exists) to the type-class constraint and returns it to the
\rocq elaborator. We refer to such a custom solver as a \emph{meta-solver}.

% When the elaborator encounters a type-class constraint during the elaboration
% of a \rocq term, it may delegate its resolution to a registered meta-solver.
% The meta-solver receives the type-class goal together with the context in
% which it appears and must return an updated environment (called an
% \cI{evar_map} in \rocq terminology).

To support this mechanism, we also introduced another API,
\cI{Classes.register_observer}. This API provides a systematic way to notify
the meta-language whenever a new class or instance is declared in \rocq. The
meta-language can then translate these declarations into its own
representation and store them in its knowledge base.

Concretely, a meta-language integration must provide two components:
(1) a compiler that translates \rocq class and instance declarations into the
meta-language representation, and (2) a type-class solver that animates the
search by interacting with the resulting database.

In our setting, the meta-language used to implement the meta-solver is
\elpi. Consequently, the main task is to implement the class and instance
compiler, which incrementally builds the database on which the \elpi program
operates.

The type-class solver itself typically follows a \prolog-like resolution
strategy: instances are tried according to their priority, and backtracking
may reconsider previous choices when a branch fails. In \elpi, this behavior
comes for free, since the resolution mechanism of the type-class solver
strongly imitates the standard execution model of the \elpi runtime.

In the following sections
(\cref{sec:class-encoding,sec:instance-encoding,sec:goal-encoding}), we
present the compiler by separating its three main components: the class
compiler, the instance compiler, and the goal compiler.

In \cref{sec:rule-indexing}, we describe our work on an alternative rule
indexing mechanism for the \elpi runtime, designed to speed up clause
retrieval during resolution.

Finally, in \cref{sec:tc-discussion}, we discuss practical aspects of using
the type-class solver. In particular, we explore how users can control and
customize the solver to better fit their needs. We also show the
application of our solver to existing libraries, such as \tlc, \stdpp, and
\iris.

\section{Simple instance compiler}
\label{sec:simple-instance-compiler}

A type-class goal is a \rocq type\footnote{or term, since in \rocq\ types are
terms.} $T$ whose head symbol is a type-class $C$. Solving such a goal amounts
to finding a \rocq instance whose type is an instantiation of $T$.

Conceptually, a type-class goal can be translated into a query with two
arguments: the type to be solved and the concrete instance that provides the
solution. The predicate used for the search is \eI{pred tc term -> term}.

As an example, consider the \cI{Add} type-class introduced in
\cref{sec:ad-hoc-poly}. For convenience, the full definition of the class and
its instances is reproduced in \cref{fig:add-class-full}.
%
\begin{figure}
  \input{code/plus_tc_add_inst.tex}
  \caption{Add class and instances}
  \label{fig:add-class-full}
\end{figure}
\begin{figure}
  \input{code/toy_compiler_tc.tex}
  \caption{Simple \elpi compiler}
  \label{fig:simple-elpi-compiler-tc}
\end{figure}

After an instance is declared, an observer triggers the instance compiler
shown in \cref{fig:simple-elpi-compiler-tc}. The compiler is similar to the
example presented in \cite[Sec.~4.5]{hdr}.

The entry point of the compiler is the predicate \eI{compile}, which takes the
global reference \eI{G} of the instance as input. Using the
\eI{coq.env.typeof} API, the compiler retrieves the type \eI{Ty} of \eI{G}.
Compilation then proceeds by invoking the auxiliary predicate \eI{comp} to
produce the rule \eI{R}. Finally, \eI{coq.elpi.accumulate} adds the clause
\eI{R} to the database, here called \eI{tc.db}.

The predicate \eI{comp} performs the core of the compilation. It takes four
arguments: the instance term; its type, which is structurally consumed during
recursion; and two accumulators storing the list of instance arguments and the
list of premises that will form the body of the resulting rule. From these
inputs, \eI{comp} produces the \elpi rule corresponding to the compiled
instance.

Compilation proceeds by analyzing the structure of the instance type. Three
cases are relevant. Rules \eI{~\PYG{c}{r$\to$}~} and
\eI{~\PYG{c}{r$\forall$}~} handle quantifications, while rule
\eI{~\PYG{c}{rB}~} is the base case that constructs the final \elpi rule from
the information accumulated during the recursion.

The base case is reached when the current type \eI{Ty} is not a quantification.
The compiler then constructs the final rule by assembling its head and body.

The head is the predicate \eI{tc} applied to the instance type \eI{T} and to a
proof term \eI{Proof}. The proof is obtained by applying the instance \eI{I} to
its arguments \eI{rev Ag}. Since the arguments are accumulated in reverse order
during the traversal, the list \eI{Ag} is reversed before building the
application.

The premises of the clause are stored in the accumulator \eI{P}. As for the
arguments, the list is reversed before constructing the final rule.

For example, compiling the instance \cI{addNat} produces the rule

\begin{center}
  \eI{tc {{Add nat}} {{addNat}}}.
\end{center}

When the current type \eI{Ty} is a quantification, the compiler introduces a
fresh nominal variable representing the bound variable in the recursive call.
Two situations must be distinguished depending on the shape of the
quantification.

If the quantification corresponds to a premise of the instance, rule
\eI{~\PYG{c}{r$\to$}~} is used. This rule introduces a fresh variable \eI{x}
representing the conditional instance with type \eI{T}. The premise
\eI{tc T x} is added to the list of premises \eI{P}, and the variable \eI{x} is
added to the list of instance arguments \eI{Ag}.

Rule \eI{~\PYG{c}{r$\forall$}~} handles dependent quantification corresponding
to parameters of the instance, that are supposed not to have a class as type. In
this case the abstraction is simply consumed: the list of premises \eI{P}
remains unchanged, while the variable \eI{x} is added to the list of instance
arguments.

Both rules \eI{~\PYG{c}{r$\to$}~} and \eI{~\PYG{c}{r$\forall$}~} return a term
of the form \eI{(pi y\ R y)}, where \eI{R} is the result of the recursive call
to \eI{comp}. Since \eI{R} has type \eI{term -> prop} and abstracts the local
variable \eI{x}, the compiler introduces a fresh variable \eI{y} to quantify
over the corresponding argument. This ensures that the resulting rule is
closed (ground), as required by the \eI{coq.elpi.accumulate} predicate.

As an example, consider the instance \eI{addProd}, whose type is

$$
\forall\ \underbrace{x\ y}_{\eI{~\PYG{c}{r$\forall$}~}},
\underbrace{\cI{Add}\ x \to \cI{Add}\ y}_{\eI{~\PYG{c}{r$\to$}~}} \to
\underbrace{\cI{Add}\ (x * y)}_{rB}.
$$

Compiling this instance yields the following \elpi rule:

\begin{elpicode}
  pi x y\ 
    tc {{Add (lp:x * lp:y)}} {{addNat lp:x lp:y lp:Px lp:Py}} :-
      tc {{Add lp:x}} Px, tc {{Add lp:y}} Py.
\end{elpicode}

This rule provides a proof for \eI{Add (x * y)} provided that the two premises
\eI{Add x} and \eI{Add y} can be solved.

To also solve type-class goals, we define an \elpi tactic containing the
following rule:

\end{center}

Given a \rocq goal \eI{G}, the tactic retrieves its type \eI{Ty}, performs a
backchaining step on \eI{tc Ty P} to obtain a proof \eI{P}, and refines the goal

The implementation presented in this section illustrates the expressive power
of the \elpi language. The core of the compiler fits in roughly eight lines of
code, while a similar number of lines is required to complete the
\elpi command fot the compiler. The solver itself consists of a single rule. However, this
simplified implementation has several limitations.

\begin{itemize}
  \item The predicate \eI{tc} does not expose the class arguments as \elpi
        arguments. Consequently, the modes declared on a class are not preserved
        in the \elpi solver. The compiler should therefore generate a specialized
        predicate for each class, with arguments and modes matching those of the
        class so that rule backchaining can be performed correctly. This problem
        is addressed in \cref{sec:class-encoding}.
  \item Rule $r\forall$ does not account for the possibility that the quantified
        variable $x$ is itself a premise of the class. In complex instances,
        $x$ may have a class as its type and should therefore appear as a
        premise in the generated rule. This problem is addressed in
        \cref{sec:instance-encoding}.
  \item The compiler does not handle instances of the form
      $(c_1 \to c_2) \to c_3$, where the implementation of $c_3$ requires a
      proof of $c_2$ in a context extended with a local instance of $c_1$.
      Supporting such cases requires compiling deep hereditary Harrop
      formulas and therefore tracking the polarity of the instance being
      compiled. This problem is addressed in
      \cref{sec:instance-encoding}.
  \item The \eI{solve} rule of the solver ignores the context of the goal. As
        discussed in \cref{sec:elpi-tactics}, the first projection of a
        \eI{goal} in \rocqelpi is its context, which may contain local
        instances that should be compiled and used during resolution. This
        problem is addressed in \cref{sec:goal-encoding}.
\end{itemize}

\section{Class compilation}
\label{sec:class-encoding}

When a class $c$ is declared in \rocq, the compiler generates a corresponding
\elpi predicate. If the class has $n$ parameters, the generated predicate has
$n+1$ arguments: the first $n$ arguments correspond to the parameters of $c$,
while the final argument represents the instance witnessing the class in the
current rule.

From the perspective of the \elpi solver, two aspects of a class declaration in
\rocq are particularly relevant: the global reference identifying the class and
the modes associated with its parameters. In \rocq, users may explicitly
declare modes using the attribute \cI{~\#~[mode="..."]}. If no mode declaration
is provided, the parameters of the class are considered outputs by default.

The compiler responsible for generating the corresponding \elpi predicate is
shown in \cref{fig:class-compiler}.

\begin{figure}
  \input{code/toy_compiler_pred.tex}
  \caption{Class compiler}
  \label{fig:class-compiler}
\end{figure}

The entry point of the compiler is the predicate \eI{add-class-pred}, which
takes two arguments: the global reference \eI{C} of the class and a string
\eI{S} describing its modes. The string \eI{S} encodes the modes using the
three \rocq symbols \cI{-, +, !}, separated by spaces. If the user does not
provide an explicit mode declaration, \eI{S} is the empty string.

Predicates can be created dynamically in \elpi using the API
\eI{coq.elpi.add-predicate}. This primitive takes four arguments: the database
in which the predicate will be stored (in our case \eI{tc.db}), the indexing
strategy, the predicate name \eI{N}, and a list \eI{M} of values of type
\eI{mode-type}. Each element of \eI{M} specifies the mode and the type of one
argument of the predicate. The predicate name is constructed from the global
reference of the class using the predicate \eI{gref->pred-name}. The list of
modes \eI{M} is obtained by processing the string \eI{S} with the predicate
\eI{str->modes}.

Two cases must be distinguished depending on whether the string \eI{S} is
empty. If \eI{S} is empty, the compiler derives the modes from the type of the
class. It retrieves the type of \eI{C} and creates a pair \eI{pr out "term"} for
each quantification in that type. In the base case, an additional output
argument corresponding to the instance is added, again represented by the pair
\eI{pr out "term"}.

As an example, consider the declaration of the class \cI{Add}
(cf.~\cref{fig:add-class-full}). When this class is declared, the \elpi class
compiler is triggered and receives the \rocq symbol \eI{indt «Add»} as input.
Since no mode attribute is provided, the compiler receives the empty string.

From the symbol \cI{Add} the compiler retrieves its type and determines the
number of parameters. In this example, the HOAS representation of the type of
\cI{Add} in \elpi is
%
\begin{center}
  \eI{prod `T` (sort (typ «Add.u0»)) c0 \ sort (typ «Add.u0»)}
\end{center}

\noindent which indicates that the class has a single parameter.

From this information the compiler generates the predicate associated with the
class:

\begin{center}
  \eI{pred tc-Add o:term, o:term.}
\end{center}

If \eI{S} is not empty, the user has provided explicit modes for the class. In
this case, each \rocq mode is translated into the corresponding \elpi mode.
This translation is performed by the predicate \eI{str->mode}, which maps
\cI{-} to the \elpi output mode, and both \cI{+} and \cI{!} to the \elpi input
mode.

It is important to note that the goal of this type-class solver is not to
faithfully reproduce the behavior of the \rocq solver. Instead, it aims to
exploit the features of the \elpi language whenever possible.

In particular, there is no direct correspondence between \rocq modes and
\elpi modes. While the \rocq mode \cI{-} corresponds naturally to the \elpi
output mode, neither \cI{+} nor \cI{!} has a precise counterpart among the
\elpi input modes. Furthermore, a \rocq class may declare multiple mode
specifications, whereas an \elpi predicate admits only a single mode
declaration. We postpone the discussion of this discrepancy to
\cref{sec:tc-mode-and-determinacy}, after presenting the compilation of
instances and goals.

\section{Instance compilation}
\label{sec:instance-encoding}

\begin{figure}
  \input{code/toy_compiler.tex}
  \caption{Instance compiler}
  \label{fig:simple-elpi-compiler}
\end{figure}

In \rocq, instance compilation is triggered immediately after an instance
declaration. \Cref{fig:simple-elpi-compiler} shows an instance compiler
implemented in \elpi where we take more care about the type of dependent
quantification and the polarity of the instance being compiled is an essential
ingridient for compiling deep hereditary Harrop formulas.

Similarly to \cref{fig:simple-elpi-compiler-tc}, we define a \eI{compile}
predicate which calls the \eI{comp} auxiliary function. \eI{comp} this time
takes one more argument which is a boolean and tells the polarity of an element.

The compilation proceeds by analyzing the structure of the instance type.
There are three relevant cases. Rules \eI{~\PYG{c}{r1}~} and
\eI{~\PYG{c}{r2}~} handle quantifications, while rule
\eI{~\PYG{c}{r3}~} is the base case that constructs the final \elpi rule
from the information accumulated during the recursive traversal.

When the current type has the form $\forall \eI{x}: \eI{Ty}, \eI{Bo x}$, the
abstraction binds a variable of type \eI{Ty} in the body \eI{Bo}. The test
\eI{is-class? Ty} checks whether \eI{Ty} has the shape $\forall x_1 \dots x_n,
T$ (possibly with zero quantifiers), where \eI{T} is a term whose applicative
head is a type class.

If this condition holds, we are compiling a conditional instance and rule
\eI{~\PYG{c}{r$\to$}~} is applied. The rule introduces a fresh nominal variable
\eI{x} representing both the abstracted variable in \eI{Bo} and the local
instance with type \eI{Ty}. To construct the premise
corresponding to \eI{x}, the compiler recursively invokes \eI{comp} on \eI{x}
while switching the polarity of the rule. This recursive call produces the
premise \eI{M}, which abstracts \eI{x}. Compilation then continues on
\eI{Bo x}, while extending the accumulators with the new instance argument
\eI{x} and the new premise \eI{M x}.

Rule \eI{~\PYG{c}{r$\forall$}~} handles the case where the quantified type is
not a type class. In this situation, the compiler behaves exactly as rule
\eI{~\PYG{c}{r$\forall$}~} in \cref{fig:simple-elpi-compiler-tc}: it simply
consumes under the abstraction, leaving the list of premises \eI{P} unchanged
and adding the variable \eI{x} to the list of instance arguments.

As in \cref{fig:simple-elpi-compiler-tc}, the base case of \eI{comp} is reached
when the current type \eI{Ty} is not a quantification. In this case, \eI{Ty} is
a type class \eI{C} applied to a list of arguments \eI{CAg}. The compiler then
constructs the final rule by building its head and premises.

To build the head \eI{Head}, the compiler first constructs the proof term
\eI{Proof}, obtained by applying the instance \eI{I} to its arguments
\eI{rev Ag}. The list \eI{Ag} is stored in reverse order during traversal, so
it is reversed before constructing the application. The predicate
\eI{make-rule-head} takes the class name as its first argument in order to
generate the predicate corresponding to the class. The arguments of this
predicate are obtained by appending the proof term to the list of class
arguments.

The premises of the clause are stored in the accumulator \eI{P}. As with the
instance arguments, they are reversed before constructing the final rule.

Finally, the predicate \eI{build-rule} assembles the rule according to the
current polarity. With positive polarity, it produces a standard clause
\eI{Head :- Prems}. With negative polarity, it produces the implication
\eI{Prems => Head}.

\subsection{Rule priorities}

In the declaration of instances, the priority assigned to each rule plays a
fundamental role in the performance of the resolution phase. In
\rocq, every newly declared instance is associated with a priority.

To support rule priorities, we extend the instance trigger so that it also
transmits the priority information to the \elpi compiler. To reproduce a
similar behavior in \elpi, we exploit its grafting mechanism, which allows
rules in the database to be named and enables new rules to be inserted
either before or after existing ones.

In the \elpi compiler, we predeclare a reasonable number of hooks, each
associated with an integer $n$ representing a grafting position. We account
for this mechanism by modifying the \eI{compile} rule in
\cref{fig:simple-elpi-compiler} so that it takes this integer as input.
When a rule is accumulated into the database, we explicitly specify that it
must be grafted at position $n$.\marginpar{before, not at}

\subsection{Goal encoding}
\label{sec:goal-encoding}

\begin{figure}
  \input{code/toy_compiler_solver.tex}
  \caption{Goal compiler}
  \label{fig:goal-compiler}
\end{figure}

The compilation of the database is now ready. We need to write the tactic to
solve a type-class goal, we show the implementation of the \eI{solve} predicate
in \cref{fig:goal-compiler}. The tactic needs to compile the goal so that it is
a valid \elpi query. A \rocq goal in \elpi contains, among the other
information, the context \eI{C} in which the goal leaves and a \rocq term
representing the type \eI{Ty} of the goal that is to be solved.

The first operation we perform is to traverse the context, keep the hypotheses
being type-classes and compile them using the \eI{comp} procedure from the
compiler. This operation returns a list of local rules \eI{H} that will be
loaded in the program for the resolution of the goal. The next step of the goal
compilation asks to compiler to compile \eI{Ty}. As in herediray harrop formulas,
a goal is an atom in negative position, therefore, we need to make the
compilation passing \eI{ff} as polarity. Concretely,
%
\begin{center}
  \eI{comp ff P Ty [] H R} 
\end{center}

\noindent
is in charge of building an atom in negative position (\eI{ff}). Since we are
compiling a goal, we use the unification variable \eI{P} to represent the proof
of the query, while the \eI{Ty} variabile represent the goal that is to be
compiled. The list of instance parameters is empty. The list of premises is
\eI{H}, that is the context we have compiled. The compilation return an atom
\eI{R} which has the form \eI{H => Q} and \eI{Q} is a query corresponding to
a type-class and the last argument is the variable \eI{P}.

The invocation of \eI{R} will instanciate the proof term \eI{P} which will be
refined to the initial \rocq goal \eI{G}.

\subsection{Modes and determinacy}
\label{sec:tc-mode-and-determinacy}


In \rocq, the modes \cI{+} and \cI{!} impose conditions on the shape of the
argument: \cI{+} requires a ground term, while \cI{!} requires a term with a
rigid applicative head. If the condition is satisfied, the search proceeds.
In contrast, \elpi modes do not check the syntactic shape of the argument.
Instead, they modify the unification strategy by using the \matching
procedure.

This leads to different operational behavior between the \rocq solver
and the \elpi-based solver. Consider the following example:

\begin{enumerate}
  \item Assume the instance \cI{Instance dummy T : Add T. Admitted.}
  \item Suppose the first argument of \cI{Add} has mode \cI{+} (or \cI{!}).
  \item Consider the goal \cI{Add ?X}, where \cI{?X} is a metavariable.
\end{enumerate}

With the \rocq mode system, this goal has no solution because \cI{?X} is a
flexible term and therefore does not satisfy the mode constraint. In
contrast, under the \elpi mode interpretation the instance \cI{dummy} is
considered a valid solution.

In the \elpi philosophy, the instance \eI{dummy} is considered as a catchall: it
can be used on any goal for \eI{Add}. Moreover, we are creating an ambiguity in
the program, since the goal \eI{Add nat} has two solution, namely the instances
\cI{addNat} and \cI{dummy} due to bracktracking. In order to control this
behavior, in \elpi we can use the \cut, which, in \rocq is not an option.
