\chapter{Architecture of a Type-Class Solver in \rocqelpi}
\label{chap:tc}

Type classes provide an elegant mechanism for implementing ad-hoc
polymorphism~\cite{wadler1989}. As discussed in
\cref{sec:ad-hoc-poly}, they allow the same symbol to be reused in
different contexts. Moreover, as explained in
\cref{sec:th-overloading}, in a proof assistant such as \rocq{},
instances of a type class may contain properties, making theorem
overloading possible.

Using the type-class solver for overloaded theorems provides a form of
automatic proof search. Given a theorem statement represented as a
type-class goal, the solver searches the instance database for a
suitable theorem instance and automatically constructs the corresponding
proof.

This mechanism is closely related to query resolution in \prolog{}. A
type-class goal can be viewed as a query to a predicate whose arguments
correspond to the parameters of the class. Type-class instances play the
role of rules stored in a database, and the solver resolves goals by
backchaining on these rules until a proof is found.

A meta-language integration for type-class resolution must provide two components:
(1) a compiler that translates \rocq class and instance declarations into the
meta-language representation, and (2) a type-class solver that animates the
search by interacting with the resulting database.

In our setting, the meta-language used to implement the meta-solver is
\elpi. Consequently, the main task is to implement the class and instance
compiler, which incrementally builds the database on which the \elpi program
operates.

As explained in~\cref{sec:ad-hoc-poly}, 
the type-class solver itself typically follows a \prolog-like resolution
strategy: instances are tried according to their priority, and backtracking
may reconsider previous choices when a branch fails. In \elpi, this behavior
comes for free, since the resolution mechanism of the type-class solver
strongly imitates the standard execution model of the \elpi runtime.

The remainder of this chapter is organized as follows. We first demonstrate how
\rocq terms can be compiled into an \elpi database and how type-class goals can
be translated into \elpi queries, enabling proof automation through \elpi's
search mechanism. In \cref{sec:simple-instance-compiler}, we present a minimal
instance compiler, showing how a basic type-class solver can be implemented with
few lines of code. While simple, this approach lacks important features required
for handling complex instances. We therefore introduce a more powerful
compiler in \cref{sec:class-encoding,sec:instance-encoding}, where we
discuss how rule priorities influence database construction, how \rocq goals are
encoded as \elpi queries, and how users can extend the database with custom
rules to tailor the solver's behavior.

We then report on our experimental evaluation in \cref{sec:exp-res}, where the
solver is applied to real-world libraries such as \stdpp and \tlc. Benchmarks
presented in \cref{sec:bench} compare the performance of \rocq and \elpi,
analyzing how execution time in \elpi is distributed across different phases of
the search. In \cref{sec:modes-stdpp}, we examine the differences between \elpi
and \rocq modes and their impact on resolution. Finally, in
\cref{sec:unif-problems}, we discuss the unification challenges that arise when
using \elpi's unification algorithm on \rocq terms. The discussion concludes in
\cref{sec:tc-discussion}.

\section{Interfacing \rocq with \elpi for Type-Class Resolution}
\label{sec:interface-rocq-elpi}

To address type-class unification problems, we extend \rocq with the
following APIs (simplified here for clarity):

\begin{camlcode}
(* API for Type-Class Compiler *)
val register_compiler   : string ~$\to$~ (event ~$\to$~ unit) ~$\to$~ unit
val activate_compiler   : string ~$\to$~ unit
val deactivate_compiler : string ~$\to$~ unit

(* API for Type-Class Solver *)
val register_solver   : string ~$\to$~ tc_solver ~$\to$~ condition ~$\to$~ unit
val activate_solver   : string ~$\to$~ unit
val deactivate_solver : string ~$\to$~ unit
\end{camlcode}

These APIs allow one to declare new compilers and solvers inside the
\rocq\ system.

A compiler is implemented as an observer, which is triggered whenever a
new class or instance is declared. To define a compiler, one provides a
name and an event handler to \mlI{register_compiler}. Compilers are
stored in a table that maps their names to their handlers. The handler is a
higher-order function, invoked each time an event occurs. Each event
contains the class or instance currently being defined in \rocq. The
handler processes this information and updates its internal database.
Observers can be activated or deactivated when needed.

A type-class solver is registered using \mlI{register_solver}, which
takes a name, a value of type \mlI{tc_solver}, and a condition. The
\mlI{tc_solver} is a higher-order function that receives a \rocq
context together with a list of goals, and returns an updated environment
where some type-class goals may be solved. The condition specifies
whether the solver should be applied to the current list of goals. This
is useful, for instance, when a solver is intended only for specific
type-class problems.

Solvers are stored in a table indexed by their name. During resolution,
the \rocq\ type-class mechanism scans the registered solvers and selects
the first active one whose condition holds. If the condition is not
satisfied, the next solver is considered. As for observers, solvers can
be activated or deactivated by the user.

\section{Simple instance compiler}
\label{sec:simple-instance-compiler}

% A type-class goal is a \rocq type\footnote{or term, since in \rocq\ types are
%   terms.} $T$ whose head symbol is a type-class $C$. Solving such a goal amounts
% to finding a \rocq instance whose type is an instantiation of $T$.

Conceptually, a type-class goal can be translated into a query with two
arguments: the goal itself and a concrete instance witnessing it. The
search is expressed using the predicate \eI{pred tc term ~$\to$~ term}.

By invariant, a query of the form \eI{tc T I} ensures that the term
\eI{I} has type \eI{T}.


\begin{figure}
  \begin{coqcode}
  Class Add T := {
    plus: T ~$\rightarrow$~ T ~$\rightarrow$~ T;
    comm: ~$\forall$~ a b, plus a b = plus b a.
  }.

  Instance addNat : Add nat := ...
  Instance addR : Add R  := ...
  Instance addProd : ~$\forall$~ T1 T2, Add T1 ~$\rightarrow$~ Add T2 ~$\rightarrow$~ Add (T1 * T2) := ...
  \end{coqcode}
  % \input{code/plus_tc_add_inst.tex}
  \caption{The \cI{Add} type class and its instances}
  \label{fig:add-class-full}
\end{figure}%

As an example, consider the \cI{Add} type-class introduced in
\cref{sec:ad-hoc-poly}. For convenience, the full definition of the class and
its instances is reproduced in \cref{fig:add-class-full}\footnote{The auxiliary
predicates are provided in \cref{app:builtins}}.

\begin{figure}
  % \input{code/toy_compiler_tc.tex}
  \begin{elpicode}
  %         Inst  Ty    Args       Prems        Res
  pred comp term, term, list term, list prop ~$\rightarrow$~ prop.
  comp I {{lp:T ~$\rightarrow$~ lp:Bo}} Ag P (pi y\ R y) :- !,  % r$\to$
    pi x\ comp I Bo [x|Ag] [tc T x | P] (R x).
  comp I {{~$\forall$~ x, lp:(Bo x)}} Ag P (pi y\ R y) :- !, % r$\forall$
    pi x\ comp I (Bo x) [x|Ag] P (R x).
  comp I T Ag P (tc T Proof :- Body) :-   % rB
    rev Ag Ag',
    mk-app I A' Proof,
    rev P Body.

  pred compile gref ~$\rightarrow$~.
  compile G :- coq.env.typeof G Ty,
    comp (global G) Ty [] [] R,
    coq.elpi.accumulate _ "tc.db" (clause _ _ R).
  \end{elpicode}
  \caption{Simple \elpi compiler}
  \label{fig:simple-elpi-compiler-tc}
\end{figure}

After an instance is declared, a trigger activates the instance compiler
shown in \cref{fig:simple-elpi-compiler-tc}. The compiler is similar to the
example presented in \cite[Sec.~4.5]{hdr}.

The entry point of the compiler is the predicate \eI{compile}, which takes the
global reference \eI{G} of the instance as input. Using the
\eI{coq.env.typeof} API, the compiler retrieves the type \eI{Ty} of \eI{G}.
Compilation then proceeds by invoking the auxiliary predicate \eI{comp} to
produce the rule \eI{R}. Finally, \eI{coq.elpi.accumulate} adds the clause
\eI{R} to the database, here called \eI{tc.db}.

The predicate \eI{comp} performs the core of the compilation. It takes four
arguments: the instance term; its type, which is structurally consumed during
recursion; and two accumulators storing the list of instance arguments and the
list of premises that will form the body of the resulting rule. From these
inputs, \eI{comp} produces the \elpi rule corresponding to the compiled
instance.

Compilation proceeds by analyzing the structure of the instance type. Three
cases are relevant. Rules \eI{~\PYG{c}{r$\to$}~} and
\eI{~\PYG{c}{r$\forall$}~} handle quantifications, while rule
\eI{~\PYG{c}{rB}~} is the base case that constructs the final \elpi rule from
the information accumulated during the recursion.

The base case is reached when the current type \eI{Ty} is not a quantification.
The compiler then constructs the final rule by assembling its head and body.

The head is the predicate \eI{tc} applied to the instance type \eI{T} and to a
proof term \eI{Proof}. The proof is obtained by applying the instance \eI{I} to
its arguments \eI{rev Ag}. Since the arguments are accumulated in reverse order
during the traversal, the list \eI{Ag} is reversed before building the
application.

The premises of the clause are stored in the accumulator \eI{P}. As for the
arguments, the list is reversed before constructing the final rule.

For example, compiling the instance \cI{addNat} produces the rule

\begin{center}
  \eI{tc {{Add nat}} {{addNat}}}.
\end{center}

When the current type \eI{Ty} is a quantification, the compiler introduces a
fresh nominal variable representing the bound variable in the recursive call.
Two situations must be distinguished depending on the shape of the
quantification.

If the quantification corresponds to a premise of the instance, rule
\eI{~\PYG{c}{r$\to$}~} is used. This rule introduces a fresh variable \eI{x}
representing the conditional instance with type \eI{T}. The premise
\eI{tc T x} is added to the list of premises \eI{P}, and the variable \eI{x} is
added to the list of instance arguments \eI{Ag}.

Rule \eI{~\PYG{c}{r$\forall$}~} handles dependent quantification corresponding
to parameters of the instance, that are supposed not to have a class as type. In
this case the abstraction is simply consumed: the list of premises \eI{P}
remains unchanged, while the variable \eI{x} is added to the list of instance
arguments.

Both rules \eI{~\PYG{c}{r$\to$}~} and \eI{~\PYG{c}{r$\forall$}~} return a term
of the form \eI{(pi y\ R y)}, where \eI{R} is the result of the recursive call
to \eI{comp}. Since \eI{R} has type \eI{term ~$\to$~ prop} and abstracts the local
variable \eI{x}, the compiler abstracts \cI{x}
in the result \eI{pi y\ R y}. This ensures that the resulting rule is
closed (ground), as required by the \eI{coq.elpi.accumulate} predicate.

As an example, consider the instance \eI{addProd}, whose type is

$$
  \forall\ \underbrace{x\ y}_{\eI{~\PYG{c}{r$\forall$}~}},
  \underbrace{\cI{Add}\ x \to \cI{Add}\ y}_{\eI{~\PYG{c}{r$\to$}~}} \to
  \underbrace{\cI{Add}\ (x * y)}_{rB}.
$$

Compiling this instance yields the following \elpi rule:

\begin{elpicode}
  pi L\ pi R\ pi PL\ pi PR\  % this line is optional in toplevel rules
    tc {{Add (lp:L * lp:R)}} {{addProd lp:L lp:R lp:PL lp:PR}} :-
      tc {{Add lp:L}} PL, tc {{Add lp:R}} PR.
\end{elpicode}

This rule provides a proof for \eI{Add (x * y)} provided that the two premises
\eI{Add x} and \eI{Add y} can be solved. Note that the generated rule
contains explicit \eI{pi} quantifiers for the unification variable in the rule.
In a hand-written rule they become optional.% \marginpar{FIXME: enrico, nota snip pag 37}

Given a \rocq goal \eI{G}, the tactic retrieves its type \eI{Ty}, performs a

\paragraph*{Complete example of execution}
To illustrate how type-class goals are delegated from \rocq to \elpi, we
present a complete example. Consider the following \rocq goal, using the class
and instances defined in \cref{fig:add-class-full}:

\begin{prooftree}
  \AxiomC{}
  \UnaryInfC{$?s : \cI{plus}\ (\pig, 3)\ (e, 4) = \cI{plus}\ (e, 4)\ (\pig, 3)$}
\end{prooftree}

This goal can be solved using the commutativity property of addition. The
interesting part is the associated type-class resolution problem, which
consists in finding an implementation of \cI{plus} from the instance database,
that is, an instance of \cI{Add} for the type \cI{(R * nat)}.

The corresponding \elpi goal is
\eI{(goal [] X0 {{Add (R * nat)}} X1 [])}. This goal is solved through the
recursive call \eI{tc {{Add (R * nat)}} P}. Applying the rule corresponding to
\cI{addProd} generates two recursive type-class goals, which are solved using
the instances \cI{addR} and \cI{addNat}, respectively. As a result,
\eI{P} is instantiated with \cI{addProd R nat addR addNat}, which is returned
to \rocq as the solution to the type-class goal.

\paragraph*{Concluding remarks}

The implementation presented in this section illustrates the expressive power of
the \elpi language: the core of the compiler fits in roughly eight lines of
code, while a similar number of lines is required to complete the \elpi command
for the compiler. The solver itself consists of a single rule. 

However, this
simplified implementation has some limitations it is worth to point out.

\begin{itemize}
  \item The predicate \eI{tc} does not expose the class arguments as \elpi
        arguments. Consequently, the \rocq modes (see~\cref{sec:ad-hoc-poly}) declared on a class are not preserved
        in the \elpi solver. The compiler should therefore generate a specialized
        predicate for each class, with arguments and modes matching those of the
        class so that rule backchaining can be performed correctly. This problem
        is addressed in \cref{sec:class-encoding}.
  \item Rule $r\forall$ does not account for the possibility that the quantified
        variable $x$ is itself a premise of the class. In complex instances,
        $x$ may have a class as its type and should therefore appear as a
        premise in the generated rule. This problem is addressed in
        \cref{sec:instance-encoding}.
  \item The compiler does not handle instances of the form
        $(c_1 \to c_2) \to c_3$, where the implementation of $c_3$ requires a
        proof of $c_2$ in a context extended with a local instance of $c_1$.
        Supporting such cases requires generating 
        complex formulas and therefore tracking the positive/negative
        position (see~\cref{sec:elpi-syntax}) of the instance being
        compiled. This problem is addressed in
        \cref{sec:instance-encoding}.
  \item The \eI{solve} rule of the solver ignores the context of the goal. As
        discussed in \cref{sec:elpi-commands-tactics}, the first projection of a
        \eI{goal} in \rocqelpi is its context, which may contain local
        instances that should be compiled and used during resolution. This
        problem is addressed in \cref{sec:goal-encoding}.
\end{itemize}

\section{Class compilation}
\label{sec:class-encoding}

When a class $c$ is declared in \rocq, the compiler generates a corresponding
\elpi predicate. If the class has $n$ parameters, the generated predicate has
$n+1$ arguments: the first $n$ arguments correspond to the parameters of $c$,
while the final argument represents the instance witnessing the class in the
current rule.

From the perspective of the \elpi solver, two aspects of a class declaration in
\rocq are particularly relevant: the global reference identifying the class and
the modes associated with its parameters. In \rocq, users may explicitly
declare modes using the attribute \cI{~\#~[mode="..."]}. If no mode declaration
is provided, the parameters of the class are considered outputs by default.

The compiler responsible for generating the corresponding \elpi predicate is
shown in \cref{fig:class-compiler}\footnote{The auxiliary
predicates are provided in \cref{app:builtins}.}.

\begin{figure}
  \input{code/toy_compiler_pred.tex}
  \caption{Class compiler}
  \label{fig:class-compiler}
\end{figure}

The entry point of the compiler is the predicate \eI{add-class-pred}, which
takes two arguments: the global reference \eI{C} of the class and a string
\eI{S} describing its modes. The string \eI{S} encodes the modes using the
three \rocq symbols \cI{-, +, !}, separated by spaces. If the user does not
provide an explicit mode declaration, \eI{S} is the empty string.

Predicates can be created dynamically in \elpi using the API
\eI{coq.elpi.add-predicate} (see \cref{sec:elpi-commands-tactics}). 
% This primitive takes four arguments: the database
% in which the predicate will be stored (in our case \eI{tc.db}), the (optional) indexing
% strategy, the predicate name \eI{N}, and a list \eI{M} of values of type
% \eI{mode-type}. Each element of \eI{M} is a pair specifying the mode and the type of one
% argument of the predicate. The predicate name is constructed from the global
% reference of the class using the predicate \eI{gref~$\to$~pred-name}. The list of
% modes \eI{M} is obtained by processing the string \eI{S} with the predicate
% \eI{str~$\to$~modes}.

Two cases must be distinguished depending on whether the mode string is
empty. If it is empty, the compiler derives the modes from the type of the
class. It retrieves the type of \eI{C} and creates a pair \eI{pr out "term"} for
each quantification in that type. In the base case, an additional output
argument corresponding to the instance is added, again represented by the pair
\eI{pr out "term"}.

As an example, consider the declaration of the class \cI{Add}
(cf.~\cref{fig:add-class-full}). When this class is declared, the \elpi class
compiler is triggered and receives the \rocq symbol \cI{«Add»} as input.
Since no mode attribute is provided, the compiler receives the empty string.

From the symbol \cI{Add} the compiler retrieves its type and determines the
number of parameters. In this example, the HOAS representation of the type of
\cI{Add} in \elpi is \eI{{{Type ~$\to$~ Type}}} which indicates that the class
has a single parameter.

From this information the compiler generates the predicate associated with the
class:

\begin{center}
  \eI{pred tc-Add ~$\to$~ term, term.}
\end{center}

If \eI{S} is not empty, the user has provided explicit modes for the class. In
this case, each \rocq mode is translated into the corresponding \elpi mode.
This translation is performed by the predicate \eI{str->mode}, which maps
\cI{-} to the \elpi output mode, and both \cI{+} and \cI{!} to the \elpi input
mode.

\subsection{\rocq and \elpi mode discrepancies}
\label{sec:tc-mode-and-determinacy}

Our type-class solver is not intended to replicate the \rocq solver. Instead, it
aims to exploit, whenever possible, the features of the \elpi language. A
natural claim is that mapping two \rocq mode to only one in \elpi is that the
\rocq and \elpi type-class solvers will have different runtime behaviors.

We can note that there is no direct correspondence between \rocq modes and
\elpi modes. While the \rocq mode \cI{-} corresponds naturally to the \elpi
output mode, neither \cI{+} nor \cI{!} has a precise counterpart among the
\elpi input mode. Furthermore, a \rocq class may declare multiple mode
specifications, whereas an \elpi predicate admits only a single mode
declaration.

We recall that the \rocq modes \cI{+} and \cI{!} impose conditions on the shape
of the argument: \cI{+} requires a ground term, while \cI{!} requires a term
with a rigid applicative head. During the resolution phase, if a goal does not
satisfy the mode constraint imposed by the class declaration, a failure
immediately stops the instance search. In contrast, \elpi modes do not check the
shape of the argument before backchaining the query into the database, it, instead,
modifies the unification strategy by using the \matching procedure
(see~\cref{sec:elpi-semantics}).

In order to see the different mode behavior of the \rocq and \elpi modes, we
rework the implementation of the \cI{Add} type class.
%
\input{code/add_dummy.tex}

Consider a goal $g = \cI{Add ?X}$ where \cI{?X} is an existential
variable. With the \rocq mode system, this goal has no solution because the
argument of the class is a non-ground term and therefore does not satisfy the
mode constraint. In contrast, under the \elpi mode interpretation the instance
\cI{addDummy} is a valid solution.

In \elpi, the instance \cI{addDummy} acts as a catchall rule: the first argument
of the \cI{Add} class is a variable, i.e., a pattern that can match any goal
involving \cI{Add}. Catchall rules have two main consequences. First, in the
goal $g$ above, the variable \cI{?X} is not assigned: the proof term leaves a hole in
the solution. Second, they introduce a source of nondeterminism in \elpi. As
their name suggests, catchall rules can apply to any goal, and
overlap with other applicable instances, resulting in multiple possible rule
selections. This nondeterministic behavior is detected by the determinacy
checker presented in \cref{chap:det-elpi}.

\section{Instance compilation}
\label{sec:instance-encoding}

\begin{figure}
  \input{code/toy_compiler.tex}
  \caption{Instance compiler}
  \label{fig:simple-elpi-compiler}
\end{figure}

As explained in \cref{sec:interface-rocq-elpi}, instance compilation is
triggered immediately after an instance declaration.
\Cref{fig:simple-elpi-compiler} shows an instance compiler more advanced than
\cref{sec:simple-instance-compiler}. It takes into account the type of dependent
quantification and the positive/negative position of the term being compiled.

Similarly to \cref{fig:simple-elpi-compiler-tc}, we define a \eI{compile}
predicate which calls the \eI{comp} auxiliary function. This time, \eI{comp}
takes one more boolean argument.

The compilation proceeds by analyzing the structure of the instance type.
There are three relevant cases. Rules \eI{~\PYG{c}{r$\to$}~} and
\eI{~\PYG{c}{r$\forall$}~} handle quantifications, while rule
\eI{~\PYG{c}{rB}~} is the base case that constructs the final \elpi rule
from the information accumulated during the recursive traversal.

When the current type has the form $\forall \eI{x}: \eI{Ty}, \eI{Bo x}$, the
abstraction binds a variable of type \eI{Ty} in the body \eI{Bo}. The test
\eI{is-class? Ty} checks whether \eI{Ty} has the shape $\forall x_1 \dots x_n,
\eI{app[C|Ag]}$ (possibly with zero quantifiers) and \eI{C} is a declared type class.

If this condition holds, we are compiling a conditional instance and rule
\eI{~\PYG{c}{r$\to$}~} is applied. The rule introduces a fresh nominal variable
\eI{x} representing both the abstracted variable in \eI{Bo} and the local
instance with type \eI{Ty}. To construct the premise
corresponding to \eI{x}, the compiler recursively invokes \eI{comp} on \eI{x}
while switching the boolean in the recursive call. This recursive call produces the
premise \eI{M}, which abstracts \eI{x}. Compilation then continues on % \marginpar{FIXME: enrico?}
\eI{Bo x}, while extending the accumulators with the new instance argument
\eI{x} and the new premise \eI{M x}.

Rule \eI{~\PYG{c}{r$\forall$}~} handles the case where the quantified type is
not a type class. In this situation, the compiler behaves exactly as rule
\eI{~\PYG{c}{r$\forall$}~} in \cref{fig:simple-elpi-compiler-tc}: it simply
consumes the abstraction, leaving the list of premises \eI{P} unchanged
and adding the variable \eI{x} to the list of instance arguments.

As in \cref{fig:simple-elpi-compiler-tc}, the base case of \eI{comp} is reached
when the current type \eI{Ty} is not a quantification. In this case, \eI{Ty} is
a type class \eI{C} applied to a list of arguments \eI{CAg}. The compiler then
constructs the final rule by building its head and premises.

To build the head \eI{Head}, the compiler first constructs the proof term
\eI{Proof}, obtained by applying the instance \eI{I} to its arguments
\eI{rev Ag}. %The list \eI{Ag} is stored in reverse order during traversal, so
% it is reversed before constructing the application.
The predicate
\eI{make-rule-head} takes the class name as its first argument in order to
generate the predicate corresponding to the class. The arguments of this
predicate are obtained by appending the proof term to the list of the class
arguments.

The premises of the clause are stored in the accumulator \eI{P}. As with the
instance arguments, they are reversed before constructing the final rule.

Finally, the predicate \eI{build-rule} assembles the rule according to the
current position tag: positive or negative. In the former
case, it produces a standard clause
\eI{Head :- Prems}. Otherwise, it produces the implication % \marginpar{FIXME: enrico,per soddisfare sintassi}
\eI{Prems => Head}.

Given the instance in \cref{fig:add-class-full}, this version of the
compiler produces the following rules:

\begin{elpicode}
  tc-Add {{nat}} {{addNat}}.
  tc-Add {{R}} {{addR}}.
  pi L \ pi R \ pi PL \ pi PR \ % this line is optional in toplevel rules
    tc-Add {{lp:L * lp:R}} {{addProd lp:L lp:R lp:PL lp:PR}} :-
      tc-Add L PL, tc-Add R PR.
\end{elpicode}

\noindent
These rules are similar to those produced by the compiler in
\cref{sec:simple-instance-compiler}, except for the specialization of the
predicate \eI{tc-Add} for the \cI{Add} class.

while \texttt{and} and

respectively.

The function \cI{interp} assigns a semantics to \texttt{mlogic}
formulas by translating them into \rocq{} propositions. This
interpretation is compositional: an atom evaluates to a proposition using
the \cI{to_prop} function, a conjunction is interpreted as a logical conjunction,
and an implication as a function type.

Automatic reasoning is expressed via the type-class
\texttt{Provable T}, which packages a proof of \texttt{interp T}.
This allows \rocq{}'s type-class resolution mechanism to act as a
proof search procedure.

The inference rules of the logic are encoded as type-class
instances. The instance \texttt{Pand} corresponds to conjunction
introduction: if \texttt{F1} and \texttt{F2} are provable, then
\texttt{and F1 F2} is also provable.

Similarly, the instance \texttt{Pimpl} captures implication
introduction. It states that to prove \texttt{impl F1 F2}, it
suffices to show that \texttt{F2} is provable under the assumption
\texttt{F1}.

The instance \cI{Pand} is compiled into:

\begin{elpicode}
  pi L \ pi R \ pi PL \ pi PR \ % this line is optional in toplevel rules
    tc-Provable {{and lp:L lp:R}} {{Pand lp:L lp:R lp:PL lp:PR}} :-
      tc-Provable L PL, tc-Provable R PR.
\end{elpicode}

\noindent
This rule closely mirrors the rule for \cI{addProd}, since both rely on the same
search principle: constructing a proof requires recursively constructing proofs
for the subcomponents (the arguments of \cI{and}, respectively \cI{*}).

The rule corresponding to the instance \cI{Pimpl} is more subtle,
since it involves a higher-order hypothesis. Its type is:

$$
  \forall \cI{F1 F2},
  \underbrace{
    (\underbrace{\cI{Provable F1}}_{positive} \to
    \underbrace{\cI{Provable F2}}_{negative})
  }_{negative}
  \to
  \underbrace{\cI{Provable (impl F1 F2)}}_{positive}
$$

The compiled rule is:

\begin{elpicode}
  pi F B Q \ % this line is optional in toplevel rule
    tc-Provable {{impl lp:F lp:B}} {{Pimpl lp:F lp:B lp:Q}} :-
      pi p \ tc-Provable F p => tc-Provable B {{lp:Q lp:p}}.
\end{elpicode}

The structure of this rule matches the intended semantics: the head
targets \cI{impl F B}, while the body attempts to construct a proof
of \cI{B} in a context extended with the assumption \cI{F}.

Even though this rule is very close to its final implementation, it is still not
the implementation one would naturally write. In particular, the premise
\eI{tc-Provable B {{lp:Q lp:p}}} is not flexible enough, since the solution
\eI{{{lp:Q lp:p}}} requires a term with exactly the shape \eI{app[Q, p]}. This
is too restrictive, since the variable \eI{Q} may depend on \eI{p}. A more
flexible solution is to replace this premise with \eI{tc-Provable B (X p)}. In
this way, we use the \elpi term application of a higher-order variable \eI{X}
depending on the proof term \eI{p}.

However, we must be careful: \eI{X} is not a \rocq term, but an \elpi term
living in the function space. Therefore, some additional work is required to
establish the correspondence between the variable \eI{X} and the variable \eI{Q}
appearing in the rule head. This is precisely the subject of
\cref{chap:ho-for-free}.


\subsection{Rule Priorities}
\label{sec:rule-prio}

When declaring instances, the priority assigned to each rule plays a
fundamental role in the performance of the resolution phase. In \rocq,
every instance is associated with a priority at declaration time.

To support rule priorities, we extend the instance trigger so that it
also propagates priority information to the \elpi compiler. To reproduce
a similar behavior in \elpi, we exploit its grafting mechanism (see~\cref{sec:elpi-rule-names}), which
allows rules in the database to be named and enables new rules to be
inserted before or after existing ones.

In the \elpi compiler, we predeclare a fixed number of hooks, each
associated with an integer $n$ representing a grafting position. We
account for this mechanism by modifying the \eI{compile} rule in
\cref{fig:simple-elpi-compiler} so that it takes this integer as input.
When a rule is added to the database, we explicitly specify that it must
be grafted \eI{:before} the hook named $n$.

The choice of grafting \rocq instances into the \elpi database by number is only
a partial solution, but it is necessary to preserve compatibility with \rocq. In
particular, we must ensure that \rocq instances can be grafted into the \elpi
database while preserving the declaration order of these instances. However, the
\rocq grafting mechanism is less expressive than the one provided by \elpi.
Relying on a numerical ordering scheme is sometimes limiting: a user may wish to
insert an instance relative to other instances already present in the database,
for example by referring to them by name and specifying that a new instance
should be placed before or after them. Such a mechanism would provide a more
flexible way of controlling instance ordering. Nevertheless, in order to remain
compatible with \rocq, we reproduce its grafting behavior, where each instance
is inserted at a position determined by its numerical priority.

\subsection{Goal Encoding}
\label{sec:goal-encoding}

\begin{figure}
  \input{code/toy_compiler_solver.tex}
  \caption{Goal compiler}
  \label{fig:goal-compiler}
\end{figure}

With the database compilation in place, we now define the tactic used to
solve type-class goals. The implementation of the \eI{solve} predicate is
shown in \cref{fig:goal-compiler}.

A \rocq goal in \elpi contains, among other information, the context
\eI{C} in which the goal is defined and a term \eI{Ty} representing the
type to be solved. The first step is to traverse the context, select the
hypotheses that correspond to type classes, and compile them using the
\eI{comp} procedure. This produces a list of local rules \eI{H}, which
are added to the program during resolution.

Next, we compile the goal type \eI{Ty}. The
compilation is performed with boolean set to \eI{ff}. Concretely,
%
\begin{center}
  \eI{comp ff P Ty [] H R}
\end{center}

\noindent
constructs a formula in negative position. Here, \eI{P} is a unification
variable representing the proof term, \eI{Ty} is the goal to be compiled,
the list of instance parameters is empty, and \eI{H} provides the
premises extracted from the context. The result of the compilation is a
formula \eI{R} of the form \eI{H => Q}, where \eI{Q} is a query corresponding
to a type class whose proof argument is \eI{P}.

Evaluating \eI{R} instantiates the proof term \eI{P}, which is then used
to refine the original \rocq goal.

\paragraph*{Example of execution}

We consider as an example of execution the following \rocq goal,
where local instances are taken into account for the resolution.

\begin{prooftree}
  \AxiomC{$\cI{T}: \cI{Type} \qquad x : \cI{T} \qquad H : \cI{Add}\ \cI{T}$}
  \UnaryInfC{$?s : \cI{plus}\ (x, 3)\ (x, 4) = \cI{plus}\ (x, 4)\ (x, 3)$}
\end{prooftree}

The goal can be solved using the \cI{comm} property over addition. What is % \marginpar{FXIME:enrico? why reduce the lemma, it is the same as pag 33}
interesting here is the type-class goal aiming to find the right implementation
of \cI{plus} in the database, i.e. an instance of \cI{Add} applied to the type
\cI{(T * nat)}, where \cI{T} appears in the hypothesis lists.

The \elpi goal is:

\begin{coqcode}  
nabla t \ nabla x \ nabla h \ seal
  (goal 
    [decl h `H` {{Add lp:t}}, decl x `x` t, decl t `T` {{Type}}] % the context
    (X0 t x h)
    {{Add (lp:t * nat)}}                                     % the conclusion
    (X1 t x h) [])
\end{coqcode}

The context contains a premise which is a typeclass, namely \cI{h}. It is compiled
into the simple local rule \eI{tc-Add t h}: the proof for the type-class
\cI{Add} applied to the local type \cI{t} is the local hypothesis \cI{h}. The
conclusion is encoded as the query \cI{tc-Add {{lp:t * nat}} P}.

To solve this goal we backchain the query in the program extended with
\eI{tc-Add t h} and obtain the proof $\eI{P} := \cI{addProd lp:t nat lp:h addNat}$.

\subsection{Benchmarks}
\label{sec:bench}

Using the instance compiler show in the previous section and the \elpi
interpreter to solve type-class goals, we evaluate our solver on existing
libraries, in particular \tlc~\cite{tlc} and \stdpp~\cite{stdpp}. Both libraries
use type-class inference as a main implementation tool. Studying them helps us
understand the practical needs of \rocq users. %Moreover, \stdpp uses
%modes in type-class resolution. 
This can reveal limitations of our
implementation and suggest directions for future work. An important
goal of this evaluation is also to compare our solver with the native
\rocq solver.

As a first benchmark, we consider a set of classes and instances from
\stdpp. We focus on the \cI{Inj} type class, defined as follows:

\begin{coqcode}
Class Inj {A B} (f : A ~$\to$~ B) :=
  inj x y : f x = f y ~$\to$~ x = y.
\end{coqcode}

The type class \cI{Inj} expresses that a
function $f$ is injective if, for all $x$ and $y$, $f\ x = f\ y$
implies $x = y$.

The library provides $13$ instances of this class. These include, for example,
instances for the identity function and injections of the sum type. The instance
we target in our benchmark is function composition. The composition (written
$\circ$) of two functions \cI{f} and \cI{g} is injective if both functions are
injective.

To evaluate performance, we measure the time needed by the instance
solver to solve goals of increasing size. This helps us understand
where time is spent and compare \elpi with \rocq. The benchmark goals
are generated by the following function. It builds a balanced tree
where internal nodes are compositions and leaves are a fixed
injective function $f$:

$$
g_n =
\begin{cases}
  f                     & \text{if } n = 0, \\
  g_{n-1} \circ g_{n-1} & \text{if } n > 0.
\end{cases}
$$

For a given $n$, we submit the goal \cI{Inj ~$g_n$~} to the solver. The size of
this goal grows exponentially with $n$. \Cref{fig:bench-1} shows the resolution
time for $n$ from $0$ to $15$. The $x$-axis is the number of nodes (logarithmic
scale), and the $y$-axis is the time in seconds. The plot compares the time
spent by the \rocq and \elpi solvers.

For \elpi, we split the total time into four parts: type-class
resolution, query construction (translation of \rocq terms into
\elpi), communication between \elpi and \rocq, and typechecking of
the final proof.

For \rocq, query construction and communication intuitively do not appear as
part of the total time. However, it is harder to separate the time cost of
instance search and typechecking, since they are mixed together. In fact,
partial typechecking is done after each instance selection. For this reason, we
cannot easily measure them separately.

The results in \cref{fig:bench-1} show that instance search is very
fast. For goals with $2^{15}$ nodes, it takes about $0.25$ seconds
out of a total of $4.9$ seconds. On the other hand, query
construction and communication grow with the size of the goal. This
cost comes from the interaction between \rocq and \elpi and does not
depend on the \elpi interpreter itself.

The main cost is typechecking the proof term. It represents about
$77\%$ of the total time. We consider two ways to reduce this cost.
First, we can introduce ad hoc rules in the \elpi database for the specific problem.
Second, we can skip typechecking of the produced proof.

The first approach also produces smaller proof terms, which are
faster to check. As explained in
\cref{sec:user-defined-rules}, memory sharing can reduce time and space
complexity from exponential to linear. This effect is shown in
\cref{fig:bench-2}: smaller terms give faster typechecking and
faster translation from \elpi to \rocq. However, this solution is
not very portable, since it depends on the specific goal.

The second approach, i.e. skipping typechecking, reduces the time of
the proof refinement to the goal by about a factor of $5$, as shown in
\cref{fig:bench-3}. In most cases, this does not cause problems. The
proof term should be correct, because the rules in the database are
compiled in a context where they already typecheck. The main problem
comes from universe constraints~\cite{universes}.

In the \elpi compiler, universes are removed from the compiled rules to simplify
unification. For example, the \rocq term \cI{Type@{i}} corresponds to
the HOAS term \eI{sort (typ i)}. During compilation, the level $i$ is
replaced by a unification variable. This allows matching terms at
different levels at runtime.

However, removing universes from the database can introduce inconsistencies or
may forget to state some universe constraint. These are usually detected during
typechecking. A possible solution, which we do not implement, is to add universe
constraints explicitly in the compiled rules. In this way, a small part of typechecking
would be done during the search. This approach is similar to the strategy used
by the \rocq solver.

\subsection{Unification problems}
\label{sec:unif-problems}

As explained in~\cref{sec:interface-rocq-elpi}, the \elpi solver can be used as
an alternative -- not a replacement -- to the \rocq solver. In a development,
one can enable or disable either solver depending on the needs.

When running the \elpi solver on existing libraries, one may observe
failures in situations where the \rocq solver succeeds, and vice versa,
although the latter case is rare. In our setting, we focused on making the
target library compile with the \elpi solver. % Note that in this library,
% all type-class problems are solvable with the \rocq solver.

When a type-class resolution fails in \elpi, the cause can be investigated by
inspecting the execution traces of both \elpi (using the \elpi trace
browser~\cite[Sec.~3.5]{hdr}) and \rocq (using the \cI{Set Typeclasses Debug}
option). Our analysis shows that most discrepancies arise from unification
issues. We distinguish two main categories encountered in our study: failures
related to $\beta\eta$-reduction, and failures related to $\delta$-reduction
(see~\cite{rocq-unif}).

A typical $\beta\eta$-unification example is the term
\cI{fun x y => ?F y x} unified with \cI{map}\footnote{The standard list map
function}, where \cI{?F} is a unification variable. In \rocq, this succeeds
by instantiating \cI{?F} with \cI{fun x y => map y x}. In contrast, \elpi
represents these terms as HOAS expressions, namely
\eI{fun _ _ x\ fun _ _ y\ app[F, y, x]} and
\eI{global (const «map»)}. Since these terms have different rigid heads,
unification fails.

This behavior is expected from the \elpi unification algorithm, but it is % \marginpar{FIXME: enrico? random order of sentences?}
problematic in the context of instance resolution, where equivalent
problems -- expressed differently -- should be solvable. For example, using
\elpi-style $\lambda$-abstraction and application, the term
\eI{(x\ y\ F y x)} unifies with \cI{map}, assigning \eI{F} to
\eI{x\ y\ map y x}. To address this, we extend the instance compiler to
detect potential $\beta\eta$-unification issues. Such terms are replaced
with a fresh unification variable $v$, simplifying unification in \elpi.
The variable $v$ is then linked back to the original \rocq term, so that
instantiations in \elpi are reflected in \rocq. This approach led to our
contribution presented in~\cite{fissore2024}, described in detail in
\cref{chap:ho-for-free}, which provides an automatic solution to
$\beta\eta$-unification issues.

A concrete example of $\beta\eta$-unification failure in the \elpi solver
arises from the compiled rule for the instance \cI{Pimpl}, introduced at
the end of \cref{sec:instance-encoding}. Consider the goal
\cI{Provable (impl (atom a) (atom a))} for some atom \cI{a}. This goal has
the solution \cI{Pimp (atom a) (atom a) (fun x => x)}. However, the compiled rule
fails to find this solution due to $\beta\eta$-unification.

After applying the rule for \cI{Pimpl}, the sub-query becomes

\begin{center}\eI{tc-Provable {{atom a}} {{lp:Q lp:p}}}\end{center}

\noindent in a context extended with the
hypothesis $h = \eI{tc-Provable {{atom a}} p}$. Solving the sub-query
requires unifying it with $h$. However, the HOAS term corresponding to
\eI{{{lp:Q lp:p}}} is \eI{app[Q, p]}, which cannot be unified with \eI{p},
whose HOAS representation is simply \eI{p}.

The second class of issues concerns $\delta$-unification, which is not
handled by the \elpi unification mechanism. In \rocq, definitions can be
unfolded during unification. For example, the function $id$ unifies with
\cI{fun x => x} after unfolding its definition. In contrast, \elpi{} -- and
more generally \prolog-like systems -- does not support definitional
unfolding during unification.

An example of failure due to missing $\delta$-unification is given by the
following code, from the library \tlc:

\begin{coqcode}
  Class Extens A := ...
  Instance Extens_f1 A1 A2: Extens (~$\forall$~ x1 : A1, A2 x1) := ...
  Definition map A B := A ~$\to$~ option B.
\end{coqcode}

The \rocq solver can solve the goal \cI{Extens (map A B)} using the
instance \cI{Extens_f1}. However, \elpi fails because \cI{map A B} does not
syntactically match a term starting with a quantifier.

Providing a general and automatic solution for $\delta$-unification in
\elpi is non-trivial. In some cases, the absence of $\delta$-unification is
actually desirable, since unfolding definitions can make unification
unpredictable and harder to debug. Moreover, it may introduce performance
issues~\cite{rocq-unif}.

To address $\delta$-unification issues, the user has two options. First,
one can declare \cI{map} as a notation for \cI{A ~$\to$~ option B}, since
notations are unfolded by the elaborator, creating no ambiguity in the
unification algorithm. Alternatively, one can add an
ad-hoc rule to the solver:

\begin{coqcode}
  Elpi Accumulate TC.Solver lp:{{
    tc-Extens {{map lp:A lp:B}} R :-
      tc-Extens {{lp:A ~$\to$~ option lp:B}} R.
  }}.
\end{coqcode}

This rule manually implements unfolding: when the first argument of
\cI{Extens} is \cI{map}, the solver recursively processes the unfolded
definition.

\section{Discussion}
\label{sec:tc-discussion}

The previous sections highlighted the flexibility of the \elpi language and its
suitability for compiling \rocq terms into \elpi rules. In particular, \elpi
provides a natural framework for proof automation: its \prolog-like search engine
acts as an inference mechanism, provided that the program contains the
derivation rules required to solve a given query. Although the type-class engine
in \rocq exhibits a similar behavior, our goal was not to faithfully reproduce
the \rocq solver. Instead, we aimed to leverage the distinctive features of \elpi
whenever possible.

A key advantage inherited from \elpi is the control the user have over the search
process. This control is achieved through several mechanisms, including rule
priorities, predicate modes, the \unify/\matching unification algorithm, and the
\cut operator. All these aspects have been discussed in previous sections, with
the exception of the \cut operator.

We have deliberately postponed the discussion of \cut, as it has no direct
counterpart in the \rocq type-class solver. As explained in
\cref{sec:elpi-semantics}, the \cut operator allows the user to commit to a
solution once certain conditions (e.g., rule guards) are satisfied. To fully
exploit this feature, the \rocq language would require a syntax extension capable of
indicating where \cut should be introduced during compilation to \elpi rules.
Discussions with other researchers suggest that \cut may provide an effective
approach to addressing a well-known issue in type-class resolution: determinacy.

In logic programming, determinacy is the property that a predicate produces at
most one solution for any given call. The \cut operator is a central mechanism
for enforcing this property. Transposed to type-class resolution, determinacy
would ensure that a class declared as deterministic remains so, regardless of
the rules added to the database.

In \rocq, the flag \cI{Typeclasses Unique Solutions} enforces a related
behavior: it computes all possible solutions to a type-class query and returns a
result only if exactly one solution exists; otherwise, it raises an error.
However, as noted in the \rocq manual~\cite{rocq_class_command}, this approach is
computationally expensive, since it requires exploring the entire search tree.

In contrast, determinacy has been extensively studied in logic programming
(e.g.,~\cite{warren1989,king2005,henderson1996}) and can be verified statically
using abstract interpretation. This approach incurs no runtime cost during goal
execution. Moreover, since determinacy is a general property of logic programs
rather than being specific to type-class resolution, we extend \elpi with a
determinacy checker implemented at the compiler level. As a result, all
applications built on \elpi, including the type-class solver, can benefit from
this analysis.

We presented this work in~\cite{fissore2026}, where we describe the implementation
of a determinacy checker for \elpi that accounts for both the \cut operator and
higher-order features such as local rule insertion. A detailed discussion is
provided in \cref{chap:det-elpi}. Finally, we formalize the first-order fragment
of the checker within \elpi in the \rocq system; this formalization is described
in \cref{chap:mechanization}.% \marginpar{FIXME: enrico?}
