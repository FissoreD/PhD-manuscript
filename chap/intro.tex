\chapter{Introduction}
In computer science, an essential feature of most programming languages
is the way users interact with the interpreter or compiler. Computers
operate on binary expressions, but humans cannot easily write programs
that are too far from their natural way of thinking.

Modern languages provide many tools to improve the coding experience.
For instance, syntactic sugar~\cite{synt-sugar} allows programmers to
write code in a form that is closer to natural reasoning rather than
the underlying core syntax. Static checkers verify that programs satisfy
expected properties, such as type safety~\cite{type-safety}, code quality
via linters~\cite{linter}, and correct dependencies. Compilers also offer
optimization options that produce more efficient executable
code~\cite{opt-flags}.

These features can be seen as forms of automation, a central topic in
computer science aimed at improving developer productivity. A major
recent development is artificial intelligence, where part of the coding
process is delegated to systems that generate programs from a given
prompt~\cite{ia-prompt}.

Automation has also deeply influenced mathematics. The traditional
pen-and-paper approach to proving theorems has progressively been
supported, and sometimes replaced, by proof assistants. Based on the
Curry--Howard correspondence, a \underline{proof} of a \uuline{theorem}
can be interpreted as the implementation of a \underline{program} of a
given \uuline{type}.

In type theory~\cite{russell}, a proof assistant ensures that all cases
of a program are covered and satisfy a given specification. Formal
reasoning requires writing very detailed proof terms, with no ambiguity
or omitted steps. Even simple theorems can lead to verbose proofs, which
motivates the use of automation during the proving process.

One widely used proof assistant is \rocq~\cite{coqart}, formerly known as
\coq. It provides a mechanism called the
elaborator~\cite{elaboration}, which allows users to write terms close to
standard mathematical notation. The elaborator resolves ambiguities and
infers implicit information using inference rules stored in a knowledge
base.

In mathematics, it is common to reuse the same symbol in different
contexts. For example, the symbol $+$ may denote addition over natural
numbers in $1 + 2$, or vector addition in
$[\pi, e] + [\sqrt{2}, \frac{1}{3}]$. A reader can usually infer the
correct meaning from the context. In computer science, this idea is
called symbol overloading and is formalized using type
classes~\cite{wadler1989-tc}.

Since multiple implementations may exist for the same symbol, a type
class solver must determine the correct one. In \rocq~\cite{sozeau2008-tc},
this process can be seen as a form of logic programming, where goals are
resolved by searching for instances in a database, possibly with
backtracking.

The \rocq proof assistant can be extended using meta-languages. In this
setting, some tasks are delegated to an external language, which computes
results and returns them to \rocq. One such language is
\elpi~\cite{dunchev15}, a dialect of \lprolog~\cite{miller1988}, used via
the \rocqelpi plugin~\cite{tassi2018}. In meta-programming, the object
language is the one being studied (here \rocq), while the meta-language
(\elpi) is used to implement auxiliary mechanisms.

Since type-class resolution follows a \prolog-like
strategy~\cite[Chap.~9]{sld}, and \elpi uses a similar resolution
mechanism, it is natural to investigate whether the \elpi interpreter can
serve as a type-class solver for \rocq.

In this work, we study the integration of \rocq with an alternative
type-class solver implemented in \elpi. This requires translating type
classes and instances from \rocq into an \elpi database, which can be
seen as a compilation step. We show in
\cref{sec:simple-instance-compiler} that a basic compiler can be written
in only a few lines, while relying on the existing \elpi interpreter for
resolution. We then extend this translation to support more complex
instances and compare the resulting solver with the native one of
\rocq~\cref{sec:class-encoding,sec:instance-encoding,sec:exp-res}.

This approach has some limitations. A main difficulty comes from the
mismatch between the object language and the meta-language. Although
both support higher-order unification~\cite{miller1991-pf} and
$\beta\eta$-conversion, \rocq terms are represented in \elpi using
higher-order abstract syntax (HOAS)~\cite{pfenning1988}. In this
representation, $\lambda$-abstractions and applications are encoded with
rigid constructors, which introduces additional constraints during
unification.

As a consequence, some terms that unify in \rocq may fail to unify in
\elpi after translation. Therefore, directly reusing meta-level
unification is not sufficient.

To address this issue, we propose a compilation scheme
(\ref{chap:ho-for-free}) that preserves most of the structure of terms
while isolating problematic subterms. These are replaced only when
necessary and recorded as \emph{links}, representing delayed constraints.
They are checked during execution, allowing us to recover the intended
behavior without reimplementing unification.

This compilation with links is also motivated by efficiency. 
Since most of the term
structure is preserved, we can still exploit \elpi features such as
indexing and mode-directed unification. This is important in type-class
resolution, where the search space can be large.

Another contribution of this work is a determinacy analysis for \elpi
programs~\cref{chap:det-elpi}. Determinacy ensures that selected
predicates produce at most one solution and do not introduce unnecessary
choice points. This property helps control the behavior of logic
programs. In our setting, type classes correspond to predicates, and
instances to rules. If a class is declared deterministic, the analysis
ensures that all its instances satisfy this property.

We present an analysis based on inspecting clauses and tracking argument
modes. The algorithm supports most features of \elpi, including
higher-order predicates, dynamic clauses, and the cut operator. Handling
cut is important, as it can enforce determinism but interacts in subtle
ways with logical semantics.

We have started formalizing the expected properties of the static checker in the
\rocq proof assistant by encoding the \elpi
interpreter~\ref{chap:mechanization}. To support this development, we restrict
the model to a first-order fragment of the language, where terms do not contain
higher-order variables. In this setting, the absence of propositional variables
simplifies the formalization and allows us to produce a fully mechanized proof.

Although this model does not cover all higher-order features, it captures
the essential behavior of the system and provides a solid foundation for
the analysis.

\section{Contributions and structure of the thesis}

This thesis is organized as follows. We first present the
context of the work (\cref{chap:context}). In particular, we describe the
type-class resolution mechanism implemented in \rocq, together with its main
options. Then, we introduce the \elpi language and give a formal description of
its syntax and semantics. Finally, we present the \rocqelpi plugin, which enables
the interaction between \elpi and \rocq.

This thesis contains four main contributions, organized as follows:

\begin{description}
  \item[\Cref{chap:tc}] We study the implementation of a type-class solver
                        written in \elpi for \rocq. We present the core part of
                        the compiler that translates \rocq classes and
                        instances into an \elpi database. This database is then
                        used by the interpreter to search for inhabitants of
                        type classes. We also compare our solver with the one of
                        \rocq, focusing on performance, modes, and unification
                        issues.

  \item[\Cref{chap:ho-for-free}] We analyze unification problems arising from
                the higher-order abstract syntax used to represent \rocq terms
                in \elpi. In \rocq, terms that are equal up to
                $\beta\eta$-conversion can unify, while in \elpi such
                unification may fail, even if its algorithm supports these
                conversions. Based on our work~\cite{fissore2024}, we explain how
                to address this issue by delaying problematic unifications using
                a system of links.

  \item[\Cref{chap:det-elpi}] We present a static determinacy checker
               implemented in \elpi, available since version 3. This tool
               verifies that predicates declared as deterministic by the user
               effectively behave deterministically, meaning that they never
               create additional choice points. This result is based on our
               work~\cite{fissore2026}.

  \item[\Cref{chap:mechanization}] We mechanize the determinacy checker in the
               \rocq proof assistant. The formalization considers a restricted
               fragment of \elpi, namely its first-order part, where variables
               only represent data. Within this setting, we prove the main
               determinacy property: in a program that satisfies the checker,
               any call to a deterministic predicate produces at most one
               solution.
\end{description}
