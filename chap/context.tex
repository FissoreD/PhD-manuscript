\chapter{Context: languages and tools}
\label{chap:context}

At the core of this manuscript, there are two important pieces of software.
On the one hand, we
consider the \rocq proof assistant (formerly known as \coq); on the other hand,
we consider the logic programming language \elpi.

\rocq~\cite{coqart} is one of the main proof assistants. It is based on
type theory and allows formal reasoning about mathematical statements
and program specifications. In this setting, logical propositions are
interpreted as types, and proofs are interpreted as programs (or terms) of
these types. The underlying type theory of \rocq~\cite{cc-Coquand} ensures that the coherence
between a program and its type is checked, thus providing
guarantees of correctness.
Proof development in \rocq is carried out using a language of tactics, which
allows the user to construct proofs interactively.

On the other hand, \elpi~\cite{dunchev15} is a language from the field of logic
programming. In particular, it is a dialect of \lprolog~\cite{miller1988} which features
higher-order programming and unification, backtracking control
through the \cut operator, unification control through predicates modes. 
A plugin, called \rocqelpi~\cite{tassi2018}, allows one to extend \rocq
with new commands and tactics~\cite{krebbers2025,maas2024,tassi2023}.

In \rocqelpi:

\begin{itemize}
  \item \emph{Commands} extend the \rocq language by introducing new definitions or
  theorems that are automatically generated by \elpi programs. Examples of
  libraries that intensively use this feature include \derive~\cite{tassi2019},
  which derives equality theorems for inductive types, and \hb~\cite{hb}, which helps define
  complex algebraic structures while automatically generating associated theory.
  \hb supports the \mc~\cite{assia2022} ecosystem and
  mechanizations such as the Odd Order and Four Color theorems
  \cite{gonthier2013,gonthier2023}.

  \item \emph{Tactics} extend the proof system of \rocq{} by allowing additional
  forms of automation during proof development.
  As an example, the \trocq~\cite{enzo2023,enzo2024} library provides an \elpi-based tactic for
  automatic reasoning using proof transfer techniques. The \algtac~\cite{algtac}
  library instead offers \elpi-based tactics to reason about computational
  reflection for algebraic structures such as rings and lattices.
\end{itemize}

In the following sections, we introduce the key concepts that form the
foundation of \cref{chap:tc,chap:ho-for-free,chap:det-elpi,chap:mechanization}.
In particular, in \cref{sec:rocq-intro-lam-calc}, we briefly introduce
the notion of parametric polymorphism (also called system F~\cite{systemf}), 
so that we can provide a very simple
intuition about the role of the elaboration. Elaboration is treated in
\cref{sec:rocq-intro}, where we focus
about type-classes, a central component
of the elaborator for symbol overloading. In
\cref{sec:the-elpi-language}, we present the core aspects of the \elpi language,
including its syntax and semantics, which are necessary to understand its
execution model. Finally, in \cref{sec:coq-elpi}, we describe the main ideas
behind the \rocqelpi plugin.

\section{Parametric polymorphism: first steps into elaboration}
% TODO: vedere dove è usata
\label{sec:rocq-intro-lam-calc}

As anticipated, the \rocq language is based on type theory~\cite{coq-huet}.
At its core lies the pure $\lambda$-calculus, introduced by Church
in 1932~\cite{church}. This is a minimal language whose syntax is defined
by \emph{terms}:
%
$$t := x\ |\ t\ t\ |\ \lambda x.t$$

A term can be a variable $x$, an application $t\ t$, or an abstraction $\lambda
x.t$. A \emph{subterm} is any term occurring inside another term. In an
application, the first (sub)term is called the \emph{head} and the second the
\emph{argument}. An abstraction $\lambda x.t$ binds the variable $x$ in it's
abstraction scope $t$. A variable that is declared by a lambda abstraction and
whose occurrences lie within that abstraction's scope is called \emph{bound}
variable, whereas, a variable that occurs in an expression but is not bound by
any enclosing lambda abstraction is called \emph{free}.

For instance, the term $\lambda x.\lambda y.x$ (often called
\texttt{fst}) contains two bound variables, $x$ and $y$. The term
$\lambda y.x$ is a subterm of \texttt{fst}, and $x$ is free in it.

Evaluation of $\lambda$-terms is defined by \emph{reduction} rules. Two
terms are considered equivalent if they reduce to the same term. The
main rules used here are:
%
\begin{center}
  \begin{bprooftree}
    \AxiomC{$~$}
    \RightLabel{\rulelabel{$\beta$-rule}}
    \UnaryInfC{$(\lambda x.t_1)\ t_2 =_\beta t_1[x\backslash t_2]$}
  \end{bprooftree}
  \begin{bprooftree}
    \AxiomC{$x \text{ is not free in } t$}
    \RightLabel{\rulelabel{$\eta$-rule}}
    \UnaryInfC{$\lambda x.t\ x =_\eta t$}
  \end{bprooftree}
\end{center}

The $\beta$-rule describes function application: when the head is an
abstraction, the argument replaces all free occurrences of $x$ in $t_1$.
A term where this rule applies is called a $\beta$-redex. A term with no
such reductions is in $\beta$-normal form. For example,
$((\lambda x.\lambda y.x)\ 1)\ 2$ reduces first to
$(\lambda y.1)\ 2$, and then to $1$.

The $\eta$-rule expresses a form of extensionality: if $x$ does not occur
free in $t$, then $\lambda x.t\ x$ is equivalent to $t$. Terms where this
rule applies are called $\eta$-redexes.

In type theory, the pure $\lambda$-calculus is extended with typing
rules. These constrain how terms can be formed by assigning a
\emph{type} to each term. This extension is known as the
simply-typed $\lambda$-calculus~\cite{church-type}:
%
$$\tau := \alpha\ |\ \tau \to \tau$$

Types are either base types $\alpha$ or function types
$\tau \to \tau$, where the first component is the domain and the second
the codomain. Term abstractions are annotated accordingly:
%
$$t := x\ |\ t\ t\ |\ \lambda (x:\tau).t$$

A \emph{typing environment} $\Gamma$ maps variables to types. We write
$\Gamma + (x:\tau)$ for the extension of $\Gamma$ with a new binding.
The typing rules are:
%
\begin{center}
  \begin{bprooftree}
    \AxiomC{$x:\tau \in \Gamma$}
    \RightLabel{\rulelabel{$T_x$}}
    \UnaryInfC{$\Gamma \vdash x:\tau$}
  \end{bprooftree}
  \begin{bprooftree}
    \AxiomC{$\Gamma \vdash t_1:\tau_1 \to \tau_2 \quad
             \Gamma \vdash t_2:\tau_1$}
    \RightLabel{\rulelabel{$T_@$}}
    \UnaryInfC{$\Gamma \vdash t_1\ t_2:\tau_2$}
  \end{bprooftree}
  \begin{bprooftree}
    \AxiomC{$\Gamma + (x:\tau) \vdash t:\tau'$}
    \RightLabel{\rulelabel{$T_\lambda$}}
    \UnaryInfC{$\Gamma \vdash \lambda (x:\tau).t:\tau \to \tau'$}
  \end{bprooftree}
\end{center}

The judgment $\Gamma \vdash t:\tau$ means that $t$ has type $\tau$ under
$\Gamma$. If such a derivation exists, the term is said to
\emph{typecheck}. The algorithm implementing these rules is called the
\emph{typechecker}.

However, the simply-typed $\lambda$-calculus can be too restrictive for
expressing more abstract constructions. Several extensions exist, as
illustrated by the Barendregt cube~\cite{cube}. One important extension
is the polymorphic $\lambda$-calculus (System~F)~\cite{systemf}, where
terms may depend on types.

Consider the identity function $\lambda x.x$. In the simply-typed
setting, it must be assigned a fixed type, for example
$\lambda (x:\texttt{bool}).x$. A separate definition would be needed for
each type, such as $\texttt{nat}$. This duplication can be avoided in the
polymorphic calculus.

Polymorphism allows quantification over types. The syntax is extended as
follows:
%
$$t := \dots\ |\ \tau \qquad
  \tau := \dots\ |\ \forall (x:T).\tau$$

The constructor $\forall$ expresses that a type may depend on another
type. $\forall (x : T), \tau$ is a generalization of $T \to \tau$,
in particular the two representation are equivalent if $x$ does not appear
as a free variable in $T$.

At the term level, we write $\lambda (x:T).t$ to abstract over a
type. With this, the polymorphic identity function can be written as
$\lambda (x:T).\lambda (y:x).y$.

The typing system is extended with:
%
\begin{center}
  \begin{bprooftree}
    \AxiomC{$\Gamma + (x:T) \vdash t:\tau$}
    \RightLabel{\rulelabel{$T_\forall$}}
    \UnaryInfC{$\Gamma \vdash \lambda (x:T).t:\forall (x:T).\tau$}
  \end{bprooftree}
\end{center}

Using this definition, the identity function can be applied as
$(\lambda (x:T).\lambda (y:x).y)\ \texttt{nat}\ 3$, which reduces to $3$
by successive $\beta$-steps.

In practice, explicitly passing types can be inconvenient. If the typing
environment already assigns $3$ the type \texttt{nat}, the system can
infer that the first argument should be \texttt{nat}. One may then write
$(\lambda (x:T).\lambda (y:x).y)\ \_\ 3$, where the underscore denotes
missing information to be inferred.

Such placeholders, often called \emph{holes}, correspond to existential
variables that the typechecker must instantiate. In systems like \rocq,
these arguments can often be omitted entirely when they are declared
implicit.

This illustrates how type inference improves usability, allowing the
user to leave parts of a term unspecified while the system reconstructs
them automatically.

\begin{figure}

The possibility of writing terms with holes, as indicated in the previous section,
is just one of the aspects that are covered by the elaborator~\cite{elaboration}.
In this section, we study more deeply this technical component that mediates the
interaction between the user and the \rocq system. This component is present in all
proof assistants. Its role is to accept expressions that may be
incomplete or ambiguous, and to reconstruct the missing information
automatically, simplifying therefore the exchanges with the user.

Figure~\ref{fig:elaboration}, adapted from~\cite{elaboration}, outlines
the main steps of this process. Starting from a raw input string, the
system first parses it into a \rocq term, which can still contain
implicit parts. This term is then elaborated into a fully explicit one.
The resulting term is passed to the kernel, which typechecks it. If the
check succeeds, the term is a valid inhabitant of its type, that is, a
proof of the corresponding statement.

Elaboration performs several tasks, including notation resolution,
type inference, resolution of overloaded
symbols\dots

\emph{Notation resolution} removes syntactic ambiguity by replacing
user-defined notations with their underlying constructors in the
abstract syntax tree. The obtained term is unambiguous, although it may
still contain holes. For example, the term \cI{[1, 0]} uses common
mathematical notation for lists and natural numbers. After this step,
it becomes:
%
\begin{center}
  \cI{@cons _ (S O) (@cons _ O (@nil _))}
\end{center}

\noindent
Here, \cI{cons} and \cI{nil} are constructors for lists, representing
respectively insertion at the head and the empty list. The symbols
\cI{S} and \cI{O} denote the successor function and the constant $0$.

\emph{Type inference} fills in the missing information using the typing
environment. It relies on a set of rules that propagate type
constraints through the term.

As an example, consider the following typing environment:
%
\begin{center}
\begin{tabular}{ccc}
  Symbol & & Type \\
  \hline
  \cI{cons} & : & \cI{~$\forall$~ T, T ~$\to$~ list T ~$\to$~ list T} \\
  \cI{nil}  & : & \cI{~$\forall$~ T, list T} \\
  \cI{S}    & : & \cI{nat ~$\to$~ nat} \\
  \cI{O}    & : & \cI{nat}
\end{tabular}
\end{center}

Running the typechecker on the previous term produces the fully
elaborated version:
%
\begin{center}
\cI{@cons nat (S O) (@cons nat O (@nil nat))}
\end{center}

% types. If a function of type $t_1 \to t_2$ is declared as a coercion,
% it can be inserted automatically when a term of type $t_1$ is used
% where a $t_2$ is expected. For example, assume that
% \cI{nat_to_bool} maps \cI{0} to \cI{false} and any other natural

Finally, elaboration also supports overloading, allowing a symbol to be
used with different types. Since ad-hoc polymorphism is important for
this work, we study this mechanism in more detail in the next
subsection.

\subsection{Ad-hoc polymorphism}
\label{sec:ad-hoc-poly}

Polymorphism is a central feature of functional programming languages. In his
lecture notes, Strachey~\cite{polymorphism} distinguishes two main forms:
parametric polymorphism and ad-hoc polymorphism. Parametric polymorphic
functions are \emph{uniform}, meaning that their behavior does not depend on the
specific type at which they are instantiated. For example, the function
\texttt{length}, which computes the length of a list, has type \cI{list A
~$\to$~ int}. When applied to either \cI{[1,0]} or \cI{["foo","bar"]}, it
returns $2$. The same implementation is reused for every instantiation
of~\cI{A}.

Although parametric polymorphism is widely used, it is not well suited to model
overloading as it appears in mathematics. In mathematical notation, a symbol
such as $+$ has a stable meaning and no ambiguity for the reader. For instance,
in $1 + 2$ it denotes addition on integers, while in $\pig + e$ it denotes
addition on real numbers. The same symbol is reused for operations that share
common algebraic properties.

In contrast, parametric polymorphism does not support multiple
type-dependent implementations of the same symbol. This limitation appears in
languages such as \ocaml, where integer and floating-point additions are
represented by different operators, $+$ and $+.$. One writes $1 + 2$ for integers
and $\pig +\!.\ e$ for floating-point numbers. In general, a new symbol must be
introduced for each type implementing the same mathematical operation.

To address this issue, Wadler and Blott introduced type classes
in~1989~\cite{wadler1989-tc}. The idea was later implemented in
Haskell~\cite{wadler1996-hs}, where it became a core feature. Similar mechanisms
were then adopted in other languages such as \cpp~\cite{cpp-tc},
\java~\cite{java-tc}, and proof assistants like \rocq~\cite{sozeau2008-tc} and
\lean~\cite{lean-tc}.

\paragraphTwo{Symbol overloading}
Type classes provide a principled form of ad-hoc polymorphism. They allow a
single symbol to be associated with different implementations while preserving
static type safety. A type class is parameterized by one or more types~$t$ and
declares a set of functions, called methods, whose types may depend on~$t$. An
instance of a type class gives a concrete implementation for a specific type.

Unlike parametric polymorphism, where it exists only one function implementing
each symbol, type classes
rely on instance resolution. Instances are stored in a database. When a method
is used, the elaborator selects the appropriate implementation by searching for
an instance matching the required type.

\paragraphTwo{Instance search}

Type classes are widely used in several major \rocq{} libraries, including
\tlc~\cite{tlc}, \stdpp~\cite{stdpp}, and \iris~\cite{iris-junk}. The
type-class solver automatically infers instances by searching a database
of declared instances. This database is organized as an ordered list.

The position of an instance in this list is determined by its priority.
A priority can be assigned explicitly at the end of the declaration
using \cI{| N}, where \cI{N} is an integer. When no priority is
specified, \rocq{} computes one automatically by assigning a weight of
$1$ to each premise that is itself a type-class constraint.

Instances with lower priorities are placed earlier in the list. When two instances
have the same priority, their relative order is determined by their
declaration order in the source code: the instance declared first is
placed before the other.

The search procedure is similar to a depth-first search and closely
resembles the \prolog{} SLD-resolution
algorithm~\cite{sld}. To solve a goal, the type-class solver traverses
the instance database in order and attempts to unify the conclusion of
each instance with the current goal.

When unification succeeds, the premises of the selected instance become
new subgoals. These subgoals are solved recursively using the same
procedure. If all premises can be resolved, the instance provides a
solution to the original goal. Otherwise, the solver backtracks and
continues the search with the next matching instance.

Because instances are explored according to their position in the
database, the ordering of the database can have a significant impact on
the search process. In particular, it may affect both the performance of
instance resolution and its termination behavior.

As an example, consider the instances defined for the type class
\cI{Add}, ordered as follows: \cI{addNat}, \cI{addR}, and
\cI{addProd}. To solve the goal \cI{Add (nat * R)}, the solver examines
the instances in that order. The first two instances are discarded
because their conclusions do not match the goal. The instance
\cI{addProd} matches and generates the subgoals \cI{Add nat} and
\cI{Add R}. These subgoals are solved by \cI{addNat} and \cI{addR},
respectively, yielding the solution
\eI{addProd nat R addNat addR}.

% The ordering of the database is also important for termination. 
Consider now
the same set of instances, but assume that \cI{addProd} has the highest
priority. When solving the goal \cI{Add ?X}, where \cI{?X} is an
existential variable, \cI{addProd} matches by instantiating \cI{?X} as
\cI{?X1 * ?X2}. This produces the subgoal \cI{Add ?X1}. Since
\cI{addProd} is considered first, it matches again and instantiates
\cI{?X1} as \cI{?X3 * ?X4}, generating a new subgoal \cI{Add ?X3}. The
same situation repeats indefinitely, leading to a non-terminating search.

To control the search, several mechanisms are available. A common one is the use
of \emph{modes}, which restrict the shape of class arguments during resolution.
In \rocq{}, modes are lists of symbols \texttt{+}, \texttt{!}, and \texttt{-},
indicating respectively ground terms, terms with rigid head symbol, and
arguments with no constraints on their shape.

A type class may have multiple modes. During search, these modes are checked
dynamically, and the solver proceeds only if at least one mode matches the
current goal.

Another important aspect is that multiple instances may match the same goal,
which requires backtracking. Some libraries, such as \stdpp{}, exploit this
behavior to emulate logic programming. For example, the type class
\cI{SetUnfold} is used to rewrite set expressions into logical statements. An
inclusion $X \subseteq Y$ can be transformed into a formula of the form
$\forall x, P\ x \to Q\ x$, under suitable assumptions on $X$ and $Y$. When no
specific rule applies, the default instance
\cI{set_unfold_default P : SetUnfold P P} leaves the goal unchanged.
This default instance acts as a catch-all rule, since it applies to any goal.

While backtracking is useful in such patterns, it can introduce ambiguities and
lead to behavior that is difficult to predict in practice.

In \rocq{}, backtracking for a given type class can be disabled using the flag
\texttt{Typeclasses Unique Instances}. When enabled, once a solution is found,
the solver does not backtrack, assuming that the solution is canonical.

\section{The \elpi language}
\label{sec:the-elpi-language}

\elpi~\cite{dunchev15} stands for \emph{Embeddable Lambda-Prolog Interpreter}.
It is a dialect of \lprolog~\cite{miller1991-pf,miller2012} that supports
higher-order logic programming and integrates a goal suspension mechanism
based on CHR (Constraint Handling Rules~\cite{chr,chr-elpi}).

The term ``embeddable'' highlights that \elpi\ is designed to be used as an
extension language. Its main application is the \rocqelpi plugin~(see
\cref{sec:coq-elpi}), which enables communication between \elpi\ as the
meta-language and the \rocq\ proof assistant as the object language.

A comprehensive presentation of the \elpi\ language and its applications can
be found in Tassi's ``habilitation à diriger les recherches''~\cite{hdr}.
Here we briefly introduce the aspects of \elpi\ that are relevant to this
document.

Sections~\cref{sec:elpi-syntax,sec:elpi-semantics} present the syntax and the
operational semantics of \elpi. A first formal description appeared in the
appendix of our contribution~\cite{fissore2026}, and was later revised
in~\cite{hdr}. In this thesis, we follow a slightly different presentation. The
goal is to be consistent with the conventions used in
\cref{chap:det-elpi,chap:mechanization}. We leave aside the syntax and semantics
of the \chr\ component of \elpi. This part is discussed only informally in
\cref{sec:chr}.

In \cref{sec:elpi-execution-example,sec:example-ho-dyn-programs}, we first
present an example of execution, highlighting the role of the \cut
operator in the \elpi language.

Finally, in \cref{sec:chr,sec:elpi-rule-names}, we outline two features of the
\elpi language: the constraint handling rules system, and rule naming

\subsection{Abstract syntax of \elpi (without \chr)}
\label{sec:elpi-syntax}

\begin{figure}
  \centering
  \includegraphics{img/syntax.pdf}
  \caption{Abstract syntax of \elpi\ programs}
  \label{fig:elpi-syntax}
\end{figure}

\paragraphTwo{Syntax of \elpi\ programs}

\Cref{fig:elpi-syntax} presents the abstract syntax of \elpi\ programs.

The basic syntactic categories are data~\DATA,
predicates~\PRED, unification variables~\UVAR, and
nominal variables~\NVAR. Nominal variables represent binders
introduced either by $\lambda$-abstractions or by $\pi$-quantification.

A term~\TERM\ is either a basic construct or an application. More precisely,
terms are formed by applying a term to a $\lambda$-term~\LTERM.
Lambda terms introduce abstractions; in the concrete \elpi\ syntax, an
abstraction is written \eI{x\ t}. Function application follows a curried
style. In contrast with \prolog, arguments are not passed within
parentheses, which allows partial application. We write, for example,
\eI{p 1 X}, instead of \eI{p(1, X)}.

An formula~\ATOM\ represents an executable unit. It can be:
\begin{enumerate}
  \item the cut operator (\eI{!} in the concrete syntax),
  \item a predicate call (called atom in the literature),
  \item a $\pi$-quantification, written \eI{pi x\ t} in the concrete syntax,
        which introduces a fresh nominal variable \eI{x} visible in \eI{t}, or
  \item the dynamic insertion of a rule, written \eI{r => t}, which
        makes the rule \eI{r} locally available in the scope of \eI{t}.
\end{enumerate}

A rule\ consists of a head and a (possibly empty) body, which is a
list of atoms. The atoms in the body are called the \emph{premises} of the rule.

For simplicity, we omit constraints from the syntax, since they
do not play an immediate role in the presentation. They are briefly
described in \cref{sec:chr}.

% The syntax we propose allows writing hereditary Harrop formulas. 
In this abstract syntax, logical connectives such as negation and disjunction,
which are usually encoded as native symbols of a logic programming-language,
can be treated as first-class objects and implemented directly as \elpi rules.

\paragraphTwo{Syntax of \elpi\ types}

In \elpi, users can define the algebraic data types required by their
development as well as the signatures of predicates. A new algebraic data type
is declared with the \kind\ keyword, while constructors of that type are
introduced using the \type\ keyword. A type is ether a
base type, a variable, or the application of a type to another in the
case of parametric types. The arrow symbol is used to type function space and in
\elpi it takes an optional mode information. The mode, \Einput or
\Eoutput, tells the runtime which unification algorithm to use when unifying the
arguments of two terms, we dealy this discussion in the next section,
in particular at \cref{def:unify,def:matching}. By
default, no mode information is compiled to \Eoutput.

For example, the constructors for natural numbers and polymorphic lists,
introduced in \cref{sec:rocq-intro}, can be defined in \elpi as follows:

The type \eI{nat} contains the constant \eI{z} representing zero and the
constructor \eI{s} representing the successor of another natural number.
A \eI{list} is either empty \eI{nil} or the
constructor \eI{cons} that combines a head element with a tail list.
Lists are polymorphic: the type of the head element must coincide with
the type of the elements stored in the tail.

A predicate is a symbol whose type ends in \eI{prop}. The type \eI{o}
is an equivalent notation following the convention of~\cite{miller2012}.
\elpi\ provides a dedicated syntax for declaring predicates, which also
allows the programmer to specify the modes of their arguments.

The declaration \eI{pred p t1 ~$\to$~ t2}, where \eI{t1} and \eI{t2} are
types, is equivalent to \eI{type p t1 ~$\to$~ t2 ~$\to$~ prop}. However, it also
defines the modes of the two arguments.

Arguments placed before the arrow symbol in a \eI{pred} declaration
are considered inputs, while those
after the arrow are outputs.

\subsection{Operational semantics of \elpi\ (without \chr)}
\label{sec:elpi-semantics}

In this section, we use the notation $\vecL{x}$ to denote an ordered list
containing $x$ elements. The binary operator $+$, when applied to partial
mappings, denotes their disjoint union.

% Finally, the notation \eI{set ~S~} denotes a set, that is, an unordered
% collection of elements of type $S$ without duplicates.

A substitution $\sigma$ of type $\Sigma$ is a partial mapping from
unification variables \UVAR\ to terms \TERM. The empty substitution is denoted by
$\EmptySubst$. The notation $\sigma = \{ X \mapsto t\}$ represents a substitution
$\sigma$ where the variable $X$ is assigned to the term $t$.
The domain $\dom\ \sigma$ of a substitution $\sigma$ is the set
of variables that are assigned in $\sigma$.

\begin{definition}[Substitution extension]
  A substitution $\sigma'$ is an extension of $\sigma$, noted $\sigma \subseteq \sigma'$,
  iff
  $$\exists \sigma'',\ \sigma + \sigma'' = \sigma' \ \land\
  \dom\ \sigma'' \cap \dom\ \sigma = \varnothing $$
  \label{def:sub-extension}
\end{definition}

\vspace{-3em}

\begin{definition}[Substitution application (or term dereferencing)]
  A substitution $\sigma$ applied to a term $t$, noted $\sigma t$, is the operation
  allowing to recursively replace the variables in $t$ by their assignement in 
  $\sigma$.
  \label{def:deref}
\end{definition}

% \begin{definition}[Typing environment]
%   A typing environment is a partial mapping from symbol names to their type.
% \end{definition}

We use the notation $\env$ to represent a typing environment, it
maps symbol names to their type.

A program $\prog$ of type $\PROG$ is made by a triple
$(\vecL{\RULE}, \vecL{\NVAR}, \env)$

The first element represent the ordered list of rules characterising the
program, we use the notation $\prog.\cI{index}$ to get this element from \prog. 
The second element of the triple contains the set of nominal
variables that have already been introduced, we use the notation
$\prog.\cI{nvar}$ to get this element for the program \prog. Finally, the
last element of the triple contain the typing environment, we use the
notation $\prog.\cI{sig}$ to get this element.

We write $x \# \prog$ to denote that the nominal variable $x$ is fresh with
respect to $\prog.\txtI{nvar}$, i.e. $x \notin \prog.\txtI{nvar}$. The notation $x +_\forall \prog$ denotes the
program obtained by adding $x$ to $\prog.\txtI{nvar}$. Similarly,
$h +_\Rightarrow \prog$ denotes the program obtained by prepending the rule $h$
to $\prog.\txtI{index}$.

A goal $g$ of type
$\g = \PROG \times \ATOM \times \vecL{\alt}$
is a triple consisting of a program, an atom, and a list of
\emph{cut-to alternatives}. An alternative $a$ of type $\alt$ is a pair
$\Sigma \times \vecL{\g}$ composed of a substitution and a list of goals.

\begin{figure}[t]
  \centering
  \includegraphics{img/det_check/dynamic.pdf}
  \caption{Operational semantics of \elpi}
  \label{fig:elpi-semantics}
\end{figure}

\Cref{fig:elpi-semantics} presents the derivation rules of the \elpi\
interpreter, defined in terms of the function
\[
  \runE : \vecL{\alt} \to \mathrm{option}\ (\Sigma, \vecL{\alt}).
\]

This semantics is inspired by
\cite[Sec.~4.3]{debray1988} and \cite{hdr}. Execution is modeled as the
evaluation of a stack of alternatives $\alt$. The interpreter processes
alternatives sequentially. The evaluation of the alternative list either succeeds,
producing a substitution and a new list of alternatives, or fails, returning
None.

In \cref{fig:elpi-semantics}, rule \runE[\top] captures success: if the first
alternative contains an empty list of goals, the interpreter returns its
associated substitution together with the remaining alternatives. Conversely,
rule \runE[\bot] states that evaluation fails when the list of alternatives is
empty.

The remaining rules of \runE, namely \runE[!], \runE[\backchain],
\runE[\forall], and \runE[\Rightarrow], apply when the first alternative
contains a non-empty list of goals. Such alternative list has the form
$\ConsHd{\ConsHd{q}\ConsTl{g}}{\ConsTl{a}}$, where $q$ is the current goal atom
(or query). The derivation rule to use depends on the syntactic form of $q$, which
can be one of the four forms of \ATOM\ listed in \cref{fig:elpi-syntax}.

If $q$ is a \cut, rule \runE[!] discards the current alternatives $a$ and
replaces them with the cut-to alternatives stored in $q$. Evaluation then
continues with the remaining goals $g$.

If $q$ is a $\pi$-quantification $\pi x.\,t$, the interpreter generates a fresh
nominal variable $y$ not occurring in $\prog$, replaces all free occurrences of
$x$ in $t$ with $y$, and continues evaluation with the resulting atom.

If $q$ corresponds to the dynamic insertion of a rule $h$, evaluation continues
with atom $t$ in the program extended with the local rule $h$. Intuitively $h
\Rightarrow t$ amounts to a well-bracketed use of \prolog's \texttt{assert/1} and
\texttt{retract/1}.

Finally, if $q$ is a predicate call, the interpreter performs \emph{backchaining} over
the rules stored in $\prog.\txtI{index}$. Backchaining retrieves the rules that
can be used on the query $q$. In standard \prolog this is done by selecting
rules whose head unifies with $q$. In \elpi the process depends on predicate
modes, which determine if a argument should be \emph{matched} or \emph{unified}.

\elpi provides two procedures, \unify\ and \matching. Both have type
\[
\TERM \to \TERM \to \Sigma \to \mathrm{option}\ \Sigma,
\]
taking two terms and an initial substitution $\sigma$. They either fail
(returning None) or succeed with an updated substitution $\sigma'$ that is
an extension of $\sigma$.

\begin{definition}[Pattern fragment]
  A $\lambda$-term belongs to Miller's pattern frangment~\cite{miller1991-pf} if in every subterm of
  the form $F\ t_1\ t_2 \dots t_n$, where $F$ is a higher-order unification
  variable, each term $t_i$ is a bound variable distinct from any $t_j$ (with $i
  \neq j$).
  \label{def:pattern-fragment}
\end{definition}

The procedure \unify\ implements higher-order unification restricted to the
pattern fragment, and is used for arguments in \Eoutput\ position. The
procedure \matching, inspired by \bprolog's ``matching clauses''
\cite{zhou2012}, is used for arguments in \Einput\ position. It also performs
higher-order unification restricted to the pattern fragment.

\begin{definition}[\unify]\label{def:unify}
Two terms $q$ and $u$ \emph{unify} under a substitution $\sigma$ if there
exists a substitution $\sigma'$ extending $\sigma$ such that
$\sigma' q = \sigma' u$, and $\sigma'$ is a most general unifier for the two terms.
\end{definition}

\begin{definition}[\matching]\label{def:matching}
A query $q$ \emph{matches} a pattern $u$ under a substitution $\sigma$ if there
exists a substitution $\sigma'$ extending $\sigma$ such that
$\sigma' u = \sigma q$, where $\sigma'$ assigns at most the free variables
occurring in $u$.
\end{definition}

Backchaining is defined by the function \backchain:

\begin{definition}[Backchain, $\backchain : \PROG \times \vecL{\VAR} \times \TERM \times \Sigma \to
\vecL{\Sigma \times \vecL{\ATOM}}$]
\begin{multline*}
\backchain(\prog, V, q, \sigma) =
\bigg[
(\sigma', b)\ \mathrm{if}\
 \getmode(\prog.\mathrm{sig}, q) = \mathrm{Some}\ m \land \select(m, q, h, \sigma) = \mathrm{Some}\ \sigma'
\ \bigg|\ \\
(\clauseCmd{h}{}{b}) \in \text{fresh}(V, \prog.\mathrm{index})
\bigg].
\end{multline*}
\end{definition}

Intuitively, \backchain selects the rules from the program 
that can be applied to the current
query $q$ under a substitution $\sigma$. The variables occurring in the program
rules are assumed to be disjoint from those in the current execution state. To
guarantee this, the program is refreshed using the function \texttt{fresh},
which renames its variables with respect to the set $V$.

For each applicable rule, \backchain returns the substitution obtained by
matching/unifying the rule head with $q$, together with the corresponding
rule body.

The definition relies on two auxiliary functions:
\begin{align*}
  \getmode &: \env \to \TERM \to \mathrm{option}\ \TYPE \\
  \select  &: \TYPE \to \TERM \to \TERM \to
              \Sigma \to \mathrm{option}\ \Sigma
\end{align*}

The function \getmode retrieves the signature of the predicate occurring in a
term. It returns the signature if the predicate is present in the environment,
and None otherwise.

The function \select tests whether the query $q$ matches/unifies the head $h$ of a rule
under an initial substitution $\sigma$. The predicate signature determines the
mode of each argument, which in turn selects the appropriate procedure:
\matching\ for \Einput\ arguments and \unify\ for \Eoutput\ arguments.
If all arguments satisfy the unification condition, \select returns the resulting substitution
$\sigma'$; otherwise it returns None.

\begin{definition}[\elpi backchain, $\backchainE :
\PROG \times \TERM \times \Sigma \times \vecL{\alt} \times \vecL{\g}
\to \vecL{\alt}$]

\[
\backchainE(\prog, t, \sigma, a, g) =
\bigg[
\sigma',
(
  [(\prog, q, a) \mid q \in b] \atsign g
)
\ \bigg|\ 
(\sigma', b) \in \backchain(\prog, F_v(t) \cup F_v(g::a) \cup F_v(\sigma), t, \sigma)
\bigg].
\]
\end{definition}

The function \backchainE, used by rule \runE[\backchain] in
\cref{fig:elpi-semantics}, builds a new list of alternatives from the result of
\backchain ($F_v$ is the function retrieving the set of free variables in 
the term $t$, we lift the definition over list of terms, and substitution%
\footnote{$F_v(\sigma)$ is made by the domain of $\sigma$ and the free variables
in all terms appearing in the codomain in $\sigma$}).
For each filtered rule, the atoms in the rule body become new
goals whose cut-to alternatives are $a$ and whose continuation is $g$. The
substitution associated with each alternative is the one returned by
\backchain.

\paragraphTwo{Comparison with Tassi's presentation}

In the previous subsections, we presented the \elpi language, including its
syntax and semantics. This formalization has been
developed in collaboration with Enrico Tassi. A comprehensive description of
\elpi can be found in his work~\cite{hdr}.

We highlight here the main differences between his presentation and the one
adopted in this section. First, in the syntax, we use binary application for
terms, instead of the $n$-ary application used in \cite{hdr}. Second, in the
semantics, programs carry not only the list of rules and nominal variables, but
also the signature of declared predicates. We also omit the formal treatment of
constraints, as it is not required for the remainder of this manuscript; a brief
informal explanation is sufficient for our purposes (see~\cref{sec:chr}).

Another difference concerns the definition of \runE. In Tassi's presentation,
\runE, called \texttt{run}, is defined as a procedure that takes two arguments:
the current alternative and the list of future alternatives. This choice
reflects closely the concrete implementation in \elpi, where execution starts
from a query, and a query is represented as an alternative. In contrast, we
define \runE with a single input, namely a list of alternatives, from which the
first element is extracted by pattern matching when needed. This design choice
is motivated by the mechanization in \rocq (see \cref{chap:mechanization}),
where we need to prove the equivalence between two semantics and to represent
the execution of \runE on an empty list of goals.
Despite these differences, as the theorem below claims, the two semantics are
equivalent when executed on non-empty lists of alternatives, modulo the
absence of constraints, which is forced to the empty list in the \texttt{run}
semantic (this is performed by the \txtI{map}ping of one list to the other
and putting the empty set, i.e. $\emptyset$, of constraints).

\subsection{Example of program execution in \elpi with \cut}
\label{sec:elpi-execution-example}

We believe that the main difficulty in the semantics presented in the previous
section lies in the treatment of choice points and their interaction with the
\cut operator.

Several variants of the cut operator exist in the literature. The variant we
consider, used in \elpi, is the so-called \emph{hard cut} (see, for example, the
documentation of \sprolog~\cite{swi-prolog-cut}). When the \cI{backchain}
function returns a non-empty list of alternatives, the first alternative is
executed immediately, while the remaining ones are stored as choice points.

Within a selected alternative, premises are evaluated from left to right, each
atom being executed in sequence. When a \cut is encountered, it removes two
kinds of choice points: (i) those generated by \cI{backchain} for the current
predicate call, and (ii) those created during the evaluation of premises to the
left of the \cut.

clarity, \cref{ex-elpi} illustrates its execution, explicitly showing the
pointers to the cut-to alternatives. We only highlight the alternatives targeted
by the \cut operator, since the alternatives stored for predicate calls do not
play a role in the semantics discussed here.

% discards the second and third elements in the stack. Backtracking is
% performed by simply consuming the first alternative from the stack, as shown
% in \cref{ex-elpi3}.

Consider the program in \cref{fig:progx} and the query
$\eI{g 0 R}$.
Both rules for \eI{g} apply to this query. Backchaining therefore returns the
following two alternatives:
\[
  [(\sigma_1, [\eI{r A B, f B C, !}]),\; (\sigma_2, [\eI{f D E, f E F}])]
\]
with
$
  \sigma_1 \coloneq \{\eI{A} \mapsto \eI{0}, \eI{C} \mapsto \eI{R}\}
$
and
$
  \sigma_2 \coloneq \{\eI{D} \mapsto \eI{0}, \eI{F} \mapsto \eI{R}\}
$.
For simplicity, we choose an example where variable refreshing plays no role/
% , so we do not discuss the set \FV{} any further.

Execution continues with the first premise of the first alternative, namely
\eI{r A B} under $\sigma_1$, i.e. \eI{r 0 B}. The remaining alternatives are
stored as choice points.
Backchaining \eI{r 0 B} returns
$
  [(\sigma_3, []), (\sigma_4, []), (\sigma_5, [\eI{!}])]
$
where
$
  \sigma_3 \coloneq \sigma_1 + \{\eI{B} \mapsto \eI{0}\}
$
;
$
  \sigma_4 \coloneq \sigma_1 + \{\eI{B} \mapsto \eI{1}\}
$
and
$
  \sigma_5 \coloneq \sigma_1 + \{\eI{B} \mapsto \eI{2}\}
$.

The next step of interpretation continues with \eI{f B C} under $\sigma_3$,
that is, \eI{f 0 R}, and leaves $[(\sigma_4, []), (\sigma_5, [\eI{!}])]$ as new choice points.
This time, backchaining fails (no rule for \eI{f} matches input $0$). We
therefore backtrack to the most recently introduced choice point and retry
\eI{f B C} under $\sigma_4$, i.e. \eI{f 1 R}. This succeeds with
$\sigma_6 \coloneq \sigma_4 + \{\eI{R} \mapsto \eI{2}\}$.

We now reach the cut. At this point there are still two unexplored
alternatives: one from the third rule for \eI{r} and one from the second rule
for \eI{g} (respectively, $\sigma_5$ and $\sigma_2$). Both are discarded,
because they were created when, or after, the first rule for \eI{g} was
selected. In contrast, a cut does not discard choice points created earlier;
in this example, there are none.
The final solution is:
$
  \{\eI{A} \mapsto \eI{0}, \eI{B} \mapsto \eI{1}, \eI{C} \mapsto \eI{R},
  \eI{R} \mapsto \eI{2}\}
$.

\subsection{Higher-order, dynamic and meta- programs in \elpi}
\label{sec:example-ho-dyn-programs}

One of the main features of \elpi is the possibility to work with
higher-order and dynamic programs. In this section, we present some simple
examples illustrating these two aspects. These examples will be used later as a
reference when discussing determinacy checking in \elpi (see
\cref{chap:det-elpi}).

\paragraphTwo{Higher-order programming} A well-known higher-order predicate in \elpi is \eI{map}, whose
implementation is shown below.
%
\begin{elpicode}
pred map (pred A ~$\to$~ B), list A ~$\to$~ list B.
map _ [] [].
map F [X|XS] [Y|YS] :- F X Y, map F XS YS.
\end{elpicode}

This is a \prolog-style definition. The predicate takes a
higher-order argument \eI{F}, which is applied to each element of the input
list. In the base case, the empty list is mapped to the empty list. In the
recursive case, the head \eI{X} is transformed into \eI{Y} using \eI{F}, and the
predicate is then applied recursively to the tail \eI{XS}.

Another common higher-order construct in \elpi is the predicate
\eI{once}, defined as follows.
%
\begin{elpicode}
pred once (pred) ~$\to$~.
once P :- P, !.
\end{elpicode}

The predicate \eI{once} acts as a wrapper around a goal. It executes the goal
\eI{P} and then removes all remaining choice points. As a consequence, only the
first solution is returned. For example, the query \eI{once (r 0 X)}, where
\eI{r} is defined in \cref{fig:progx}, produces a single result, binding
\eI{X} to \eI{0}.

The behavior of the \cut operator depends on where it is placed. The
following snippets illustrate similar programs with different uses of \cut.

\paragraphTwo{Dynamic clauses}

The domain where \elpi really shines is the manipulation of higher-order data
represented via the so-called higher-order abstract syntax (or $\lambda$-tree syntax)~\cite{miller2018}
also called HOAS~\cite{pfenning1988}.
Such data is pervasive in interactive provers
such as \rocq. In the paradigmatic example below \eI{tm} is
the data type for $\lambda$-terms.
%
\begin{elpicode}
kind tm type.                      % datatype of $\lambda$-terms in HOAS form
type app tm ~$\to$~ tm ~$\to$~ tm.            %  - binary application
type lam (tm ~$\to$~ tm) ~$\to$~ tm.          %  - $\lambda$-abstraction
\end{elpicode}
%
In the HOAS encoding of syntax with binders we do not find a node for variables:
we re-use the notion of bound variable of the programming language to encode the
one of the syntax tree. At the level of types we see that the \eI{lam}
node carries an \elpi function over terms. It is by applying this function
that one can recover the body of the $\lambda$-abstraction.
A simple program manipulating higher-order data is the function
performing a deep copy of a term:
%
\begin{elpicode}
pred copy tm ~$\to$~ tm.
copy (app A B) (app C D) :- copy A C, copy B D.
copy (lam F)   (lam G)   :- pi x\ copy x x => copy (F x) (G x).
\end{elpicode}
%
The copy of an application is built from the copies of the subterms. What is
more interesting is how one copies under a binder.
The ``\eI{pi x\ copy x x =>}'' instruction
explains how to copy the new constant \eI{x}.
Finally the code performs a recursive call over \eI{F x}:
by applying the \elpi function \eI{F} to
the fresh symbol \eI{x} one obtains the body of the $\lambda$-abstraction
where the bound variable is replaced
by the new symbol \eI{x}.

In \elpi, all predicates are \emph{dynamic}, or open, hence
the code of \eI{copy} can be
augmented with rules at runtime. 
% \todo{remark app, lam and each x are different}
% \todo{we want copy to be a understood as a function}
% Even so \eI{copy} is a function because no
% two rules can apply to the same input: \eI{lam} and \eI{app}
% are different constants, and each constant \eI{x} generated dynamically is
% guaranteed to be fresh by the \eI{pi} operator, hence
% each \eI{copy x x} rule is mutually exclusive with the other rules.

The \eI{copy} predicate, as given, implements the identity and may seem rather useless, 
but it is not! Since the program is open, one can add new rules for
\eI{copy} and change its behavior. For example the code below
computes the weak head normal form of a $\lambda$-term by contracting
the application of a $\lambda$-abstraction
to an argument and uses \eI{copy} to perform the substitution:

\begin{elpicode}
pred whd tm ~$\to$~ tm.
whd (app H A) R :- whd H (lam F), !,           % we fire the $\beta$-redex
  pi x\ copy x A => copy (F x) S, whd S R.     %   and we continue
whd X X.                                       % or we stop
\end{elpicode}

The argument \eI{A} is put in place of the (previously) bound variable in
\eI{F} by replacing that variable with \eI{x} and
by running \eI{copy} with the addition of a special rule
copying \eI{x} to \eI{A}.
Our static analysis understands this programming pattern
and is able to recognize that \eI{whd} is also a function.
In particular the first rule, if taken, discard the second rule (due to the cut)
and only calls functions.

\subsection{\chr: goal suspension}
\label{sec:chr}

Constraint Handling Rules (\chr, \cite{chr,chr15}) is a declarative,
rule-based language designed to manipulate a multiset of constraints. A
\chr program consists of rules that match patterns of constraints,
optionally guarded by conditions, and transform the current constraint
store by adding or removing elements. Operationally, execution proceeds
by repeatedly selecting applicable rules and applying them to the
constraint store. 

From a conceptual point of view, \chr can be seen as a rewriting system
over constraints, where rules describe how local configurations evolve.
In contrast to standard logic programming rules, which operate on a
single goal, \chr rules may inspect and rewrite several constraints at
once. 
% This aspect is important when correctness depends on the
% interaction between constraints, rather than on their independent
% resolution. For this reason, \chr naturally supports a more global view
% of computation.

In \elpi, \chr\ is integrated as an extension of the underlying
\lprolog\ engine. The motivation for this integration is the need to
combine and refine goal (seen as suspended constraints) that arise during proof search.
This model explains how the system manages the constraint store. The
main operations are simplification, propagation, and their combination,
called simpagation.
In the following, the notation $\vecL{h}, \vecL{g}, \vecL{b}$, and
$\vecL{k}$ denotes lists of atoms.

\emph{Simplification}, written
$\vecL{h}\ \iff \vecL{g}\ |\ \vecL{b}$, is triggered when the constraints
$\vecL{h}$ are present in the store and the guards $\vecL{g}$ hold. In
this case, $\vecL{h}$ is removed, and the body $\vecL{b}$ is executed,
possibly introducing new constraints.

\emph{Propagation}, written $\vecL{k}\ \iff \vecL{g}\ |\ \vecL{b}$, is
triggered under the same conditions, namely when $\vecL{k}$ is in the
store and $\vecL{g}$ holds. The body $\vecL{b}$ is then executed, but in
contrast to simplification, the constraints $\vecL{k}$ remain in the
store.

\emph{Simpagation}, written
$\vecL{k}\ \backslash \vecL{h} \iff \vecL{g}\ |\ \vecL{b}$, combines the
previous two mechanisms. It is triggered when both $\vecL{k}$ and
$\vecL{h}$ are present in the store and the guards $\vecL{g}$ hold. Then
$\vecL{h}$ is removed, while $\vecL{k}$ is retained, and the body
$\vecL{b}$ is executed.

In \elpi, the concrete syntax for defining rules that handle the
constraint store closely follows the mathematical notation above. A
constraint is declared using the predicate
\eI{declare_constraint}, which takes two arguments: the constraint
itself (an atom) and a list of variables on which the constraint is
suspended.
When a variable is assigned, the constraint is resumed within the
constraint store. A more complete presentation can be found in
\cite[Sec.~4.3]{chr-elpi} and \cite[Sec.~2.4]{hdr}.

\subsection{Rule names and insertion}
\label{sec:elpi-rule-names}

In the \elpi database, the rules used during backchaining are stored in
an ordered data structure. Each rule
can optionally be given a name by the user.

These names are useful when adding new rules that should have higher or
lower priority than existing ones. In this way, the user can control the
position of rules in the search order.

In \elpi, inserting a rule before or after an existing one is called
\emph{grafting}.

\begin{elpicode}
  :name "nth-fail"
  nth _ _ _ :- error "List is to short".
\end{elpicode}

The definition of \eI{nth} above is a catch-all rule, since it applies to
any query. This rule is named \eI{nth-fail}.
When defining additional rules for \eI{nth}, one can write:

\begin{elpicode}
  :before "nth-fail"
  nth N [] _ :- N < 0, error "Index is negative".
\end{elpicode}

This declaration places the new rule just before the catch-all rule,
giving a more precise error in the case of negative index. A
similar syntax can be used with \eI{:after} to insert a rule after an
existing one.

The usefulness of grafting becomes clearer in
\cref{sec:rule-prio}, where type-class instances must be inserted at
specific positions in the database to respect the intended priority.

\subsection{HOAS: \texorpdfstring{$\lambda$}{lambda}-terms representation}
\label{sec:hoas}

In \cref{sec:example-ho-dyn-programs}, we sketched how to encode the syntax of a
language using the HOAS of \elpi. This syntax is inspired by the
$\lambda$-calculus, which forms the core of the \rocq system. 

The encoding of \rocq terms is performed using a \elpi type called
\eI{term}. The snippet depicted in \cref{fig:hoas} shows the main constructors
for terms.

\begin{figure}  
\begin{elpicode}
kind term type.

type sort    sort ~$\to$~ term.                 % Prop, Type@{i}
type global  gref ~$\to$~ term.

type app     list term ~$\to$~ term.            % app [hd|args]
type fun     name ~$\to$~ term ~$\to$~ (term ~$\to$~ term) ~$\to$~ term. 
type prod    name ~$\to$~ term ~$\to$~ (term ~$\to$~ term) ~$\to$~ term. 

...                     % Other constructors omitted
\end{elpicode}
\vspace{-1.5em}
\caption{HOAS of \rocq terms in \elpi}
\label{fig:hoas}
\end{figure}

The base constructors are \eI{sort}, which encodes the \cI{Type} and \cI{Prop}
terms of \rocq, and \eI{global}. The \eI{global} constructor represents
user-defined symbols such as types, inductives, and constants. 

These symbols are identified by a \eI{gref}, which is an opaque object
containing the unique identifier of the corresponding \rocq symbol. For better
space management we use a more compact notation: opaque \rocq{} symbols are
written using guillemets, avoiding the explicit use of the \eI{global}
constructor. For instance, the \rocq{} constant \cI{nat} is represented in HOAS
form as \cI{~<<nat>>~}.

Term application in \rocq is represented by the \eI{app} constructor,
which takes a list of terms. $\lambda$-abstractions and
$\forall$-quantifications are encoded using the \eI{fun} and \eI{prod}
constructors, respectively. Each of these constructors carries the
\eI{name} of the \rocq binder (used only for pretty printing), the type of the
binder, and an \elpi higher-order object of type
\eI{term ~$\to$~ term}, which represents the abstraction of the bound
variable in the term.

  \centering
\begin{tabular}{lll}
  \rocq terms & \elpi HOAS & description\\
  \hline
  \cI{plus 0}             & \eI{app [~<<~plus~>>~, ~<<0>>~]} & term application\\
  \cI{fun x: int => ?F a}       & \eI{fun `x` ~<<int>>~ y\ app [F, ~<<a>>~]} & $\lambda$-abstraction\\
  \cI{~$\forall$~ x: bool, p x} & \eI{prod `x` ~<<bool>>~ z\ app [~<<p>>~, z]} & $\forall$-quantif and binding
\end{tabular}

\label{tab:rocq-to-elpi-hoas}
\end{table}

The \rocqelpi backend translates \rocq terms into HOAS \elpi terms and
conversely when the two systems interact. In
\cref{tab:rocq-to-elpi-hoas}, we show some examples of this encoding:
the first column contains \rocq terms, and the second column their HOAS
representation in \elpi.

The second and third rows illustrate how binders are handled for
$\lambda$-abstraction and $\forall$-quantification. The original binder
name from \rocq is stored in the \eI{fun} and \eI{prod} constructors,
while the name of the bound variable in \elpi is not relevant. In the third row,
the \elpi abstracted variable \eI{z} is reused to represent the abstraction

The second row shows a \rocq unification variable \cI{?F}. It is

assigned to \cI{?F}.

\paragraphTwo{Quotations and Antiquotations}

Writing \rocq{} terms can be tedious, as it requires explicitly constructing
their full HOAS representation. As shown in
\cref{tab:rocq-to-elpi-hoas}, the \elpi{} HOAS syntax is significantly more
verbose than standard \rocq{} syntax. Moreover, \rocq{} often includes implicit
subterms, whereas \elpi{} does not provide such a mechanism.

To simplify development, \rocqelpi{} offers a system of quotations and
antiquotations. This mechanism allows embedding \rocq{} syntax within \elpi{}
code, and conversely \elpi{} syntax within \rocq{} code, in a recursive manner.

An illustrative example, adapted from~\cite{hdr}, is the following:
%
$$\underbrace{\eI{print}}_{\elpi}\ \{\{ \underbrace{\cI{1 +}}_{\rocq}\ \eI{lp:}\{\{\underbrace{\eI{app[~<<S>>~, }}_{\elpi}\{\{ \underbrace{\cI{0}}_{\rocq} \}\} \underbrace{\phantom{aa}}_{\elpi} \}\} \underbrace{\phantom{aa}}_{\rocq} \}\}$$

Within an \elpi{} code block, the syntax \cI{{{ ... }}} denotes a
quotation that allows writing \rocq{} code. Conversely, within \rocq{} code, the
syntax \eI{lp:{{ ... }}} denotes a quotation for embedding \elpi{} code.
These constructs can be nested arbitrarily.

\subsection{API in \rocqelpi}
\label{sec:elpi-main-API}

Thanks to the HOAS representation of \rocq terms in \elpi, the two
languages become closer and can share a common representation. This
makes their interaction easier and allows interleaving computations
between them. The \rocq language exposes several APIs that can be used
directly from \elpi.
%
\begin{center}
  \eI{pred coq.unify-eq term, term ~$\to$~ diagnostic.}
\end{center}

The predicate above is widely used in \elpi developments. It takes two
terms and attempts to unify them. If unification fails, it returns a
diagnostic explaining the error. Internally, this predicate relies on
the \rocq unification algorithm. When \elpi{coq.unify-eq} is called, the
HOAS representation of the terms is translated into \rocq terms before
performing the unification.

Other predicates allow extending the \rocq system with new definitions,
modules, modes, and more.
%
\begin{center}
  \eI{pred coq.typecheck term ~$\to$~ term, diagnostic}
\end{center}

For example, the predicate above calls the \rocq typechecker of a term $t$.
typechecking returns the type of $t$ if $t$ can be typechecked, otherwise it
returns a dignostic of the type-error in its last argument.

\subsection{Declaring Databases in \rocqelpi}

In \cite[Sec. 4.4.3]{hdr}, a database is defined as a non-executable \elpi
program. It contain a collection of code that can be included into commands
or tactics by referring to its name.

When a program is executed, it does not use the state of the database at the
moment when the command was defined. Rather, it accesses the current content
of the database at execution time. This means that any update to the database
is visible to all programs that include it.

An \elpi database can be dynamically modified by adding new predicate
signatures and rules.

\begin{elpicode}
kind clause type.
%           Name     Grafting    Rule
type clause string ~$\to$~ grafting ~$\to$~ prop ~$\to$~ clause.

%                           DB name  Indexing  PName
pred coq.elpi.add-predicate string,  string,   string,
                                  list (pair argument_mode string) ~$\to$~.
%                        Scope    DB name   Clause
pred coq.elpi.accumulate scope, string, clause ~$\to$~.
\end{elpicode}

The \eI{coq.elpi.add-predicate} predicate takes as arguments the name of
the database where the predicate is inserted, the indexing
strategy\footnote{We do not discuss indexing in detail, as it is not
central for this manuscript. It determines the data structure used to
store rules in order to improve search efficiency.}, the predicate
name, and its specification (argument modes and types).

The \eI{coq.elpi.accumulate} predicate adds a new clause to a database
within a given \rocq scope (e.g. module, section, file \dots). A clause is a specific type with a single
constructor, which contains the clause name, its grafting with respect
to the existing database, and the rule itself.

These last two predicates are particularly useful in the context of
\cref{sec:class-encoding,sec:instance-encoding}.

The \eI{msolve} predicate takes as input a list of \rocq sealed goals and
returns an updated list of sealed goals. The type \eI{sealed-goal}, shown in
\cref{fig:goals-type}, represents goals that may contain abstractions (typically
the context in which the goal leaves). These abstractions are encoded using the
\eI{nabla} constructor.

For example, consider the \rocq{} goal
\begin{prooftree}
  \AxiomC{$h : t$}
  \UnaryInfC{$?s : t$}
\end{prooftree}
where $?s$ denotes the proof term to be constructed for the conclusion
$t$ in a context containing the hypothesis $h : t$. In \elpi{}, this
goal is represented as \eI{nabla x\ t'}, where the variable $x$
corresponds to the abstraction of the local hypothesis $h$ in the term
$t'$. The term $t'$ is the \elpi{} encoding of the \rocq{} conclusion
$t$.

Under a spine of \eI{nabla} abstractions, the \eI{seal} constructor
encodes a goal. A goal is a tuple with five components: a context $C$,
a raw solution $S_r$, a type $T_y$, a final solution $S$, and a list of
arguments $L$.

The context $C$ assigns types to the quantified variables. The type
$T_y$ represents the type of the \rocq goal to solve. The terms $S_r$
and $S$ are \elpi unification variables associated with the same
\rocq existential variable, and both are constrained by $T_y$.

Instantiating $S_r$ triggers its elaboration with respect to $T_y$.
By contrast, instantiating $S$ triggers typechecking against $T_y$.
The difference is that elaboration (see \cref{sec:rocq-intro}) may
transform the input term, for example by inserting coercions, while
typechecking only verifies that the term has the expected type.

The list $L$ contains additional arguments that guide the resolution
process. In this work, we mainly use two projections of a goal: the
context and the goal type.

We can now define more precisely the shape of the translation of
\begin{prooftree}
  \AxiomC{$h : t$}
  \UnaryInfC{$?s : t$}
\end{prooftree}
which is represented in \elpi{} as \eI{nabla x.(goal [decl x ~<<t>>~] (X x)
~<<t>>~ (Y x) [])}. The context \eI{[decl x ~<<t>>~]} records that \cI{x} has
type \eI{t}. The two higher-order variables \cI{X} and \cI{Y} are associated
with the \rocq{} existential variable \cI{?s}.


If the predicate \eI{msolve L N} is not defined, or if it fails when applied to
the list of goals \eI{L}, then the system attempts to solve each goal in
\eI{L} individually using the predicate \eI{solve}. In this case, \eI{solve} is
called on the content of the \eI{seal} constructor, meaning that all
\eI{nabla}s have already been traversed, and the type of these nablas loaded in
the context as local rules with \eI{=>}.
%
\begin{center}
  \eI{pred solve goal ~$\to$~ list sealed-goal.}
\end{center}

The final point addressed in this section concerns the \eI{refine} predicate.

Given a goal \eI{G} and a proof term \eI{P}, one may wish to typecheck \eI{P}
against the \eI{G} and obtain the corresponding list of subgoals that must be
solved recursively. The \rocq tactics performing this task is called
\eI{refine}.

In \elpi{}, the \eI{refine} predicate exists and has the same behavior: it takes
a proof term and a goal, it typechecks the proof agains the goals and returns a
list of subgoals on the for of a list of sealed-goals. It is customary for
\elpi{} tactics to invoke \eI{refine} in order to produce the output list for the
\eI{solve} predicate.

For performance reasons, \elpi{} also provides a variant, \eI{refine.no_check},
which skips typechecking and directly produces the list of sealed subgoals from
the given term and goal. This results in faster, although less reliable,
computation.
