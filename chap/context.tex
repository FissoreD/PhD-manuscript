\paragraphTwo{Ad-hoc polymorphism}

\marginpar{Collegare con Elaboration}

Polymorphism is a fundamental feature of functional programming languages. In
his lecture notes, Strachey~\cite{polymorphism} distinguishes between two main
forms of polymorphism: parametric polymorphism and ad-hoc polymorphism.
Parametric polymorphic functions are \emph{uniform}, meaning that their behavior
does not depend on the specific type at which they are instantiated. For
example, the function \emph{length}, with type \mlI{'a list -> int}, returns $7$
when applied to any list of seven elements. In other words, the compiler
reuses the same implementation of \emph{length} for every call, regardless of
the instantiation of \mlI{'a}.

Parametric polymorphism is widely used in functional
programming. However, it is not suitable for modeling mathematical
function overloading. In mathematics, the symbol $+$ has a consistent,
intuitive meaning, and no ambiguity arises in expressions such as $1 + 2$
or $\pig + e$. In the first expression, $+$ denotes addition over integers;
in the second, it denotes addition over real numbers. The same
symbol is consistently used for operations that share common algebraic
properties.

In contrast, parametric polymorphism does not allow to
have multiple different type-dependent interpretations. This limitation appears in
languages such as \ocaml, where integer and floating-point additions
are represented by distinct operators, $+$ and $+.$, respectively. Thus, one
writes $1 + 2$ for integers and $\pig +\!.\ e$
\footnote{In \ocaml, $\pig$ is \mintinline{ocaml}{Float.pi} and $e$ is \mintinline{ocaml}{Float.exp 1.0}}
for floating-point numbers.
In
general, a different symbol must be introduced for each type implementing a
given mathematical operation.

To address the need for a shared notation for operations and
properties across types, Wadler and Blott introduced the notion of type classes
in 1989~\cite{wadler1989-tc} and were soon implemented in
\haskell~\cite{wadler1996-hs} as a pervasive feature of the language. Then
other languages, such as \rocq~\cite{sozeau2008-tc} also extended their
type system to allow this kind of overloading.

\subsection{Ad-hoc polymorphism: Type classes}
\label{sec:ad-hoc-poly}

\paragraphTwo{Symbol overloading}
Type classes provide a principled form of ad-hoc polymorphism, enabling
a single symbol to be associated with multiple type-specific implementations
while preserving static type safety.
They provide structure parameterized by one or more types~$t$ and
declare the signatures of a set of functions, called methods, whose
types may depend on~$t$. An instance of a type class provides a concrete
implementation of the type class for a specific choice of~$t$, providing
definitions for all of its methods.

Unlike parametric polymorphism, where a unique function is used for the
execution of a call, type classes rely on instance resolution. Typeclasses and
instances inhabit a database mapping classes to their instances. When compiling
a call to a type class method, the elaborator finds the right implementation by
selecting the instance of the type class associated with the given type in the
given database.

As an example, consider the type class \cI{Add}, parameterized by a
type \cI{T} and equipped with a method \cI{plus} to perform addition between
two elements of type \cI{T}. In \rocq, the definition of \cI{Add} is given
below.

\cI{Add T} are implicit. The typechecking of the term
\cI{plus 3 4} gives:

\subsection{Abstract syntax of \elpi (without \chr)}
\label{sec:elpi-syntax}

\begin{figure}
  \centering
  \includegraphics{img/syntax.pdf}
  \caption{Abstract syntax of \elpi\ programs}
  \label{fig:elpi-syntax}
\end{figure}

\paragraphTwo{Syntax of \elpi\ programs}

\Cref{fig:elpi-syntax} presents the abstract syntax of \elpi\ programs.

The basic syntactic categories are data~\DATA,
predicates~\PRED, unification variables~\UVAR, and
nominal variables~\NVAR. Nominal variables represent binders
introduced either by $\lambda$-abstractions or by $\pi$-quantification.

A term~\TERM\ is either one of these basic constructs or an application. More
precisely, terms are built by the binary application of a term to a
$\lambda$-term~\LTERM. Lambda terms introduce abstractions; in the concrete
\elpi\ syntax an abstraction is written \eI{x\ t}. Function application follows
a curried style: unlike \prolog, \elpi does not use parentheses between the
functor and its arguments.

An atom~\ATOM\ represents an executable unit. It can be:
\begin{enumerate}
  \item the cut operator (\eI{!} in the concrete syntax),
  \item a predicate call,
  \item a $\pi$-quantification, written \eI{pi x\ t} in the concrete syntax,
        which introduces a fresh nominal variable \eI{x} visible in \eI{t}, or
  \item the dynamic insertion of a rule~\RULE, written \eI{r => t}, which
        makes the rule \eI{r} locally available while solving \eI{t}.
\end{enumerate}

A rule~\RULE\ consists of a head and a (possibly empty) body, which is a
list of atoms. The atoms in the body are called the premises of the rule.

For simplicity, we omit constraints from the syntax, since they
do not play an immediate role in the presentation. They are briefly
described in \cref{sec:chr}.

\paragraphTwo{Syntax of \elpi\ types}

In \elpi, users can define the algebraic data types required by their
development as well as the signatures of predicates. A new algebraic data type
is declared with the \kind\ keyword, while constructors of that type are
introduced using the \type\ keyword. A type is ether a definition is either a
type declaration, a variable, or the application of a type to another in the
case of parametric types. The arrow symbol is used to type function space and in
\elpi it take an optional mode information. The mode, \Einput or
\Eoutput, tells the runtime which unification algorithm to use when unifying the
arguments of two terms, we dealy this discussion in the next paragraph. By
default, no mode information is compiled to \Eoutput.

For example, the following declarations define Church naturals and
polymorphic lists.

\mvspace
\begin{minipage}{0.45\textwidth}
  \input{code/elpi_nat.tex}
\end{minipage}
\begin{minipage}{0.5\textwidth}
  \input{code/elpi_list.tex}
\end{minipage}
\mvspace

The type \eI{nat} contains the constant \eI{z} representing zero and the
constructor \eI{s} representing the successor of another natural number.
A \eI{list} is either empty \eI{nil} or the
constructor \eI{cons} that combines a head element with a tail list.
Lists are polymorphic: the type of the head element must coincide with
the type of the elements stored in the tail.

A predicate is a symbol whose type ends in \eI{prop}. The type \eI{o}
is an equivalent notation following the convention of~\cite{miller2012}.
\elpi\ provides a dedicated syntax for declaring predicates, which also
allows the programmer to specify the modes of their arguments.

The declaration
\eI{pred p i:t1, o:t2.} where \eI{t1} and \eI{t2} are types,
is equivalent to the declaration
\eI{type p t1 -> t2 -> prop} but it also specifies that the first
argument of \eI{p} is an input (\eI{i:}) and the second is an output
(\eI{o:}). These modes are used at runtime to determine which
unification strategy should be applied when matching the head of a rule
with the current goal.

\paragraphTwo{Program type checking}

\elpi\ is an (almost) strongly typed language. When a program is
interpreted, the type checker verifies that it is well typed. Any type
inconsistency is reported as an error, which typically helps identify
and correct implementation bugs early.

\subsection{Operational semantics of \elpi\ (without \chr)}
\label{sec:elpi-semantics}

\begin{figure}[t]
  \centering
  \includegraphics{img/det_check/dynamic.pdf}
  \caption{Operational semantics of \elpi}
  \label{fig:elpi-semantics}
\end{figure}

A substitution $\sigma$ of type $\Sigma$ is a partial mapping from
unification variables \UVAR\ to terms \TERM. The application of a substitution
to a term $t$ is written $\sigma\ t$. The empty substitution is denoted by
$\EmptySubst$. The domain $\dom\ \sigma$ of a substitution $\sigma$ is the set
of variables that are assigned in $\sigma$.

\begin{definition}[Substitution extension]
  A substitution $\sigma'$ is an extension of $\sigma$ iff
  $$
  \exists \sigma''.\
  \sigma + \sigma'' = \sigma'
  \ \land\
  \dom\ \sigma'' \cap \dom\ \sigma = \varnothing .
  $$
\end{definition}

\noindent
A typing environment $\env$ maps predicates \PRED\ to their signatures.

A program $\prog$ of type $\PROG$ is represented as a record with the
following structure:

{
\mvspace
\centering
\txtI{~$\PROG$~ := {index: list ~$\RULE$~; nvar: set ~$\VAR$~; sig: ~\env~}}\par
\mvspace
}

The field \txtI{index} is an ordered list of rules representing the rule
database. The field \txtI{nvar} contains the set of nominal variables that have
already been introduced, and \txtI{sig} is the signature environment.

We write $x \# \prog$ to denote that the nominal variable $x$ is fresh with
respect to $\prog.\txtI{nvar}$. The notation $x +_\forall \prog$ denotes the
program obtained by adding $x$ to $\prog.\txtI{nvar}$. Similarly,
$h +_\Rightarrow \prog$ denotes the program obtained by prepending the rule $h$
to $\prog.\txtI{index}$.

A goal $g$ of type
$\g = \PROG \times \ATOM \times \vecL{\alt}$
is a triple consisting of a program, an atom, and a list of
\emph{cut-to alternatives}. An alternative $a$ of type $\alt$ is a pair
$\Sigma \times \vecL{\g}$ composed of a substitution and a list of goals.

\Cref{fig:elpi-semantics} presents the derivation rules of the \elpi\
interpreter, defined in terms of the function
\[
  \runE : \vecL{\alt} \to (\Sigma, \vecL{\alt}) + \mnone .
\]

This semantics is inspired by
\cite[Sec.~4.3]{debray1988} and \cite{hdr}. Execution is modeled as the
evaluation of a stack of alternatives $\alt$. The interpreter processes
alternatives sequentially. The evaluation of the alternative list either succeeds,
producing a substitution and a new list of alternatives, or fails, returning
$\mnone$.

In \cref{fig:elpi-semantics}, rule \runE[\top] captures success: if the first
alternative contains an empty list of goals, the interpreter returns its
associated substitution together with the remaining alternatives. Conversely,
rule \runE[\bot] states that evaluation fails when the list of alternatives is
empty.

The remaining rules of \runE, namely \runE[!], \runE[\backchainE],
\runE[\forall], and \runE[\Rightarrow], apply when the first alternative
contains a non-empty list of goals. Such alternative list has the form
$\ConsHd{\ConsHd{q}\ConsTl{g}}{\ConsTl{a}}$, where $q$ is the current goal atom
(or query). The derivation rule to use depends on the syntactic form of $q$, which
can be one of the four forms of \ATOM\ listed in \cref{fig:elpi-syntax}.

If $q$ is a \cut, rule \runE[!] discards the current alternatives $a$ and
replaces them with the cut-to alternatives stored in $q$. Evaluation then
continues with the remaining goals $g$.

If $q$ is a $\pi$-quantification $\pi x.\,t$, the interpreter generates a fresh
nominal variable $y$ not occurring in $\prog$, replaces all free occurrences of
$x$ in $t$ with $y$, and continues evaluation with the resulting atom.

If $q$ corresponds to the dynamic insertion of a rule $h$, evaluation continues
with atom $t$ in the program extended with the local rule $h$.

Finally, if $q$ is a predicate call, the interpreter performs \emph{backchaining} over
the rules stored in $\prog.\txtI{index}$. Backchaining retrieves the rules that
can be used on the query $q$. In standard Prolog this is done by selecting
rules whose head unifies with $q$. In \elpi the process depends on predicate
modes, which determine if a argument should be ``matched'' or ``unified''.

\elpi provides two procedures, \unify\ and \matching. Both have type
\[
\TERM \to \TERM \to \Sigma \to \Sigma + \mnone ,
\]
taking two terms and an initial substitution $\sigma$. They either fail
(returning $\mnone$) or succeed with an updated substitution $\sigma'$ that is
an extension of $\sigma$.

The procedure \unify\ implements higher-order unification restricted to the
pattern fragment~\cite{miller1991-pf} and is used for arguments in
\Eoutput\ position. The procedure \matching, inspired by \bprolog's
``matching clauses'', is used for arguments in \Einput\ position.

\begin{definition}[\unify]\label{def:unify}
Two terms $q$ and $u$ \emph{unify} under a substitution $\sigma$ if there
exists a substitution $\sigma'$ extending $\sigma$ such that
$\sigma' q = \sigma' u$, and $\sigma'$ is a most general unifier for the two terms.
\end{definition}

\begin{definition}[\matching]\label{def:matching}
A query $q$ \emph{matches} a pattern $u$ under a substitution $\sigma$ if there
exists a substitution $\sigma'$ extending $\sigma$ such that
$\sigma' u = \sigma q$, where $\sigma'$ assigns at most the free variables
occurring in $u$.
\end{definition}

Backchaining is defined by the function \backchain:\marginpar{var refreshing in bc def}

\begin{definition}[Backchain, $\backchain : \PROG \times \TERM \times \Sigma \to
\vecL{\Sigma \times \vecL{\ATOM}}$]
\[
\backchain(\prog, q, \sigma) =
\bigg[
(\sigma', b)\ \kIF\
\select(\getmode(\prog.\mathrm{sig}, q), q, h, \sigma) = \sigma' \neq \mnone
\ \bigg|\ 
(\clauseCmd{h}{}{b}) \in \prog.\mathrm{index}
\bigg].
\]
\end{definition}

Intuitively, \backchain selects the rules that can be applied to the current
query $q$ under substitution $\sigma$. For each usable rule it returns the
updated substitution obtained by matching/unifying the rule head with $q$,
together with the rule body.

The definition relies on two auxiliary functions:
\begin{align}
  \getmode &: \env \to \TERM \to \TYPE + \mnone \\
  \select  &: (\TYPE + \mnone) \to \TERM \to \TERM \to
              \Sigma \to \Sigma + \mnone .
\end{align}

The function \getmode retrieves the signature of the predicate occurring in a
term. It returns the signature if the predicate is present in the environment,
and $\mnone$ otherwise.

The function \select tests whether the query $q$ matches/unifies the head $h$ of a rule
under an initial substitution $\sigma$. The predicate signature determines the
mode of each argument, which in turn selects the appropriate procedure:
\matching\ for \Einput\ arguments and \unify\ for \Eoutput\ arguments.
If all arguments satisfy the unification condition, \select returns the resulting substitution
$\sigma'$; otherwise it returns $\mnone$.

\begin{definition}[\elpi backchain, $\backchainE :
\PROG \times \TERM \times \Sigma \times \vecL{\alt} \times \vecL{\g}
\to \vecL{\alt}$]

\[
\backchainE(\prog, t, \sigma, a, g) =
\bigg[
\sigma',
(
  [(\prog, q, a) \mid q \in b] \atsign g
)
\ \bigg|\ 
(\sigma', b) \in \backchain(\prog, t, \sigma)
\bigg].
\]
\end{definition}

The function \backchainE, used by rule \runE[\backchain] in
\cref{fig:elpi-semantics}, builds a new list of alternatives from the result of
\backchain. For each filtered rule, the atoms in the rule body become new
goals whose cut-to alternatives are $a$ and whose continuation is $g$. The
substitution associated with each alternative is the one returned by
\backchain.

where
$
  \sigma_3 \coloneq \sigma_1 + \{\eI{B} \mapsto \eI{0}\}
$
;
$
  \sigma_4 \coloneq \sigma_1 + \{\eI{B} \mapsto \eI{1}\}
$
and
$
  \sigma_5 \coloneq \sigma_1 + \{\eI{B} \mapsto \eI{2}\}
$.

The next step of interpretation continues with \eI{f B C} under $\sigma_3$,
that is, \eI{f 0 R}, and leaves $[(\sigma_4, []), (\sigma_5, [\eI{!}])]$ as new choice points.
This time, backchaining fails (no rule for \eI{f} matches input $0$). We
therefore backtrack to the most recently introduced choice point and retry
\eI{f B C} under $\sigma_4$, i.e. \eI{f 1 R}. This succeeds with
$\sigma_6 \coloneq \sigma_4 + \{\eI{R} \mapsto \eI{2}\}$.

We now reach the cut. At this point there are still two unexplored
alternatives: one from the third rule for \eI{r} and one from the second rule
for \eI{g} (respectively, $\sigma_5$ and $\sigma_2$). Both are discarded,
because they were created when, or after, the first rule for \eI{g} was
selected. In contrast, a cut does not discard choice points created earlier;
in this example, there are none.
The final solution is:
$
  \{\eI{A} \mapsto \eI{0}, \eI{B} \mapsto \eI{1}, \eI{C} \mapsto \eI{R},
  \eI{R} \mapsto \eI{2}\}
$.

\subsection{Higher-order programs in \elpi}
\label{sec:HO-program}

A notable higher-order program is the one turning relations into functions.
\footnote{The syntax \eI{~\PYG{k+kd}{(pred)}~}, equivalent to \eI{~\PYG{k+kd}{(pred ->)}~},
is for fully applied predicates, i.e. for terms with neither inputs nor outputs}
% any predicate
% into a function.
%
\begin{elpicode}
func once (pred) -> . % a function taking a fully applied predicate
once P :- P, !.       % the ! commits to the first success
\end{elpicode}


%
We say that the signature of the \eI{once} predicate marks it as \emph{unconditionally}
a function: \eI{once} leaves no choice points, no matter what it receives as
the higher-order argument \eI{P}.

An example of a \emph{conditional} function is
the predicate to map over a list:
\begin{elpicode}
func map (func A -> B), list A -> list B.
map _ [] [].
map F [X|XS] [Y|YS] :- F X Y, map F XS YS.
\end{elpicode}
%
We say that the signature of \eI{map} has a \emph{precondition}, namely
that \eI{F} is a function, and a \emph{postcondition}, namely that
\eI{map} is a function, i.e., the call \eI{map F L L'} leaves
no choice points.
If the precondition is not met the postcondition is not guaranteed to hold and we say
that \eI{map} is \emph{miscalled}. In this case we weaken its signature to%
\footnote{We explain in detail this weakining operation in \cref{sec:basic}}:
%
\begin{elpicode}
pred map (func A -> B), list A -> list B.
\end{elpicode}
%
Our static analysis tracks miscalled functions and considers them as
relations for the analysis of the surrounding code. This is important to
avoid code duplication, i.e., we can just have one copy of
\eI{map} in our library.
We give an example of four scenarios involving calls and miscalls to \eI{map}.


% \noindent
% \begin{minipage}{.5\textwidth}
\begin{elpicode}
% a function                      % a relation
func incr int -> int.             pred get_pdiv int -> int.
incr 1 2.                         get_pdiv 6 3. get_pdiv 6 2.

       % four predicates calling map or miscalling map
func p list int -> list int.      pred q list int -> list int.
p L R :- map incr L R. ~\PYG{c}{\PYGZpc{} OK}~       q L R :- map get_pdiv L R. % OK

func r list int -> list int.      func r1 list int -> list int.
r L R :- map get_pdiv L R.        r1 L R :- map get_pdiv L R, !. % OK
           % ^^^^^^^^ error: non-deterministic atom
\end{elpicode}
%\vspace{-1.5em}
% \end{minipage}

Here \eI{p} is a function because the precondition of \eI{map} is respected
(\eI{incr} is a function).
The body of \eI{q} contains a miscall to \eI{map}; as a consequence
\eI{q} may leave choice points. This is not an error because
\eI{q} is declared to be a relation. 
The body of \eI{q} and \eI{r} are identical, but
\eI{r} should be a function and hence the static analyzer complains.
The predicate \eI{r1} has the same signature of \eI{r} but it
compensates the miscall to \eI{map} by discarding choice points via
a cut. The static analyzer accepts this last declaration. We point out that,
partial applications, like, \eI{(map incr)}, are accepted in our system,
see \cref{sec:basic}.



\subsection{Dynamic programs in \elpi}
\label{sec:dynamic-prog}

The domain where \elpi really shines is the manipulation of higher-order data
represented via the so-called $\lambda$-tree syntax~\cite{miller2018}
also called HOAS~\cite{pfenning1988}.
Such data is pervasive in interactive provers based on Type Theory
such as \rocq. In the paradigmatic example below \eI{tm} is
the data type for $\lambda$-terms.
%
\begin{elpicode}
kind tm type.                       % datatype of $\lambda$-terms in HOAS form
type app tm -> tm -> tm.            %  - binary application
type lam (tm -> tm) -> tm.          %  - $\lambda$-abstraction
\end{elpicode}
%
In the HOAS encoding of syntax with binders we do not find a node for variables:
we re-use the notion of bound variable of the programming language to encode the
one of the syntax tree. At the level of types we see that the \eI{lam}
node carries an \elpi function over terms. It is by applying this function
that one can recover the body of the $\lambda$-abstraction.
A simple program manipulating higher-order data is the function
performing a deep copy of a term:
%
\begin{elpicode}
func copy tm -> tm.
copy (app A B) (app C D) :- copy A C, copy B D.
copy (lam F) (lam G)     :- pi x\ copy x x => copy (F x) (G x).
\end{elpicode}
%
The copy of an application is built from the copies of the subterms. What is
more interesting is how one copies under a binder.
The ``\eI{pi x\ copy x x =>}'' instruction
generates a fresh constant \eI{x} and adds to the program the
rule \eI{copy x x} for the rest of the execution of copy. That rule
explains how to copy the new constant \eI{x}. Intuitively ``\eI{pi x\.. => ..}''
amounts to a well-bracketed use of Prolog's \texttt{assert/1} and \texttt{retract/1}.
Finally the code performs a recursive call over \eI{F x}:
by applying the \elpi function \eI{F} to
the fresh symbol \eI{x} one obtains the body of the $\lambda$-abstraction
where the bound variable is replaced
by the new symbol \eI{x}.

In \elpi, all predicates are \emph{dynamic}, or open, hence
the code of \eI{copy} can be
augmented with rules at runtime. 
% \todo{remark app, lam and each x are different}
% \todo{we want copy to be a understood as a function}
Even so \eI{copy} is a function because no
two rules can apply to the same input: \eI{lam} and \eI{app}
are different constants, and each constant \eI{x} generated dynamically is
guaranteed to be fresh by the \eI{pi} operator, hence
each \eI{copy x x} rule is mutually exclusive with the other rules.

The \eI{copy} predicate, as given, implements the identity and may seem rather useless, 
but it is not! Since the program is open, one can add new rules for
\eI{copy} and change its behavior. For example the code below
computes the weak head normal form of a $\lambda$-term by contracting
the application of a $\lambda$-abstraction
to an argument and uses \eI{copy} to perform the substitution:

\begin{elpicode}
func whd tm -> tm.
whd (app H A) R :- whd H (lam F), !,           % we fire the redex
  pi x\ copy x A => copy (F x) S, whd S R.     %   and we continue
whd X X.                                       % or we stop
\end{elpicode}

The argument \eI{A} is put in place of the (previously) bound variable in
\eI{F} by replacing that variable with \eI{x} and
by running \eI{copy} with the addition of a special rule
copying \eI{x} to \eI{A}.
Our static analysis understands this programming pattern
and is able to recognize that \eI{whd} is also a function.
In particular the first rule, if taken, discard the second rule (due to the cut)
and only calls functions.

\subsection{Unification in \Fo{} and \Ho{}}
\label{sec:unif-fo-ho}

In order to reason about unification we provide a description of the
\Fo{} and \Ho languages where unification variables
are first-class terms, i.e. they have a concrete syntax as
shown in \cref{code:common-terms}.
Unification variables
in \Fo{} (\eI{o-uva} term constructor) have no explicit scope:
the ``arguments'' of a higher-order variable are given via the \eI{o-app}
constructor. For example the term <<\cI{P x}>> is represented as
<<\eI{o-app [o-uva N, x]}>>, where \eI{N} is the memory address
of \eI{P} and \eI{x} is a bound variable.
In \Ho{} the representation of <<\cI{P x}>> is instead <<\eI{uva N [x]}>>,
since unification variables are higher-order and come equipped with an
explicit scope.

\section{Notational conventions}
In the following section we note $\mathbb{B}$ for the boolean type, and $\top$
and $\bot$ for \cI{true} and \cI{false}. The constructors of the option type are written
$\msome{t}$ for \cI{Some}$~t$ and $\mnone$ for \cI{None}.
Following the Mathematical Components library, on which we depend,
we use \cI{x.1} and \cI{x.2} to denote the first and second projection
applied to the pair \cI{x}. List concatenation is the infix \cI{++},
while list comprehension (i.e. mapping a function on a list) is written
\cI{[seq f x | x <- l]}. The function \cI{odflt d o}
extracts the value from the option \cI{o} and returns the default \cI{d}
if \cI{o} is $\mnone$.
