\chapter{A Mechanized First-Order Static Determinacy Checker}
\label{chap:mechanization}

In the previous chapter we explained the implementation of the determinacy
checker algorithm that we have included in ELPI since version 3. The checker
helps users control backtracking: the user asserts which predicates should be
considered deterministic and then the checker verifies that these predicates
produce at most one solution for each call, i.e. they commit to their first
solution, leaving no \emph{choice points}.

In this chapter we present our work consisting of the formalization (in \rocq)
of the determinacy checker we implemented in \elpi. This formalization covers
the first-order part of the language, i.e. it does not consider higher-order
variables or dynamic rule loading, such as the \pi and \eI{=>} operators. The
idea of the formalization is to implement a \emph{det\_check} predicate that
tests whether a program satisfies determinacy, i.e. whether every predicate
declared deterministic produces at most one solution per call. Finally, we
show that if a program satisfies this det\_check, then any call to a
deterministic predicate in the \elpi semantics produces at most one solution.

In order to proceed in this direction, we consider one main aspect.
Determinacy is greatly influenced by the presence of cut in the code. This
operator impacts the execution of the code and, therefore, it is important to
correctly identify its scope while reasoning about determinacy.

The operational semantics of \elpi is, however, not well suited for reasoning
about the scope of cuts. Because the syntax of \elpi programs does not
explicitly record the structure of the search space, it is difficult to
determine precisely which alternatives are discarded by a given cut.

To address this issue, we introduce a semantics based on And-Or trees, in which
the history of the computation is represented in a structured way: given a goal,
each applicable rule generates an Or-branch, which is in turn followed by an
And-branch for each premise. This enables an explicit characterization of the
cut operator as a function that prunes selected branches of the tree. The
tree-based semantics allows us to formulate introduction and elimination rules
for disjunction in the presence of cut, which, as expected, differ from those of
classical logic. For example, $q_1 \lor q_2$ is not equivalent to $q_2 \lor
q_1$, since the branch corresponding to $q_2$ may be pruned during the
evaluation of $q_1$.

Once we have defined this semantics, we prove its equivalence with the
\elpi semantics. Finally, we use the tree-based semantics to prove the
correctness of the determinacy analysis from~\cite{fissore2026}.

Our mechanization is axiom-free and is available at
\url{https://github.com/FissoreD/elpi-formalization}.

The remainder of this work is organized as follows. We first present in
\cref{sec:preliminaries} the syntax we use in our \rocq development to represent
terms, atoms, rules, and programs (it is a subset of the syntax shown in
\cref{sec:elpi-syntax}). In \cref{stack-sem}, we provide the formal
representation of the \elpi semantics restricted to the first-order fragment,
called \runS (it is a subset of \cref{sec:elpi-semantics}). After the
formalization of the \runS, we formalize the And-Or tree semantics, called
\runT, and show some properties about the impact of the cut operator on
disjunctions. In \cref{equiv}, we prove the equivalence of the two semantics.
Finally, in \cref{sec:determinacy}, we prove the correctness of the determinacy
analysis with respect to the And-Or tree semantics..

\section{Introduction}


\elpi is a dialect of \lprologP (see \cite{miller1991-pf,miller2012,dunchev15,TASSI_2019})
used as an extension language for the \rocq prover (formerly the \coqP proof
assistant). \elpi has become an important infrastructure component: several
projects and libraries depend on it~\cite{krebbers2025,enzo2023,maas2024,fissore2023,fissore2024}.
Other notable Rocq libraries based on \elpi
include the Hierarchy-Builder library-structuring tool~\cite{hb};
the Trocq proof-transfer tool~\cite{Trocq,TrocqJ}
and Derive~\cite{tassi2018,tassi2019,tassi2023}, a program-and-proof synthesis
framework with industrial applications at SkyLabs AI.

Starting with version 3, \elpi is equipped with a static analysis for
determinacy~\cite{fissore2026} to help users control backtracking.
\rocq{} users are familiar with functional programming, but not necessarily
with logic programming; in particular, uncontrolled backtracking is a common
source of inefficiency and makes debugging harder. The determinacy checker
allows users to specify which predicates should be considered deterministic
and then verifies that these predicates behave like functions, i.e., that
they commit to their first solution and leave no \emph{choice points}
(places where backtracking could resume). A choice point corresponds to a
suspended, \emph{alternative}, computation. In the following, we
use \emph{choice point} and \emph{alternative} as synonyms.

Intuitively, nondeterminism arises when a computation can be completed using
two different rules. The static analysis in~\cite{fissore2026} excludes this
situation in two steps. The first step, called \emph{mutual exclusion},
checks that at most one rule can apply to a given query. This condition is
satisfied if either (i) no two rules have overlapping heads, so that no
query can unify with both, or (ii) the analysis accounts for the presence of
cut in rule premises, so that once the cut is executed all remaining rules
are discarded. The second step, called \emph{rule checking}, verifies that
each rule either (i) calls only functions, ensuring that no choice point
remains after the premises of the chosen rule have been executed, or (ii)
executes a cut after calling relations, in which case any choice points left
by the call are discarded.

The static analysis introduced in~\cite{fissore2026} is supported by
benchmarks that demonstrate its usefulness, but it is not accompanied by a
proof of soundness. This paper reports our first steps toward mechanizing
the soundness of this analysis. In particular, we focus on the control
operator \emph{cut}, which is pervasively used to write deterministic code
and causes the semantics to depart from a purely logical reading.

We mechanize two operational semantics for \prolog with cut. The first is a
stack-based semantics that closely models \elpi's implementation and is
essentially the semantics given by Debray and
Mishra~\cite[Sec.~4.3]{debray1988}, which underlies standard \prolog
abstract machines~\cite{warren1983,ait1991-wam,pusch1996}.
This semantics admits efficient implementations, but it makes reasoning
about the scope of cut difficult: alternatives are stored in a stack, in
chronological order, and the cut operator is represented as a pointer to a
shorter stack. The relation between the rule being cut and the affected
stack frames is therefore not immediately visible.

To address this limitation, we introduce a semantics based on And-Or trees,
in which the history of the computation is represented in a structured way:
given a goal, each applicable rule generates an Or-branch, which is in turn
followed by an And-branch for each premise.
This enables an explicit characterization of the cut operator as a function
that prunes selected branches of the tree. The tree-based semantics allows
us to formulate introduction and elimination rules for disjunction in the
presence of cut, which, as expected, differ from those of classical logic.
For example, $q_1 \lor q_2$ is not equivalent to $q_2 \lor q_1$,
since $q_2$ may be cut away by $q_1$.

Finally, we use the tree-based semantics to prove the correctness of the
static determinacy analysis from~\cite{fissore2026}. We prove in Rocq that
any call to a predicate identified as deterministic leaves no additional
Or-branches in the tree when it terminates. By composing this result with
the equivalence between the two semantics, we obtain that any call to a
deterministic predicate leaves no choice points on the stack used by the
\elpi interpreter.

The description of a program is given by a pair
$\PROG := (\mathrm{list}\ \mathbb{R} \times \mathrm{sigT})$ and is shared by
both semantics. A program consists of a list of rules together with a signature
environment $\mathrm{sig}$.
We delay the discussion of signatures to \cref{sec:determinacy} where we
describe the static analysis that concerns them.

A rule is a pair $\RULE := (\TERM \times \mathrm{list}\ \ATOM)$, where
the first element represents its head and the second its list of premises. Each
premise is an atom, i.e. either the cut operator or a term
call. Terms include predicate symbols, data symbols, variables, and term application.
The concrete definition of these two algebraic types is given below:
%
\begin{align*}
  \TERM & := \mathrm{Symb}\ \mathbb{N} \mid \mathrm{Pred}\ \mathbb{N} \mid \mathrm{Var}\ \mathbb{N} \mid \mathrm{App}\ \TERM\ \TERM\\
  \ATOM & := \mathrm{cut} \mid \mathrm{call}\ \TERM
\end{align*}

The syntax tree allows variables to be applied and predicates to be mixed with
data. These higher-order features play no role in the current paper, which
focuses on first-order logic programming, but they allow future extensions to
full $\lambda$\prolog to be based on the same mechanization.


Variables, predicates and data symbols
are identified by natural numbers. We represent substitutions
(of type $\Sigma$) as finitely supported maps from variables to terms, using the
finmap library~\cite{finmap}.
The empty substitution is written $\epsilon$,
while the composition of two substitutions $\sigma_1$ and $\sigma_2$ with
disjoint supports as $\sigma_1 + \sigma_2$.
 
The backchaining operation applies all rules to a query term; it is
central to both semantics and it has the following type:
%\input{./formalization/img/bc_type.tex}
%
$$\mathrm{backchain} : \mathbb{P} \to \FV \to \TERM \to \Sigma \to (\FV \times \mathrm{list}\ (\Sigma \times \mathrm{list}\ \ATOM)) $$

Since a rule may be applied multiple times, its variables must be
freshened before each application. Accordingly, the backchain function
takes a program, the set of variable names used so far (\FV), a
query term, and the current substitution. It returns an updated
set of variable names together with the list of alternatives, i.e. the
rules that apply. More precisely, for each applicable rule it returns the
rule premises together with an updated substitution obtained by unifying
the rule head with the query term.

The function \emph{unify} takes two terms $t_1$ and $t_2$, together with a
substitution $\sigma$, as input, and optionally returns a substitution
$\sigma'$ that extends $\sigma$. Therefore, if $t_1$ and $t_2$ unify
under $\sigma$, then $\sigma'~t_1 = \sigma'~t_2$, where
$\sigma~t$ denotes substitution application and $=$ denotes 
syntactic equality.

To keep the mechanization axiom-free, we implement a unification
algorithm, which we briefly describe in~\cref{sec:determinacy} and prove
sound and complete.
Since the two semantics and the static analysis use the same
unification algorithm, the equivalence proof is completely agnostic to
the particular implementation chosen for that algorithm.

\section{Stack-based semantics}
\label{stack-sem}

The stack-based semantics we present is very close to what is
implemented by the \elpi interpreter and is a subset of \cref{sec:elpi-semantics}.
This semantics is 
similar to the one proposed by Pusch in
\cite{pusch1996}, which is in turn closely related to the
semantics given by Debray and Mishra in
\cite[Section~4.3]{debray1988}. Pusch mechanized this
semantics in Isabelle/HOL, together with several optimizations that are
also present in the Warren Abstract Machine
\cite{warren1983,ait1991-wam}.

The execution state is a stack of alternatives.
Each alternative is a list of goals. Intuitively it amounts to
a disjunctive normal form: each stack item is a self contained
computation, coupling a substitution with all the goals to be
solved.

Goals pair an atom with a list of the \emph{cut-to} alternatives, 
making the two datatypes mutually recursive, but these alternatives
have a very different role. They have to be understood
as pointers to lower levels of the stack itself.
They are used to implement the cut, i.e. to prune the stack of alternatives.
$$\mathrm{alts} := \mathrm{list}\ (\Sigma \times \mathrm{goals})  \qquad \mathrm{goals} := \mathrm{list}\ (\ATOM \times \mathrm{alts})$$

% We are completely loosing the tree structure. There are no clean reset
% points. The backtracking operation is simpler: it is the tail function.
% The cutr and cutl operations disappears: the alternatives are stored 
% directly in the cutE terminal.
%\noindent
The stack-based semantics is described by the \runS inductive
predicates.

\noindent
The \runS predicates relates a set of variables and a
list of alternatives to optional result. None stands for failure,
i.e., no solution, whereas Some $(\sigma, a)$ represents success with $\sigma$
being the solution and $a$ as the list of not-yet-explored
alternatives.

The rule system for \runS is given in \cref{fig:nur-rules} and is made by $4$
cases. We distinguish two main cases. If we run out of alternatives
we fail: rule \fails stops the execution and return None.
If the list of alternatives is $(\sigma_0, h) :: a$, then
we look at the list of goals $h$ (under the substitution $\sigma_0$). If $h$ is empty, rule \stops stops the execution with a success $\sigma_0$
leaving $a$ as the unexplored alternatives.
If $h$ is not empty we look at its head goal $(t, ca)$ where $t$ is the atom and $ca$ is its
cut-to alternatives. If $t$ is a cut, rule
\cuts continues to evaluate the tail of $h$ under with alternatives $ca$. Finally, when $t$ is a call, rule \calls backchains:
for each rule it pairs each premise with the current stack of
alternatives, and prepends the obtained goals to the tail of $h$.
Note that if backchain returns the empty list, the second
premise of rule \calls amounts to exploring the next item in the current
stack.

\section{And-Or Tree semantics}
\label{tree-sem}
% \begin{figure}[b]
%     % \input{./formalization/img/tree_def.tex}
% %     \begin{coqcode}
% % Inductive tree ~$\coloneq$~
% %   | KO | OK                            (* failure and success *)
% %   | Todo of Atom                       (* unexplored branch *)
% %   | Or   of option tree & ~$\Sigma$~ & tree ~$\!$~    (* $A \lor B_\sigma$ *) 
% %   | And  of tree & list Atom & tree.   (* $A \land_{B_0} B$ *)
% % \end{coqcode}
%   $$\TREE := \mathrm{KO} \mid \mathrm{OK} \mid \mathrm{Todo}\ \ATOM \mid \mathrm{Or}\ (\mathrm{option}\ \TREE)\ \Sigma\ \TREE \mid \mathrm{And}\ \TREE\ (\mathrm{list}\ \ATOM)\ \TREE$$
% \caption{Definition of And-Or tree}
% \label{fig:tree-ty}
% \end{figure}

An And-Or tree is a stratified, variable-width tree, defined as follows:
%
$$\TREE := \mathrm{KO} \mid \mathrm{OK} \mid \mathrm{Unexplored}\ \ATOM \mid \mathrm{Or}\ (\mathrm{option}\ \TREE)\ \Sigma\ \TREE \mid \mathrm{And}\ \TREE\ (\mathrm{list}\ \ATOM)\ \TREE$$

It consists of two kinds
of layers that alternate: a disjunctive layer is followed by a conjunctive
layer and vice versa. At the root (a query), the tree records a list of
alternatives (an Or-layer); for each alternative, it records a list of
subqueries to be solved (an And-layer). Intuitively, solving a query requires
solving one alternative in the Or-layer, but all subqueries in the
corresponding And-layer. These invariants about the \TREE data type
are precisely debscribed in \cref{sec:validtree} where we introduce the
\vast predicate.


The tree is built incrementally. The \emph{Unexplored} node
represents an unexplored branch (an atom). When the atom is a
call, we use the backchaining procedure from
\cref{sec:preliminaries} to compute the two layers to attach to the tree:
alternatives form the Or-layer, and the premises of each applicable rule form
the corresponding And-layer. This expansion step is performed by the
\emph{step} procedure described in \cref{sec:step}.

In addition to the Unexplored node we have two distinguished nodes,
\koC and \okC, which respectively represent the smallest failed and successful
trees.

The \orC node, written \(A \lor B_\sigma\), represents the addition of an
alternative \(B_\sigma\) to an existing disjunction $A$. The left subtree
\(A\) is optional and is absent once that branch has been fully explored.
The right alternative is paired with a substitution \(\sigma\), which becomes
the current substitution when backtracking to \(B\).

The \andC{} node, written \(A \land_{B_0} B\), represents the addition
of a subquery \(B\) to the first choice point in \(A\). We call
\(B_0\) the \emph{reset point} for \(B\): it represents the
continuation for all alternatives of \(A\) except the first. That is,
when backtracking occurs within \(A\), the subtree \(B\) is replaced by
the atoms in \(B_0\). An example is shown in~\cref{sec:na}.

A graphical representation of a tree is shown in \cref{tree-ex1}. For
compactness, we depict \andC and \orC nodes as $n$-ary,
with children associating to the right. The \koC node acts as the terminating
element of an \orC list, while \okC is the terminating element of an \andC
list.

The tree is constructed incrementally by two recursive
functions, \step and \na. Both traverse the tree depth-first, left-to-right.
The node to be explored in a tree is retrieved thanks to \pathend (in~\cref{fig:getend}).
When this node is \okC we say the entire tree is a \emph{success}, when it
is \koC we say the tree \emph{failed}, otherwise the tree is \emph{incomplete}.
In \cref{tree-ex} we mark with a black arrow the result of \pathend.
The type of these two functions is given below.
%
\begin{align*}
  \mathrm{step}  & : \mathbb{P} \to \FV \to \Sigma \to \TREE \to (\FV\times\mathrm{tag}\times\TREE)\\
  \mathrm{prune} & : \mathbb{B} \to \TREE \to \mathrm{option}\ \TREE
\end{align*}
% $$\mathrm{step} : (\mathbb{P}\times\FV\times\Sigma\times\mathrm{tree}) \to (\FV\times\mathrm{tag}\times\mathrm{tree})$$
% $$\mathrm{prune} : (\mathbb{B}\times\mathrm{tree}) \to \mathrm{option\ tree}$$

The step routine, among its outputs, also returns a \emph{tag}, whose definition
is described in the very following section.

To avoid the constraint that all functions must terminate in Rocq, we define the transitive closure
of \step and \na as the inductive relation \runT.

\subsection{The \step procedure}\label{sec:step}
\begin{figure}
  \begin{coqcode}
  Definition step p v s A :=
    match A with
    | OK                  => (v, Success, OK)
    | KO                  => (v, Failed, A)
    | Unexplored cut      => (v, CutBrothers, OK)
    | Unexplored (call t) => 
        let: (v, l) := backchain u p v t s in
        (v, Expanded,
        if l is ((s, r) :: xs) then Or None s (big_or r xs) else KO)
    | Or A sB B =>
        if A is Some A then 
          let: (v, tA, rA) := step p v s A in
          (v, if is_cb tA then Expanded else tA, 
           Or (Some rA) sB (if is_cb tA then KO else B))
        else
          let: (v, tB, rB) := step p v sB B in
          (v, if is_cb tB then Expanded else tB, Or A sB rB)
    | And A B0 B =>
        if success A then 
          let: (v, tB, rB) := step p v (next_subst s A) B in
          (v, tB, And (if is_cb tB then cutl A else A) B0 rB)
        else
          let: (v, tA, rA) := step p v s A in (v, tA, And rA B0 B)
    end.
  \end{coqcode}
  \caption{The \step procedure}
\end{figure}

The \step procedure takes as input a program, a set of variables, a
substitution, and a tree, and returns an updated set of variables, a
\steptag, and an updated tree.

The set of variables is assumed to contain all variables occurring in the
tree. It is passed to backchain so that rules can be refreshed correctly.
% This guarantees that any call
% to \emph{backchain} returns a list of atoms whose variables are disjoint from
% the variables of the current working tree.

The \steptag is implemented as follows: 
%
% \begin{coqcode}
$$\mathrm{tag} := \mathrm{Expanded} \mid \mathrm{CutBrothers} \mid \mathrm{Failed} \mid \mathrm{Success}$$
% \end{coqcode}

It indicates which kind of step was
performed.  Failure and Success are returned for trees that satisfy,
respectively, the \failed and \success tests. 
CutBrothers
indicates the interpretation of a superficial cut: \step was called on an 
And-layer and its \pathend is the cut atom. Finally, Expanded
accounts for the interpretation of predicate calls and non-superficial cuts.

The \step procedure evaluates atoms. In particular, it leaves the tree
unchanged when the tree is \emph{success} or \emph{failed}.

The \step procedure expands Unexplored nodes by calling backchain, which returns a list
$l$ of alternatives. If $l$ is empty, then the current call atom is replaced by

each leaf corresponds to a list of atoms $e \in l$. If $e$ is empty, the leaf
is \okC; otherwise, it is a right-skewed tree of \andC nodes.

\subsubsection{The interpretation of a cut}

The step corresponding to a cut performs two actions: (i) the cut node is
replaced by \okC; and (ii) the subtrees in the scope of \cutC are pruned. More
precisely, (ii) prunes the left siblings of the \cutC node (in the same
And-layer, denoted \cutl) and prunes the right uncles of \cutC (in the
one-level-up Or-layer, denoted \cutr).

    | KO => None

\subsection{The \runT relation and its properties}\label{sec:runT}

The inductive relation \runT has the following type:
%
$$\mathrm{\runT} : \mathbb{P} \to \vec{\FV} \to \Sigma \to \mathbb{T} \to \mathrm{sol} \to \mathbb{B} \to \vec{\FV} \to \cI{Prop}$$

It associates a program, a set of variables, an initial substitution $\sigma$, and a
tree $t$ with a solution $r$, a boolean $b$, and an updated set of variable
names $v'$.

The type of sol is defined as follows:
%
$$\mathrm{sol} := \mathrm{Zero} \mid \mathrm{One}\ \Sigma \mid \mathrm{Many}\ \Sigma\ \TREE$$

Zero represents a failing execution. One\ $\sigma$ represents an interpretation
producing exactly one solution, i.e. no backtracking is possible from the given
state. It also carries the substitution $\sigma$ that makes the interpretation
succeed. Finally, Many $\sigma\ t$ represents an execution in which the
original state produces the solution $\sigma$, while $t$ represents the
remaining unexplored alternatives.

The boolean $b$ records whether a superficial cut was evaluated during execution,
and $v'$ is the updated set of variables tracking freshly generated names.

The \runT predicate has five cases, depicted as inference rules in \cref{fig:run-rules}.
% where we separate the first four arguments and the last one with a squiggle arrow,
% evocative of the fact that the given set of rules is deterministic (\cref{th:runTdet}).


Rules \stopot and \stopt say that if the tree $t$ is success, then the substitution
$\sigma'$ is extracted from $t$ (starting from $\sigma$), depending
on the result of \na true $t$ -- aiming to clean the tree from its successful
path -- we return One or Many, if there exist alternatives
to be explored. Rule \stept applies when \pathend\ $t$ is an atom,
then \step is invoked to evaluate $t$, and \runT is called recursively on the
updated tree. When \pathend\ $t$ is a failure, rule \backt calls \na
to clear the failed path; if the resulting cleaned tree exists, \runT is
called recursively on it. Finally, rule \failt accounts for trees with no
solutions.

lemma is connected to the depth-first exploration of the tree: proving a

From $A \lor B$, when $A$ is not inert (i.e. not already explored), we cannot
deduce $A$ or $B$ independently. Instead, we can only derive a weakened
conclusion of the form $\top \lor B'$, where $B'$ provides no information in the
case where the exploration of $A$ performs a cut. This yields an elimination
rule that is stronger than the usual one.
If $A$ does not cut, the elimination rule has the usual two premises, together
with the additional constraint that whenever $B$ holds, $A$ must have failed.
This again reflects the depth-first traversal of the proof tree.

It is worth recalling that the ``$A$ cuts'' side-condition in the rules above is
precisely the boolean result returned by \runT. Without this information, it is
impossible to formulate these rules: it is not merely a matter of whether $A$
contains a syntactic occurrence of cut, but whether that cut is actually
executed during the (dis)proof of $A$ (in rules $(\lor_{ir1})$ and $(\lor_{ir2})$).
Indeed, an atom preceding the cut may fail, so the cut is never reached.

As anticipated in the introduction, these lemmas contradict the commutativity of
disjunction.



\section{Equivalence of the two semantics}
\label{equiv}

In order to relate the two semantics we have to relate the computations states,
i.e., the And-Or tree and the stack of alternatives. We define a translation from trees to stacks, called \ttl, but
we do not explicitly provide the converse translation, an economy
allowed by the proof technique we employ, inspired by~\cite{yves-equiv}.
Before describing the translation of trees to stacks (in~\cref{sec:t2l})
we need to define the notion of \emph{valid tree}. The {tree}
datatype indeed contains trees that cannot be generated
by {runT} via {step} or {prune}, for example
all the trees that do not correspond to a depth-first left-to-right
tree construction strategy.

While all base cases of {tree} are valid, we need to analyze the \orC and

For the \orC constructor, we distinguish two cases depending on whether the
left-hand side is present. If it is not, then the right-hand side must be a
valid tree. Otherwise, the left-hand side must be a valid tree, and the
right-hand side must either be the \koC tree or be unexplored. The former case
occurs when the right-hand side is cut away by the evaluation of a superficial
cut in the left-hand side.
In the latter case we use the \emph{base\_or} predicate
to check that $B$ is the right-skewed tree formed by a disjunction of
conjunctions, generated after a successful backchain for a call.

For the \andC constructor, the left hand side is required to be a valid tree.
The shape of the right hand side depends on whether the left hand side is a
success. If it is not successful, then the right hand side must not be
explored, i.e. $B$ must be
the right-skewed tree containing conjunctions of premise atoms.
This is enforced using the \emph{big\_and} procedure, which generates a tree
from the reset point $B_0$ (the same procedure used to
transform each alternative output by backchain into the And-layer
of the resulting tree).
When the left hand side is successful, then the right hand side
may have been explored, and consequently must be a valid tree.

We point out the two main invariants that stating that valid trees
are preserved by calls to \step and \na.

\subsection{From trees to stacks}\label{sec:t2l}

The \ttl recursive function translates a tree to a stack.

$$
\mathrm{\ttl} : \TREE \to \Sigma \to \mathrm{alts} \to \mathrm{alts}
$$

% we give junst the implementation of the
% base cases, the full implementation is available at \href{https://github.com/FissoreD/elpi-formalization/blob/ho-check-ffun/theories/t2l.v}{\emph{this}} link.

The function \ttl takes as input the tree $t_0$, a substitution
$\sigma$ for the input tree, and an auxiliary list of choice points $cp$.
These choice points
represent alternatives that appear at the same level of the current
tree, such as, for example, the right siblings of an \orC{} node. 

The \okC node represents one successful alternative; therefore it is translated
into a singleton list whose only element has an empty list of goals. The \koC
node represents failure, hence it is mapped to the empty list of alternatives.
Finally, atoms are mapped to a singleton list containing one alternative whose
only goal is that atom, with an empty cut-to list.
At this stage, the cut-to list cannot point to $cp$: atoms are not
right-uncle subtrees, whereas $cp$ represents alternatives that will actually
be discarded if the atom turns out to be a cut. The correct cut-to list is
therefore determined later, once the trees corresponding to sibling subtrees
have been inspected.

The translation of $A \lor B_\sigma$ creates two list of alternatives,
one for the $A$ and the other for $B$. The alternatives of $B$ are valid
choice points for $A$ and should be passed to the translation of $A$.
The two lists of alternatives can then be concatenated. Moreover, every atom
occurring one level below $cp$ (i.e. in $A$ or $B$) should add $cp$ as its
cut-to alternatives.

The translation of $A \land_{B_0} B$ starts with the translation of $A$. If the
translation of $A$ is an empty list we return the empty list of
alternatives without even touching $B$ nor $B_0$, since an empty
translation for $A$ indicates failure and this in turn implies the
failure of the entire conjunction. When the translation of $A$ is
a list $(\sigma_0, g) :: a$, the $B$ node represents the continuation of the
first alternative $g$, whereas $B_0$ is the continuation for each alternative
in $a$.

From \cref{tree-ex,ex-elpi}, we observe that, upon backtracking, \runT may perform
more steps than \runS before returning a solution or a failure.
These silent transitions must be skipped
when proving the equivalence between the two semantics. Therefore, we

\begin{proof}By induction on the tree $t$.

The first direction of the equivalence states that the execution of a
valid tree is matched by the execution of the stack obtained by
translating the tree. Moreover, the unexplored alternatives returned as
a tree correspond to those returned as a stack.

% \input{./formalization/img/tree_to_elpi.tex}
\begin{theorem}[runT\_to\_runS]\label{th:runTtorunS}%
\begin{multline*}
	\forall\ p\ t\ \sigma\ r ,\ \mathrm{let}\ v\ \mathrm{:=}\ \mathrm{vars}\ t\ \cup\ \mathrm{vars}\ \sigma\ \mathrm{in}\ 
	\mathrm{valid\_tree}\ t \to \mathrm{runT'}\ p\ v\ \sigma\ t\ r \to \\
	\begin{cases}
	\mathrm{runS}\ p\ v\ ( \mathrm{tree\_to\_stack}\ t\ \sigma\ \mnil )\ \mathrm{None} & \mathrm{if}\ r = \mathrm{Zero}\\
	\mathrm{runS}\ p\ v\ ( \mathrm{tree\_to\_stack}\ t\ \sigma\ \mnil )\ (\mathrm{Some}\ (\sigma', \mnil)) & \mathrm{if}\ r = \mathrm{One}\ \sigma'\\
	\mathrm{runS}\ p\ v\ ( \mathrm{tree\_to\_stack}\ t\ \sigma\ \mnil )\ (\mathrm{Some}\ ( \sigma' ,\ \mathrm{tree\_to\_stack}\ t'\ \sigma\ \mnil)) & \mathrm{if}\ r = \mathrm{Many}\ \sigma'\ t'\\
	\end{cases}
\end{multline*}
\end{theorem}

\begin{proof}
We proceed by induction on the execution of \runT'. There are five cases
to consider. The first (similar) cases arises from \stopot and \stopt; they deal with
successful trees. A successful tree corresponds to a stack that
start with an empty list, in both cases
we conclude using \stops. The case for \stept
requires treating two subcases: \step evaluates either a cut or a call.
Accordingly, we apply \cuts or \calls, followed by the
induction hypothesis. The case for \backt is silent: it represents
the non-injective behavior of \ttl; however, thanks to
\cref{th:pruneFtreetostack} and the induction hypothesis, the conclusion is
proved. The last case arises from the derivation \failt. It is
easily proved using \fails and the fact that if \na returns
None when trying to erase failure in $t$, then \ttl applied to $t$
returns the empty list.
\end{proof}

The converse direction is stated following~\cite{yves-equiv}: instead of
using a function to translate a stack into a tree it states that any
tree that translates to the given stack has an equivalent execution,
i.e. gives the same solution and returns an unexplored tree that
translates to the unexplored stack.
% \input{./formalization/img/elpi_to_tree.tex}
\begin{theorem}[runS\_to\_runT]\label{th:runStorunT}%
\begin{multline*}
	\forall\ p\ v\ a\ r ,\ \mathrm{runS}\ p\ v\ a\ r \to
	\forall\ \sigma\ t ,\ \mathrm{valid\_tree}\ t \to \mathrm{tree\_to\_stack}\ t\ \sigma\ \mnil = a \to \\
	% \mathrm{match}\ r\ \mathrm{with} \\
  \begin{cases}
    \mathrm{runT'}\ p\ v\ \sigma\ t\ \mathrm{Zero}             & \mathrm{if}\ r = \mathrm{None} \\
    \mathrm{runT'}\ p\ v\ \sigma\ t\ ( \mathrm{One}\ \sigma' ) & \mathrm{if}\ r = \mathrm{Some}\ ( \sigma' ,\ \mnil ) \\
    \exists\ t' ,\ \mathrm{runT'}\ p\ v\ \sigma\ t\ ( \mathrm{Many}\ \sigma'\ t' ) 
    \land \mathrm{tree\_to\_stack}\ t'\ \sigma\ \mnil = a'     & \mathrm{if}\ r =  \mathrm{Some}\ ( \sigma' ,\ a' ) \\
  \end{cases}
\end{multline*}
\end{theorem}

\section{Case study: determinacy analysis}\label{sec:determinacy}

As an application of the tree semantics, we mechanize the soundness proof\marginpar{TODO: rifare}
of the determinacy-checking algorithm introduced in version~3 of the
\elpi{} language~\cite{fissore2026}. The static checker takes as input
the signatures of the predicates declared by the user and verifies that
the rules of a deterministic predicate generate at most one solution; we
call this kind of predicate a function. Thanks to this static
verification, the user can better control unexpected backtracking.

A predicate behaves deterministically if two conditions are
satisfied: \emph{mutual exclusion} guarantees that at most one rule can
be successfully applied to any given query, whereas \emph{rule body checking}
ensures that each rule does not create choice points, for example by
calling non-deterministic predicates.

% Determinacy checking is strongly related to the modes of predicates: we
% differentiate between input and output arguments. A deterministic call relates
% to its inputs only one output.
% In the literature, we find several works on
% determinacy checking, namely~\cite{1996Somogy,king2005,1989Warren}. These works
% need a mode checker that statically ensures that, in a query with ground inputs,
% each recursive call is performed with ground inputs.

Our mechanization implements the unification algorithm by
Martelli and Montanari~\cite{montanari82}, which we prove
terminating using the standard lexicographic ordering,
correct and complete.

In the following definitions and lemmas, we use the notation $x \cap y =
\varnothing$ to denote that the two sets $x$ and $y$ are disjoint. When the
arguments are terms, as in $t_1 \cap t_2 = \varnothing$, we mean that the two
terms do not share any variables.

The first notion to provide is the application of an acyclic substitution:

\begin{definition}[deref]
  $$
  \begin{array}{rlrlr}
    \sigma\ (\mathrm{Symb}\ n) &= \mathrm{Symb}\ n & \qquad\sigma\ (\mathrm{Var}\ n) &= t &\mathrm{if}\ (n,t) \in \sigma\\
    \sigma\ (\mathrm{Pred}\ n) &= \mathrm{Pred}\ n & \qquad\sigma\ (\mathrm{Var}\ n) &= \mathrm{Var}\ n& \mathrm{otherwise}\\
    \sigma\ (\mathrm{App}\ t_1\ t_2) &= \mathrm{App}\ (\sigma\ t_1)\ (\sigma\ t_2)
  \end{array}
  $$
\end{definition}

\begin{definition}[acyclic]
  $\lambda \sigma. \mathrm{dom}\ \sigma \cap \mathrm{codom}\ \sigma = \varnothing$
\end{definition}

Note that this definition of acyclicity entails that the substitution is
necessarily self applied, i.e. $\sigma \coloneq \{ X \mapsto f~Y, Y \mapsto a\}$
is not acyclic, whereas the equivalent $\sigma' \coloneq \{ X \mapsto f~a\}$
is.
The algorithm by Martelli and Montanari generates substitutions that
are acyclic in this sense.

% \input{./formalization/img/unif_correct.tex}

\begin{lemma}[unify\_correct]\label{th:unifycorrect}%
$$\forall\ t_1\ t_2\ s\ s' ,\ \mathrm{acyclic\_sigma}\ s \to \mathrm{unify}\ t_1\ t_2\ s = \mathrm{Some}\ s' \to s'\ t_1 = s'\ t_2 $$
\end{lemma}

% \input{./formalization/img/unify_complete.tex}
\begin{lemma}[unify\_complete]\label{th:unifycomplete} $\forall\ t_1\ t_2\ s ,\ \mathrm{acyclic\_sigma}\ s \to$
% \begin{multline*}
$$( \exists\ s' ,\ \mathrm{acyclic\_sigma}\ s' \land s'\ ( s\ t_1 ) = s'\ ( s\ t_2 ) ) \to \exists\ s'' ,\ \mathrm{unify}\ t_1\ t_2\ s = \mathrm{Some}\ s''$$
\end{lemma}

The \elpi language adopts a
restricted unification routine for input arguments, called
\matching~\cite{ait1991-wam,zhou2012}. Similarly to \unify, \matching takes the
query term $t_1$ and the pattern $t_2$ and returns an optional substitution
$\sigma'$ that does not assign any variable in the query arguments that
are in input position.
% The query-term is the argument in input mode taken from a dynamic
% call and the pattern is the corresponding input argument in the chosen
% rule-head.

To address this need, we extend the Martelli-Montanari unification
procedure so that it takes a set of frozen variables, i.e. variables that
cannot be assigned. The function \matching has the following property:

% \input{./formalization/img/matchdisj.tex}
\begin{lemma}[matching\_disj]\label{um}\label{th:matchingdisj}
  $$\forall t_1\ t_2\ \sigma\ \sigma', \mathrm{acyclic}\ \sigma \to \mathrm{matching}\ t_1\ t_2\ \sigma = \mathrm{Some}\ \sigma' \to \sigma'\ t_1 = \sigma\ t_2$$
\end{lemma}

In particular, we can see how the returned substitution $\sigma'$, differently
from \cref{th:unifycorrect}, does not affect variables in $\sigma\ t_2$.

\begin{corollary}[matching\_same]\label{umm}\label{th:matchingsame}
  $$\forall t\ q\ \sigma\ \sigma', \mathrm{acyclic}\ \sigma \to \mathrm{matching}\ t\ q\ \sigma = \mathrm{Some}\ \sigma' \to \sigma'\ q = \sigma\ q$$
\end{corollary}


% If the variables (\cI{vars}) of two terms are disjoint ($\#$) and the variables in the support of $\sigma$ are
% disjoint from the variables in $t_1$, then, if matching succeeds, only the
% variables in $t_2$ are assigned; that is, $t_1 = \sigma'~t_2$, and the
% variables in $t_1$ are not assigned in $\sigma'$.


The backchain function uses matching or unify on the arguments $q$
depending on whether the argument is in \emph{input} or
\emph{output} mode.
% We assume two important properties of our unification routines.

For the static checker, and in particular in order to validate rule mutual
exclusion, we need to ensure that no two rules can be used on the same query in
the absence of cut. We exploit the behavior of the matching over input
arguments to guarantee this property: mutual exclusion ensures that every
pair of rules for a deterministic predicate has an input term that does
not unify.

An important property we derive from the matching and unification
procedures is the following. Given three pairwise variable-disjoint terms
$h_1$, $h_2$, and $q$, representing two rule heads in the database and a
query, if both heads match the query $q$, then the two heads must unify.
% This is formalized in the following lemma.

% \input{./formalization/img/matching_unify_transP.tex}

\begin{lemma}[matching\_unify\_transP]\label{th:matchingunifytransP}%
\begin{multline*}
	\forall\ h_1\ h_2\ q .\ h_1 \cap h_2 = \varnothing \to h_1 \cap q = \varnothing \to h_2 \cap q = \varnothing \to \\
	\mathrm{matching}\ h_1\ q\ \varnothing \to \mathrm{matching}\ h_2\ q\ \varnothing \to \mathrm{unify}\ h_1\ h_2\ \varnothing 
\end{multline*}
\end{lemma}

\begin{proof}
  By \cref{um}, we now that the matching of $h_1$ (resp. $h_2$) and $q$ gives a
  substitution $\sigma_1$ (resp. $\sigma_2$) where the variables in $q$ are not
  assigned, i.e. its domain only contains variables in $h_1$ (resp $h_2$). Using
  \cref{th:unifycomplete} we need to prove that it exists a
  substitution $\sigma'$ such that $\sigma'\ h_1 = \sigma'\ h_2$. This
  substitution is the composition of $\sigma_1$ and $\sigma_2$, that is
  $\sigma' = \lambda x. \sigma_1 (\sigma_2\ x)$. Since $h_1$ and
  $h_2$ are disjoint, also are the domain of $\sigma_1$ and $\sigma_2$, therefore
  $\sigma' h_1 = \sigma_2 (\sigma_1\ h_1)$ and $\sigma' h_2 = \sigma_2 (\sigma_1\ h_2)$.
  We can know conclude the proof: $\sigma'\ h_1 = \sigma_2 (\sigma_1\ h_1) = \sigma_2\ q = q = \sigma_2\ h_2 = \sigma' h_2$.
\end{proof}

Finally, we also need to prove that the refreshing of variables
performed at runtime does not affect unification.
In particular, a refreshing renaming $f$ for a term $t$ is a function from
variables to variables such that: (i) $f$ is defined on all variables in
$t$, i.e. every variable is renamed; and (ii) $f$ is injective, i.e. it
does not identify distinct variables. Refreshing therefore produces
$\alpha$-equivalent terms.

  $\lambda t_1\ t_2. \exists (r:\mathrm{renaming\_for}\ t_2), t_1 = \mathrm{rename}\ r\ t_2$
\end{definition}

\begin{lemma}[unif\_ren\_ac]\label{th:unifren}
  $\forall\ t_1\ t_2\ t_1'\ t_2', t_1 =_\alpha t_1' \land t_2 =_\alpha t_2' \to$

  $\phantom{xxxxA}

  $
\end{lemma}

In \cref{fig:progx}, the rules of the program are equipped with three
signatures, one per predicate. Besides the arity of each predicate, a
signature specifies which arguments are inputs and which are outputs,
their types, and whether the predicate is deterministic. They indicate
that \texttt{f} and \texttt{g} are expected to be functions, as specified
by the \eI{~\PYG{k+kd}{func}~} keyword, whereas \eI{r} is a relation, as
indicated by the \eI{~\PYG{k+kd}{pred}~} keyword. The
\eI{~\PYG{k+kMode}{\PYGZhy{}\PYGZgt{}}~} symbol separates inputs from
outputs; therefore, all three predicates are expected to take an
\texttt{int} as input and return an \texttt{int} as output.

The signatures of the program are stored in the \texttt{sig} field of
the program and are encoded as described in
\cite{fissore2026}: we distinguish data from predicates, and predicates
are classified as deterministic or non-deterministic.

A program execution behaves deterministically if, given a program, a
substitution, and an input tree for the \runT\ inductive, the execution
either fails or succeeds with no alternatives left to explore.
% Below, we define \texttt{is\_det}.


% \input{./formalization/img/is_det.tex}
\begin{definition}[is\_det]\label{th:isdet}%
	$$\lambda\ p\ \sigma\ v\ t .\ \forall\ r ,\ \mathrm{runT'}\ p\ v\ \sigma\ t\ r \to r = \mathrm{Zero} \lor \exists\ \sigma ,\ r = ( \mathrm{One}\ \sigma ) $$
\end{definition}

\begin{definition}[tm\_is\_det]\label{def:tmisdet}
  Given a program $p$ and a term $t$,
  we say that $t$ is deterministic if its head is a predicate $f$
  which is declared as deterministic in $p$.
\end{definition}

The theorem we want to prove is the following one:

% \input{./formalization/img/det_check_call.tex}
\begin{theorem}[det\_check\_call]\label{th:detcheckcall}$\forall\ p\ \sigma\ t\ v ,$
  \vspace{.8em}\\
	$\phantom{xxxxx} \mathrm{check\_program}\ p \to \mathrm{tm\_is\_det}\ p\ t \to \mathrm{is\_det}\ p\ \sigma\ v\ ( \mathrm{Unexplored}\ ( \mathrm{call}\ t ) ) $
\end{theorem}

Here, check\_program denotes the function that checks the program
with respect to mutual exclusion and rule checking. %, and \emph{tm\_is\_det}
% denotes the function that tests whether the head of the term refers to a rigid
% constant with a deterministic type.

The proof of this lemma proceeds by induction on
the program execution. However, without further work,
the induction
hypothesis is too weak since it talks about \taC trees (i.e. atoms),
whereas we need it on any tree.

To overcome this issue, we introduce the notion of deterministic trees,
written det\_tree. Intuitively, a deterministic tree is a tree
whose interpretation does not generate choice points. The definition is
shown in~\cref{fig:dettree}.

\begin{figure}
\begin{coqcode}
  Fixpoint det_tree (p: program) A :=
    match A with
    | Unexplored cut => true
    | Unexplored (call t) => tm_is_det p t
    | KO | OK => true
    | And A B0 B =>
        det_tree p B &&
        ((prune (success A) A == None) ||
         ((det_tree p A || (has_cut B && has_cuts B0)) && det_trees p B0))
    | Or None _ B => det_tree p B
    | Or (Some A) _ B =>
        det_tree p A && if has_cut A then det_tree p B else (B == KO)
    end.
\end{coqcode}
\caption{The \emph{det\_tree} predicate\label{fig:dettree}}
\end{figure}

For a call to a term $t$, the tree is deterministic whenever $t$ calls a
deterministic predicate. The recursive cases correspond to the \andC and
\orC nodes.

A conjunction behaves deterministically whenever its right-hand side is a
deterministic tree. Two cases must then be considered.

If $\mathrm{prune}\ (\mathrm{success}\ A)\ A = \mathrm{None}$, then $A$ produces
no choice points: it either always fails or contains a single successful
execution path. Since $\mathrm{det\_tree}\ p\ B$ holds, the entire conjunction
is therefore deterministic.

Otherwise, the left-hand side may introduce backtracking, potentially
resuming the reset point, which must itself behave deterministically.
In this case, either $A$ is deterministic, or both $B$ and the reset
point contain a cut that prevents the non-deterministic behaviour arising
from the evaluation of $A$.

For \orC trees, the interesting case is when the left-hand side contains
an tree. In this case, $A$ must be deterministic. If $A$
contains a superficial cut, then $B$ must also be deterministic. Indeed,
if $A$ succeeds, the cut discards $B$; otherwise, if $A$ fails before
reaching the cut, then no solution is produced by $A$ and $B$ is evaluated.

Finally, if $A$ does not contain a cut, then $B$ must be equal to
$\mathrm{KO}$, that is, a tree already discarded by a cut. This
condition is essential. Otherwise, if $A$ succeeds without a
superficial cut and $B$ is not $\mathrm{KO}$, then $B$ could still
produce a successful branch, leading to non-deterministic behaviour.

The following lemmas show that deterministic trees are preserved by the
operations \step and \na.

%\input{./formalization/img/det_tree_step.tex}
\begin{lemma}[det\_tree\_step]\label{th:dettreestep}
  $\forall\ \mathrm{p}\ v\ \sigma_1\ A\ r ,\ \mathrm{check\_program}\ \mathrm{p} \to$\\
	$\phantom{xxxxx} \mathrm{step}\ u\ \mathrm{p}\ v\ \sigma_1\ A = r \to \mathrm{det\_tree}\ \mathrm{pr}\ (\mathrm{snd}\ r) $
\end{lemma}

% \input{./formalization/img/det_tree_prune.tex}
\begin{lemma}[det\_tree\_prune]\label{th:dettreeprune}%
	$$\forall\ p\ A\ B\ b ,\ \mathrm{det\_tree}\ p\ A \to \mathrm{prune}\ b\ A = \mathrm{Some}\ B \to \mathrm{det\_tree}\ p\ B $$
\end{lemma}

\noindent Finally, we can prove the following lemma that entails det\_check\_call:

% \input{./formalization/img/det_check_tree.tex}
\begin{lemma}[det\_check\_tree]\label{th:detchecktree}%
	$$\forall\ \sigma\ v\ p\ t ,\ \mathrm{check\_program}\ p \to \mathrm{det\_tree}\ p\ t \to \mathrm{is\_det}\ p\ \sigma\ v\ t $$
\end{lemma}

\section{Related work}

The only mechanization of \prolog's semantics that we could find is
Pusch's \isabelle formalization~\cite{pusch1996}, which follows
 Debray and Mishra~\cite[Sec.~4.3]{debray1988}.
That work starts from this semantics and refines it by introducing
optimizations commonly found in the Warren abstract
machine~\cite{warren1983,ait1991-wam}. Unlike our case study,
it does not use the semantics to prove properties of program execution;
consequently, it does not encounter the difficulty described in
\cref{stack-sem}, which led us to develop a semantics in which the
effect of cut is more explicit. In this sense, the two approaches are
complementary: taken together, they suggest that the tree-based
semantics is equivalent to an optimized stack-based one.

Another relevant work is due to Kriener and King~\cite{king2011}, but
we could not find their Rocq source code. Their semantics is
denotational and cannot easily account for all the features covered
in~\cite{fissore2026}, although it would have been sufficient for the
first-order fragment considered in this paper.

Hanus and Prott~\cite{hanus2025} formalize a determinacy checker for
the logic-functional Curry language. In this language choice points
are eplicitly denoted by the \cI{?} node in the syntax of expressions.
In this setting the mutual exclusion of rules does not need to be
ensured resorting to unification: the overlap of rules is explicit in the
syntax. Similarly the operator to absorb choice points, \cI{allValues},
explicitly receives the expression containing them as an argument making the
scope of this control operator trivial to analyze.

The proof technique we use to relate the two semantics is inspired
by~\cite{yves-equiv}, where Bertot mechanizes the correctness of a
compiler. He relates the semantics of an imperative language to that of
its compiled assembly code and proves their equivalence. His approach
uses the compiler as the translation function from one language to the
other, but does not introduce a decompiler, just as we do not define a
function from stacks to trees. To show that the assembly code behaves
like the imperative language, he proceeds by induction on the execution
of the assembly program. We adopt the same strategy in the proof of
\cref{th:runStorunT}.

For the static analysis of determinacy, we use a semantics in which
input arguments are \emph{matched}, rather than unified, against rule
heads. This choice agrees with the \elpi interpreter, which is in turn
inspired by B-\prolog's
``matching-clauses''~\cite{ait1991-wam,zhou2012}.
Applying our results to a semantics based entirely on unification is
possible by adding two extra assumptions to
\cref{th:detcheckcall}. First, the initial query must have ground inputs. Second, the
program must be well-moded. Well-moded predicates produce ground
outputs when given ground inputs; hence, starting from an initial query
with ground inputs, well-moded programs behave exactly as if input
arguments were matched. In other words,
\cref{th:matchingdisj} could be reformulated using unification, at the
cost of an additional assumption that the input arguments are ground;
under that assumption, unification and matching coincide.

\section{Conclusion}

This paper describes two operational semantics for \prolog with cut. The first\marginpar{TODO: rifare}
semantics is based on And--Or trees: it is well suited both to graphical
illustrations of the scope of cut and to proving lemmas about the effect of
cut evaluation when reasoning about disjunctions. The second semantics is
based on a stack of alternatives: it is closer to actual \prolog
implementations, including the first-order fragment of \elpi, but it loses
the explicit structure of the tree-based semantics and is therefore less
convenient for reasoning about cut. We show how to translate trees into
stacks and prove the two semantics equivalent. Using the tree-based
semantics, we mechanize a soundness proof of the first-order fragment of the
determinacy checker of~\cite{fissore2026}, namely that a call to a
deterministic predicate returns at most one solution.

The mechanization consists of approximately 2,500 lines of
specifications and about 5,000 lines of ssreflect proofs based on
the Mathematical Components library~\cite{assia2022}
and its finmap~\cite{finmap} extension.
Roughly 30\% of the code is dedicated to the tree semantics, in particular
the proofs in \cref{sec:runT}, 15\% to the stack semantics, and 35\% to the
equivalence proof. The remaining 20\% is devoted to the determinacy checker.
The mechanization took us approximately $8$ months.
We believe that the ssreflect proof language, and the proof style it
advocates, helped us carry out the many refactorings that the mechanization
underwent. The finmap library provides comprehensive support for reasoning
about finite maps and finite sets over a countable domain. In particular, it
helped us express conditions such as the disjointness between sets of
variables and the domain of a substitution, as well as define the union of
disjoint substitutions.

To obtain an axiom-free mechanization, we had to provide an implementation
of the first-order unification algorithm, since we could not find an
existing Rocq mechanization. Describing this development in detail is out of
scope for this paper. It amounts to about 1,700 lines of ssreflect code,
including 200 lines for the termination proof based on a lexicographic
ordering and 800 lines for correctness and completeness. Because of the
specific form of \cref{th:unifren,th:matchingdisj}, which deals with
matching and unification of terms with disjoint support, we did not need to
prove that the algorithm produces most-general unifiers.

To fully model the \elpi language and mechanize~\cite{fissore2026} entirely,
we would need to account for higher-order variables, that is, variables that
represent predicates. This extension is ongoing and largely orthogonal to
the present paper, since cut and higher-order variables do not interact in
subtle ways. The main difficulty is that substitutions may contain
predicates, and these predicates must have signatures compatible with those
assumed statically, in the sense of the $\subseteq$ relation defined
in~\cite[Section~5]{fissore2026}. Dynamic predicates also require minor
changes to the conditions for mutual exclusion.
