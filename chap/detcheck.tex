Elpi is a higher-order logic programming language, a dialect of
\(\lambda\)Prolog, particularly well suited for manipulating
syntax trees with binders (see \cite{miller1991-pf,miller2012,dunchev15lpar,tassi2019-1}). It is used as an
extension language for the Rocq Prover (formerly the Coq proof
assistant) and has become an important piece of infrastructure: several
projects and libraries depend on Elpi~\cite{krebbers2025,enzo2023,enzo2024,maas2024,fissore2023,fissore2024}. Examples include the
Hierarchy-Builder library-structuring tool~\cite{hb},
which supports the Mathematical Components ecosystem~\cite{assia2022} and
mechanizations such as the Odd Order and Four Color theorems
\cite{gonthier2013,gonthier2023},
and Derive~\cite{tassi2018,tassi2019,tassi2023}, a program-and-proof synthesis framework with industrial
applications at BlueRock systems.


Over the years Elpi was put in the hands of quite a number of Rocq users
and the most widely cited barrier to entry has been the paradigm shift to a
logic programming one.
Rocq users
are comfortable with typed and functional programming but often lack
experience with backtracking and its control. Uncontrolled
backtracking can produce slower programs and complicate debugging.

To lower this barrier we design a system of determinacy signatures that
allows programmers to declare when a predicate behaves like a
function: at most one result is produced and the runtime will not
consider alternative results. This notion of determinism is
called \emph{semidet} by
Henderson et al.~\cite{henderson1996} and named \emph{operationally
deterministic} by Nakamura~\cite{nakamura1986}. Alternative notions
exist, for example Warren~\cite{warren1989} considers predicates
\emph{observably deterministic} when they produce the same result
multiple times or diverge.
We chose operational determinacy since it matches
the behavior of functions in mainstream functional languages.

Our determinacy checker covers Elpi's
higher-order features, including higher-order predicates (for
example map and fold, see \cref{sec:HO-program}) and dynamic predicates that extend themselves at
runtime (see \cref{sec:dynamic-prog}). %, and meta-programs that manipulate Elpi code.

We apply these signatures to a large portion of publicly available
Elpi code in the Rocq ecosystem and report our experience. Our
findings indicate that most Elpi programs are intended to be
backtracking-free and require only minimal signatures for the static
analyzer we implemented to verify determinacy.

\section{Elpi and determinacy signatures by examples}\label{sec:intro}

As in most logic programming languages, Elpi programs are organized in rules.
When rules are not \emph{mutually exclusive}, i.e. multiple rules apply on the same query,
the runtime continues the computation 
using the rule with highest priority. Moreover it stores the 
other rules as a \emph{choice point} and
can backtrack to that point to continue the computation.
What makes backtracking tricky to Elpi users is that it is an opt-out feature
of logic programming: it is left to the programmer to tell the
runtime to commit to one rule and discard the choice point, rather than
the other way around. If the user forgets to commit to a rule, his program
still works but becomes much harder to debug and typically slower to run
in case of failures.

The simplest example is the list-membership \emph{relation} that
can succeed more than once if the element we are looking for occurs multiple
times in the list:

\begin{elpicode}
mem X [Y|_ ] :- X = Y.    % the head is the X we are looking for, or
mem X [_|YS] :- mem X YS. % recurse on the tail
\end{elpicode}

In the code above each line represents a rule. By convention, unification
variables are capitalized, and following the $\lambda$-calculus tradition
application is written without parentheses, i.e. $f~x$ rather than $f(x)$.
Square brackets are used for lists with pipe separating the head from the tail.
The \eI{:-} symbol separates the head of a rule from its premises. Rules are tried 
in the order of their declaration by unifying their head with the current query.

The first rule for \eI{mem}
is the base case: it succeeds if the head of the list is equal to the \eI{X} we are
looking for. The second one discards the list's head and continues looking for
\eI{X} in the tail.
A query such as \eI{mem 2 [2,3,2]} can be solved
in two different ways: either using rule 1 immediately, or using rule 2
twice to discard the first two items, and then conclude with rule 1. 
% Even worse, one can also observe a failure when rule 2 is applied three times.\todo{what?}

Elpi users often have a background in functional programming and simply do
expect \eI{mem} to be a \emph{function} testing membership, and not
a relation. Moreover one needs to look, carefully, at how \eI{mem} 
is implemented in order to see the peril.
This misconception becomes a problem when they use \eI{mem}
in a larger piece of code and observe its execution.
%
\begin{elpicode}
main L :- code_before L, mem 1 L, code_after L.
\end{elpicode}
%
For example, in the code above, one may see \eI{code_after} being executed
multiple times: each choice point left by \eI{mem} enables the runtime to
backtrack to that point in time and continue from there. Even worse, if
\eI{code_after} is expensive and fails, one pays its cost  multiple times.

It must be said that backtracking can be very useful in some situations and
that a programmer with experience in logic programming can take advantage of
that. We want the Elpi casual user to be able to write code without mastering
all that, and simply declare that they expect \emph{their code} to
compute functions.
%
\begin{elpicode}
func main list int -> . % the signature for main
\end{elpicode}
%
The signature starts by a keyword declaring the determinacy of
the predicate: \efunc{} for deterministic predicates, that we also call functions,
and \epred{} for any predicate, including both functions and relations.
Inputs are separated from outputs by the
arrow symbol, and in the case of \eI{main} there is no output.

\begin{elpicode}
main L :- code_before L, mem 1 L, code_after L.
%                        ^^^^^^ error: non-deterministic atom    
\end{elpicode}
%
Since \eI{main} was declared as a function, our static analysis invites the user
to discard the choice points left by \eI{mem}, for example by inserting a
\eI{!} (a \emph{cut} directive)
after it. Assuming \eI{code_after}
is a functions, this code is accepted, since the cut discards all choice
points generated by \eI{mem} and \eI{code_before L}.
% , or by using the \eI{once} higher-order predicate (see next section).

\begin{elpicode}
main L :- code_before L, mem 1 L, !, code_after L. % OK
\end{elpicode}
%
Note that the programmer may also write a functional membership test as
follows, and use it in functional code with no additional safeguard. In this case
the cut discards the second rule as soon as \eI{X = Y} succeeds.
\begin{elpicode}
func in int, list int -> .
in X [Y|_ ] :- X = Y, !. % commit to this rule, discard the next one
in X [_|YS] :- in X YS.

main L :- code_before L, in 1 L, code_after L. % OK
\end{elpicode}
%
Tracking the use of backtracking code statically is a well known technique
in logic programming called determinacy analysis~\cite{warren1989,somogy1996}.
What the literature lacks
is a treatment of Elpi features not available in plain Prolog,
see~\ref{sec:HO-program} and \ref{sec:dynamic-prog}. %and \ref{sec:meta-prog}.
% We recall them in the following sections.

\subsection{Higher-order programs}
\label{sec:HO-program}

A notable higher-order program is the one turning relations into functions.
\footnote{The syntax \eI{~\PYG{k+kd}{(pred)}~}, equivalent to \eI{~\PYG{k+kd}{(pred ->)}~},
is for fully applied predicates, i.e. for terms with neither inputs nor outputs}
% any predicate
% into a function.
%
\begin{elpicode}
func once (pred) -> . % a function taking a fully applied predicate
once P :- P, !.       % the ! commits to the first success
\end{elpicode}


%
We say that the signature of the \eI{once} predicate marks it as \emph{unconditionally}
a function: \eI{once} leaves no choice points, no matter what it receives as
the higher-order argument \eI{P}.

An example of a \emph{conditional} function is
the predicate to map over a list:
\begin{elpicode}
func map (func A -> B), list A -> list B.
map _ [] [].
map F [X|XS] [Y|YS] :- F X Y, map F XS YS.
\end{elpicode}
%
We say that the signature of \eI{map} has a \emph{precondition}, namely
that \eI{F} is a function, and a \emph{postcondition}, namely that
\eI{map} is a function, i.e., the call \eI{map F L L'} leaves
no choice points.
If the precondition is not met the postcondition is not guaranteed to hold and we say
that \eI{map} is \emph{miscalled}. In this case we weaken its signature to%
\footnote{We explain in detail this weakining operation in \cref{sec:basic}}:
%
\begin{elpicode}
pred map (func A -> B), list A -> list B.
\end{elpicode}
%
Our static analysis tracks miscalled functions and considers them as
relations for the analysis of the surrounding code. This is important to
avoid code duplication, i.e., we can just have one copy of
\eI{map} in our library.
We give an example of four scenarios involving calls and miscalls to \eI{map}.


% \noindent
% \begin{minipage}{.5\textwidth}
\begin{elpicode}
% a function                      % a relation
func incr int -> int.             pred get_pdiv int -> int.
incr 1 2.                         get_pdiv 6 3. get_pdiv 6 2.

       % four predicates calling map or miscalling map
func p list int -> list int.      pred q list int -> list int.
p L R :- map incr L R. ~\PYG{c}{\PYGZpc{} OK}~       q L R :- map get_pdiv L R. % OK

func r list int -> list int.      func r1 list int -> list int.
r L R :- map get_pdiv L R.        r1 L R :- map get_pdiv L R, !. % OK
           % ^^^^^^^^ error: non-deterministic atom
\end{elpicode}
%\vspace{-1.5em}
% \end{minipage}

Here \eI{p} is a function because the precondition of \eI{map} is respected
(\eI{incr} is a function).
The body of \eI{q} contains a miscall to \eI{map}; as a consequence
\eI{q} may leave choice points. This is not an error because
\eI{q} is declared to be a relation. 
The body of \eI{q} and \eI{r} are identical, but
\eI{r} should be a function and hence the static analyzer complains.
The predicate \eI{r1} has the same signature of \eI{r} but it
compensates the miscall to \eI{map} by discarding choice points via
a cut. The static analyzer accepts this last declaration. We point out that,
partial applications, like, \eI{(map incr)}, are accepted in our system,
see \cref{sec:basic}.



\subsection{Dynamic programs}
\label{sec:dynamic-prog}

The domain where Elpi really shines is the manipulation of higher-order data
represented via the so-called $\lambda$-tree syntax~\cite{miller2018}
also called HOAS~\cite{pfenning1988}.
Such data is pervasive in interactive provers based on Type Theory
such as Rocq. In the paradigmatic example below \eI{tm} is
the data type for $\lambda$-terms.
%
\begin{elpicode}
kind tm type.                       % datatype of $\lambda$-terms in HOAS form
type app tm -> tm -> tm.            %  - binary application
type lam (tm -> tm) -> tm.          %  - $\lambda$-abstraction
\end{elpicode}
%
In the HOAS encoding of syntax with binders we do not find a node for variables:
we re-use the notion of bound variable of the programming language to encode the
one of the syntax tree. At the level of types we see that the \eI{lam}
node carries an Elpi function over terms. It is by applying this function
that one can recover the body of the $\lambda$-abstraction.
A simple program manipulating higher-order data is the function
performing a deep copy of a term:
%
\begin{elpicode}
func copy tm -> tm.
copy (app A B) (app C D) :- copy A C, copy B D.
copy (lam F) (lam G)     :- pi x\ copy x x => copy (F x) (G x).
\end{elpicode}
%
The copy of an application is built from the copies of the subterms. What is
more interesting is how one copies under a binder.
The ``\eI{pi x\ copy x x =>}'' instruction
generates a fresh constant \eI{x} and adds to the program the
rule \eI{copy x x} for the rest of the execution of copy. That rule
explains how to copy the new constant \eI{x}. Intuitively ``\eI{pi x\.. => ..}''
amounts to a well-bracketed use of Prolog's \texttt{assert/1} and \texttt{retract/1}.
Finally the code performs a recursive call over \eI{F x}:
by applying the Elpi function \eI{F} to
the fresh symbol \eI{x} one obtains the body of the $\lambda$-abstraction
where the bound variable is replaced
by the new symbol \eI{x}.

In Elpi, all predicates are \emph{dynamic}, or open, hence
the code of \eI{copy} can be
augmented with rules at runtime. 
% \todo{remark app, lam and each x are different}
% \todo{we want copy to be a understood as a function}
Even so \eI{copy} is a function because no
two rules can apply to the same input: \eI{lam} and \eI{app}
are different constants, and each constant \eI{x} generated dynamically is
guaranteed to be fresh by the \eI{pi} operator, hence
each \eI{copy x x} rule is mutually exclusive with the other rules.

The \eI{copy} predicate, as given, implements the identity and may seem rather useless, 
but it is not! Since the program is open, one can add new rules for
\eI{copy} and change its behavior. For example the code below
computes the weak head normal form of a $\lambda$-term by contracting
the application of a $\lambda$-abstraction
to an argument and uses \eI{copy} to perform the substitution:

\begin{elpicode}
func whd tm -> tm.
whd (app H A) R :- whd H (lam F), !,           % we fire the redex
  pi x\ copy x A => copy (F x) S, whd S R.     %   and we continue
whd X X.                                       % or we stop
\end{elpicode}

The argument \eI{A} is put in place of the (previously) bound variable in
\eI{F} by replacing that variable with \eI{x} and
by running \eI{copy} with the addition of a special rule
copying \eI{x} to \eI{A}.
Our static analysis understands this programming pattern
and is able to recognize that \eI{whd} is also a function.
In particular the first rule, if taken, discard the second rule (due to the cut)
and only calls functions.

\section{Elpi's abstract syntax and rule selection}

Any static analysis to rule out non-determinism must depend on the
operational semantics of the language. In particular
the order in which rules are applied and the order in which rule premises
are executed directly impact the scope of the cut directive.

Here we specify the relevant aspects of Elpi.
Its abstract syntax is given below. %in~\cref{fig:syntaxonly}.

We assume a set \PRED of predicate names,
a set \DATA of term constructors, and a set \VAR of unification variables.
We call the union of these three syntactic categories \emph{symbols}.
In the syntax of atoms \ATOM we find predicate calls (\CALLABLE), the \cut operator (explained in \cref{sec:hc})
and the \pi\ operator.%
\footnote{
In reality, in Elpi, \eI{pi} and \eI{=>} are two separate operators,
generating a fresh symbol and loading a rule respectively,
but for simplicity we only consider their combination.}
The arguments of predicate calls are in the \TERM\ nonterminal, for terms,
that includes predicate calls along with first order data construction.
Because of space constraint we omit from the syntax the construction of
data with binders since it plays no interesting role in
the static analysis of determinacy.
We reserve $s$ for symbols ($\PRED \cup \DATA \cup \VAR$), $v$ for variables, 
$k$ for terms in $\PRED \cup \DATA$, $a$ and $b$ for atoms, $c$ for callables
and $r$ for rules.
Given a rule $h\ \cdash\ b_1 \ldots b_n$ we call $h$ the \emph{head},
$b_1 \ldots b_n$ the \emph{body}
and each $b_i$ a \emph{body atom}.
% In the signatures of the static analyzer,
We use non-terminals to represent the class of objects they identify; for example,
\TERM identifies (or is the type of) terms. We use \PROG for the type of programs,
being lists of rules in \RULE, and we reserve $t$ for terms and $\prog$ for programs.
%
% \begin{definition}[Rule priority]
\paragraph{Rule priority} 
 Each rule in a program has a unique identifier called priority; 
  this priority stems from the order in which the rule should be 
  applied at runtime.
There exists a unique total order for rules following their priority.
When a rule is applied, its body atoms are executed in order.

This selection strategy is called SLD and is the standard one for logic programs.
In this strategy non-determinism arises when:
1) at least two rules can be used (successfully) to the \emph{same query} (i.e.,
lack of mutual exclusion between rules, see~\cref{sec:hc});
2) the call to a non-deterministic predicate, or the miscall of a deterministic one,
is not followed by a cut (see~\cref{sec:basic}).

\section{Hard Cut and Mutual Exclusion}
\label{sec:hc}

We focus on how to address the first source of non-determinism.

In order to precisely describe \cut, we need to introduce the notion of choice
points, or alternatives.
The type of an alternative \ALT\ is equal to
$\SIGMA \times \vecL{\GOAL}$, that is a substitution and a list of goals.
The type of a goal \GOAL\ is equal to $\PROG \times \ATOM$, that is
a program and a query (an atom). Since the program can dynamically change due to \pi,
each (sub)goal must contain the program in which it should be solved.\\
A substitution $\subst$ is a partial mapping from unification variables
\VAR to terms \TERM{}. We call this function space \SIGMA\ and we
write \EmptySubst\ for the empty substitution. We write $\subst \cdot t$ for
the application of a substitution $\subst$ to a term $t$.


\begin{definition}[Hard cut]
  \label{def:hard-cut}
Given a rule for predicate $k$ with
priority $p$
and
body $b_1 \ldots b_i\ \cut \ \ldots$, the effect of
reaching \cut is that the runtime discards all alternatives
generated by $b_1 \ldots b_i$ and all rules for $k$ with lower priority than $p$.
\end{definition}

Elpi applies rules by matching the input arguments,
like B-Prolog's ``matching clauses''~\cite{zhou2012},
and by unifying the output ones using Miller's algorithm~\cite{miller1991-pf}.

\begin{definition}[Unification / Matching]\label{def:matching}
Two terms $t$ and $u$ unify if there exists a
substitution $\subst$ such that $\subst \cdot t = \subst \cdot u$. We say that a term $t$
matches (the pattern) $u$ if there exists a
substitution $\subst$ such that $\subst \cdot u = t$ and % $\subst \cdot t = t$.
the domain of $\subst$ is the free variables of $u$
\end{definition}

Finally, in the next definition we distinguish between global rules,
i.e., rules that are part of the program \prog, and local rules that
are loaded via the \pi operator. For example, the \eI{copy} predicate
from \cref{sec:dynamic-prog} has two global rules and one local rule.

  \label{def:mutExcl}
  Given a program \prog and a rule $r$, such that $r\notin \prog$,

  % with
  % $\ctx\ k = \rho_1 \toI \ldots \toI \rho_{n+1} \toO \ldots \toO \func$,
  % i.e., the first $n$ arguments are inputs, $k$ is rigid with determinacy \func.
  we say that $r$ is mutually exclusive with the rules in \prog if
  % $\func = \relI$. Otherwise, if $\func = \detI$,
  it has the highest priority and 
  one of the following additional conditions holds:\\
  % (a) $\exists i, b_i = \cut$, or\\
  (a) there is a \cut in the body of $r$, or\\
  (b) \parbox[t][][t]{.95\textwidth}{$r$ is a gloabl rule and
      all rules $r'$ in \prog have an input argument not unifying
      with the corresponding input in $r$, or}\\
  % $r$ is a rule and
    % $\forall r' = (k~u_1\ldots u_n \ldots ~\cdash~ \ldots) \in \prog$
      % there exists a $d \leq n$ s.t. $t_d$ and $u_d$ do not unify, or}\\
      \label{def:mut-excl-global}
  (c) \parbox[t][][t]{.95\textwidth}{$r$ is a local rule
      introduced via $\pi\ x\ r\ b$, 
      $x$ is an input of $r$ and for all rules $r'$ in the program,
      the corresponding input is not a variable
      %$\exists d \leq n$ s.t.
      % $t_d = x$ and
    % forall rules $(k~u_1\ldots u_n \ldots ~\cdash~ \ldots) \in \prog$ we have that

\subsubsection{Operations on signatures.}\label{sec:static}
% In order to be able to detect miscalls 
We compare signatures using the standard subtyping relation of functional
languages. In particular, we compare inputs contravariantly and outputs
covariantly. It is similar to
\cite{hanus2025}, except for the absence of the \texttt{Any} terminal.
% We compare signature using
% the relation  \mySub\ that is weaker than syntactic equality.
% It is defined by the rules below.
\detI is smaller than \relI since functions generate a ``smaller number
of results'' than relations.
%
% \vspace{-5pt}
$$
\small
\begin{array}{c}
\star \mySub \star \qquad \func \mySub \func \qquad\detI \mySub \relI \\
\rho \toI \tau \mySub \rho' \toI \tau'  \mathrm{~~iff~~} \rho' \mySub \rho \land \tau \mySub \tau' \\
\rho \toO \tau \mySub \rho' \toO \tau'  \mathrm{~~iff~~} \rho \mySub \rho' \land \tau \mySub \tau'
\end{array}
$$
%
The static analysis needs often to keep the stronger or weaker signature among
two. We hence derive from \mySub\ a \minT and \maxT operators defined below.
%
$$
\small
\begin{array}{l}
\minT\ \star\ \star = \star\qquad \minT\ \func \ \func = \func \\
% \minT\ \detI \ \detI = \detI \quad \minT\ \relI\ \relI = \relI\\
\minT\ \detI\ \relI = \minT\ \relI\ \detI = \detI \\
\minT\ (\rho \toI \tau)\ (\rho' \toI \tau') = \maxT\ \rho\ \rho' \toI \minT\ \tau\ \tau' \\
\minT\ (\rho \toO \tau)\ (\rho' \toO \tau') = \minT\ \rho\ \rho' \toO \minT\ \tau\ \tau'
\end{array}
\;\;\;
\begin{array}{l}
\maxT\ \star\ \star = \star\qquad \maxT\ \func\ \func = \func \\
% \maxT\ \detI \ \detI = \detI \quad \maxT\ \relI\ \relI = \relI\\
\maxT\ \detI\ \relI = \maxT\ \relI\ \detI = \relI \\
\maxT\ (\rho \toI \tau)\ (\rho' \toI \tau') = \minT\ \rho\ \rho' \toI \maxT\ \tau\ \tau'\\
\maxT\ (\rho \toO \tau)\ (\rho' \toO \tau') = \maxT\ \rho\ \rho' \toO \maxT\ \tau\ \tau'
\end{array}
$$
%
When a predicate is miscalled we need to weaken its signature. 

% in order to accept, as its first argument, a relation.
We define \minimize and \maximize as follows:
%
$$
\small
\begin{array}{l}
\minimize\ \star = \star\\
\minimize\ \relI = \detI \quad
\minimize\ \detI = \detI\\
\minimize\ (\rho \toI \tau) = \maximize\ \rho \toI \minimize\ \tau\\
\minimize\ (\rho \toO \tau) = \minimize\ \rho \toO \minimize\ \tau
\end{array}
\;\;\;
\begin{array}{l}
\maximize\ \star = \star\\
\maximize\ \detI = \relI\quad
\maximize\ \relI = \relI \\
\maximize\ (\rho \toI \tau) = \minimize\ \rho \toI \maximize\ \tau \\
\maximize\ (\rho \toO \tau) = \maximize\ \rho \toO \maximize\ \tau 
\end{array}
$$
%
The set of signatures that only differ by a leaf in \func[] form a lattice
w.r.t. the order relation \mySub, the join operator \maxT and meet operator
\minT. The infimum of the lattice is computed by \minimize and the supremum
is computed by \maximize.

In~\cref{sec:HO-program} we have weakened the signature of \eI{map}
from $\tau = (\star \toI \star \toO \detI) \toI \star \toI \star \toO \detI$
to $(\star \toI \star \toO \detI) \toI \star \toI \star \toO \relI$.

One could define the supremum of $\tau$ as
$\tau' = (\star \toI \star \toO \relI) \toI \star \toI \star \toO \relI$,
which intuitively amounts to considering all $\detI$ as $\relI$, i.e., dropping
all $\detI$ in case of error. 
However, this would contradict the lattice
property: $\maxT\ \tau\ (\maximize\ \tau) = \maximize\ \tau$, since we would
have $\maxT\ \tau\ \tau' = \tau'$, but $\tau \not\mySub \tau'$. Moreover, since
we compare input signatures using \mySub, this alternative definition of 
\maximize (resp. \minimize) would not make the checker accept more
programs.



\subsubsection{The idea.}
The static analyzer accumulates
knowledge on variables in a context $\Gamma$ initially only containing the signature
of predicates. The checking algorithm considers one rule at a time.
It begins by updating \ctx using the preconditions
on the \emph{inputs} of the head, then it scans all body atoms
and finally checks the postconditions: the determinacy of the body
and the determinacy of the \emph{outputs} of the head.

For example, consider the predicates \eI{comp} and \eI{compose} below: 
\eI{comp} is a function
that takes
as input two functions \eI{F} and \eI{G}, and
calls them in sequence, whereas \eI{compose} builds a new function
from the two received in input.
% We define $s_1 := (int \toI int \toO \detI)$ and $s_2 := (int \toI int \toO
% \relI)$ The static checker verifies whether the body atoms behave
% deterministically. To ensure this property, we start with a context \ctx\ in
% which all predicates have defined signatures and no variables are present.
% Consider a predicate \eI{r} with the signature $s_1 \toI s_2 \toI s_1 \toO
% \detI$. In other words, \eI{r} is a function that takes as input a function
% and a relation, and that returns a function.
\begin{elpicode}
func comp (func int -> int), (func int -> int), int -> int.
comp F G X Z :- F X Y, G Y Z.

func compose (func int -> int), (func int -> int) -> (func int -> int).
compose F G (comp F G).
\end{elpicode}

After updating \ctx w.r.t. the preconditions of \eI{comp},
\ctx flags \eI{F} and \eI{G} as functions. Then the algoritms scans all
body atoms computing the \maxT of their determinacies: since both
\eI{F X Y} and \eI{G Y Z} are \detI, also their \maxT is. Finally
the analyzer checks that the determinacy of the body matches the declared one.\\
The analysis for \eI{compose} needs to check two postconditions:
1) the \emph{output} term \eI{comp F G} is a function, since the two arguments of \eI{comp}
match its signature; 2) the body of \eI{compose} is deterministic since empty.

We now move to an example that involes a non-deterministic body atom.

\begin{elpicode}
func r (func int -> int), (pred int -> int), int -> int.
r F G X Y :- map G [X] [Z], !, compose F F H, H Z Y.
\end{elpicode}
%
After analyzing the head the context asserts that \eI{F} (resp. \eI{G})
is a function (resp. a relation).
In the body of \eI{r}, the first atom is non-deterministic,
since \eI{G} violates the preconditions of \eI{map}. The signature of
\eI{map G [X] [Z]} is hence \text{\auxfont weak}ened to \relI. Even if this atom could
generate multiple alternatives, the \cut\ commits to the first one
restoring the determinism of
the body of \eI{r} up to that point.
The call to \eI{compose} satisfies its preconditions, so its
postconditions apply:
the entire atom \eI{compose F F H} is considered deterministic
\emph{and}
\eI{H} is marked as a function in \ctx.
The final atom \eI{H Z Y} is also deterministic because of the knowledge
about \eI{H} accumulated so far in \ctx.

\section{Determinism guarantees}

In order to express \emph{operational determinacy}
we need to use an operational semantics for Elpi.
That semantics, for its higher-order logic-programming part,
is essentially the one given by~\cite{qi2009} using a last-in-first-out goal selection.
However it must be
complemented with a treatment of choice points to describe
the behavior of the cut operator following~\cite{vink1989}.
Moreover Elpi has a peculiar runtime threatment of input arguments, that
are matched rather than unified (see~\cref{def:matching}).

\begin{definition}[Operational semantics $(\run{} : \ALT \times \vecL{\ALT} \to \SIGMA \times \vecL{\ALT})$]

Run is a partial function from a non-empty list of alternatives to a solution

\begin{enumerate}
\item $\cut$ behaves as per \cref{def:hard-cut}
\item $\pi\ x\ r\ b$ generates a fresh constant for $x$ available in $r$ and $b$
\item $\pi\ x\ r\ b$ loads $r$ in the program giving it the highest priority
\item input arguments are matched against the query as per~\cref{def:matching}
\end{enumerate}
\end{definition}

\begin{theorem}[Static analysis]
  Given program \prog, a context of signatures \ctx and a query atom $b$,
  $
  \isdetp~\ctx~\prog \land \isdetq~\ctx~b \Rightarrow \isdet~\prog~b
  $.
  \label{th:1}
\end{theorem}

The proof of~\cref{th:1} has been mechanized in the Rocq proof assistant,
formerly known as Coq, for the first-order part~\cite{formalproof}. The mechanization for
the higher-order part is ongoing.

One key difference between our work and~\cite{warren1989,lopez2005,somogy1996,king2011,hanus2025}
is that they focus on \textit{closed}
predicates, that do not evolve during execution, while
$\lambda$Prolog, hence Elpi, allows rules to be dynamically loaded.
%
For closed predicates, programs can be transformed into
\textit{super-homogeneous} form by merging all rules into one with
disjunctions. % (or equivalently the \textit{case} constructor).
This simplifies determinacy inference and may allow to compile the code to
a faster binary.
However, this transformation is not feasible in our dynamic setting (\cref{sec:dynamic-prog}).
% and in particular the check for mutual exclusion
% needs a higher degree of sophistication.

Regarding modes, Elpi's matching procedure over input arguments allows us to
dispense with explicit mode analysis -- an essential component in
\cite{warren1989,lopez2005,somogy1996,king2011}.

We differ from Red Alert~\cite{king2011} in that we pick an operational semantics that
explicitly represents choice points as a list of alternatives, and that
hence is very close to the actual behavior of Elpi's runtime. They pick a
denotational semantics over the super-homogeneous form
that in turn lets them  formulate
the static analyzer as an abstract interpreter. It is unclear if a denotational
semantics can be written without transforming the program in super-homogeneous form.

Some of the higher-order features of the Elpi language are available in
Mercury~\cite{somogy1996}, although in a more constrained way ($\ddagger$).
For example
\eI{once} from \cref{sec:HO-program} is considerably more useful
if the input relation is allowed to be non-ground, e.g, \eI{once (map get_pdiv [6] L)}.
% Additionally, Elpi’s strong integration with an interactive theorem prover like
% Rocq prevents us from relying on ground input terms.
We allow higher-order predicates to
be miscalled, while Mercury does not.
Instead, it requires higher-order functions to be annotated with explicit
mode and determinacy signatures for each possible behavior. As a result, Mercury
ascribes
\href{https://github.com/Mercury-Language/mercury/blob/5900de3e8c1bc1dcc75799b350b381ff9b9774f2/library/list.m#L1587C1-L1597C75}{$11$ signatures}
to the \texttt{foldr} predicate
and any call that does not match exactly one of these signatures results in a
compilation failure ($\dagger$). % For instance, \textit{list.filter\_map\_corresponding} fails
% if the higher-order function is deterministic rather than semi-deterministic.
Elpi targets less technically inclined users, more familiar with functional programming languages
than logic ones, hence we strive for simplicity,
defining only one determinacy class and immediately classifying wrong calls as
non-deterministic.
As a result the signature for \eI{foldr} is just
\eI{func foldr (func L, A -> A), list L, A -> A},
 familiar to our audience.
% Finally this design choice aligns
% with our query of providing static guarantees on programs rather than
% helping the compiler to produce
% efficient, specialized, machine code.

The ``determinism types'' of Curry~\cite{hanus2025} are much more similar to
our signatures, and Curry supports miscalled functions as well.
In the work of Hanus and Prott the \texttt{Any} type stands for non-determinism
and like a black hole it absorbs the determinism
of the surrounding sub-terms. This is a convenient way to capture all miscalls
and treat them uniformly. In our presentation, we have no equivalent; instead,
we use \maximize to change the signature of a term when a miscall
is detected~\ref{rule:infer-app-ib} (or atom
calls~\ref{rule:check-atom-miscall}). The advantage is that \maximize
only changes the leaves (\F) of the signature while leaving its structure
intact. Although we do not analyze data in this paper, our set of rules can be
complemented to perform full type checking (in addition to determinacy
checking) in one pass.

In Curry the \texttt{allValues} builtin
can be used to turn a relation into a function. Prolog, and also Elpi,
provide a similar \texttt{findall} builtin, but in addition to that they
also let one commit to the first result by either using \eI{once},
or by placing a \cut after the non-deterministic call.
It is this ``after the fact'' commitment that make the analysis a bit more complex.
In fact, in the body of a deterministic predicate we can have
calls to relations (or miscalled functions) and still consider the rules
valid with respect to determinacy (see \ref{rule:check-atom-cut}).
The notion of \textit{functional context} in~\cite{warren1989}
is closely related to this difficulty.

Our experience report confirms most of the Elpi code out there is made
of functional predicates and that the static analyzer accepts the vast
majority of it requiring no changes. The main improvement we will consider

In the definition of \mySub we currently accept

a function of type $\star \toO \star \toO \detI$, since the modes
