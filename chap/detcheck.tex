Over the years, \elpi has been adopted by many \rocq users. A commonly cited
difficulty is the shift to a logic programming paradigm. While \rocq users are
generally familiar with typed functional programming, they often have limited
experience with backtracking and how to control it. When backtracking is not
properly managed, it can lead to inefficient programs and make debugging more
difficult.

This issue also appears in type class search, and it is a concern for developers
working with type classes in \rocq. In some cases, a type class is expected to
behave deterministically: the search for instances of this class should produce
at most one solution when it succeeds. However, since there is no mechanism to
verify this property, an inexperienced user may encounter long debugging traces
by unintended non-determinism.

For instance, consider the following two instances of the same class:

\begin{coqcode}
Instance i1 A1 : Class1 A1 ~$\to$~ DetClass A1.
Instance i2 A1 : Class2 A1 ~$\to$~ DetClass A1.
\end{coqcode}

If the class \cI{DetClass} is intended to be deterministic, these two instances
break that assumption. Under certain conditions, both \cI{i1} and \cI{i2} may,
in fact,
provide valid solutions, so a query to \cI{DetClass} can return more than one
result. A static checker could detect this situation and warn the user about the
loss of determinism caused by the presence of multiple instances.

Moreover, one may want to keep both instances, but ensure that if the first one
succeeds, the second is not considered. Expressing this kind of control over the
search is not possible in \rocq. In contrast, \elpi allows this behavior by
introducing a \cut in the body of the first rule, which stops further
backtracking and enforces the intended deterministic behavior.

More generally, unintended non-determinism can lead to undesirable effects.
To reduce this issue, we propose a system of determinacy signatures for \elpi. 
This system
allows programmers to specify when a predicate should behave like a function,
that is, it produces at most one result.

This notion of determinism is referred to as \emph{semidet} by
Henderson et al.~\cite{henderson1996}, and as \emph{operationally
deterministic} by Nakamura~\cite{nakamura1986}. Other notions also exist. For
example, Warren~\cite{warren1989} defines predicates as \emph{observably
deterministic} when they produce the same result multiple times or diverge. In
this work, we adopt operational determinacy, as it closely matches the behavior
of functions in mainstream functional programming languages.

Our determinacy checker covers \elpi's
higher-order features, including higher-order predicates (for
example map and fold, see \cref{sec:HO-program}) and dynamic predicates that extend themselves at
runtime (see \cref{sec:dynamic-prog}), and meta-programs that manipulate \elpi code
(see \cref{sec:meta-prog}).

We apply these signatures to a large portion of publicly available
\elpi code in the \rocq ecosystem and report our experience. Our
findings indicate that most \elpi programs are intended to be
backtracking-free and require only minimal signatures for the static
analyzer we implemented to verify determinacy.

Our contributions are:
1) we design a language of signatures to assert the determinacy of predicates
that covers higher-order logic programming constructs such as first-class
predicates and dynamic predicates; 2) we implement a
static analyzer for that language; 3) we apply the static analyzer
to most of the \elpi code available in the \rocq ecosystem.

\section{\elpi and determinacy signatures by examples}\label{sec:intro}

As in most logic programming languages, \elpi programs are organized in rules.
When rules are not \emph{mutually exclusive}, i.e. multiple rules apply on the same query,
the runtime continues the computation 
using the rule with highest priority. Moreover it stores the 
other rules as a \emph{choice point} and
can backtrack to that point to continue the computation.
What makes backtracking tricky to \elpi users is that it is an opt-out feature
of logic programming: it is left to the programmer to tell the
runtime to commit to one rule and discard the choice point, rather than
the other way around. If the user forgets to commit to a rule, his program
still works but becomes much harder to debug and typically slower to run
in case of failures.

The simplest example is the list-membership \emph{relation} that
can succeed more than once if the element we are looking for occurs multiple
times in the list:

\begin{elpicode}
mem X [Y|_ ] :- X = Y.    % the head is the X we are looking for, or
mem X [_|YS] :- mem X YS. % recurse on the tail
\end{elpicode}

The first rule for \eI{mem}
is the base case: it succeeds if the head of the list is equal to the \eI{X} we are
looking for. The second one discards the list's head and continues looking for
\eI{X} in the tail.
A query such as \eI{mem 2 [2,3,2]} can be solved
in two different ways: either using rule 1 immediately, or using rule 2
twice to discard the first two items, and then conclude with rule 1. 
% Even worse, one can also observe a failure when rule 2 is applied three times.\todo{what?}

\elpi users often have a background in functional programming and simply do
expect \eI{mem} to be a \emph{function} testing membership, and not
a relation. Moreover one needs to look, carefully, at how \eI{mem} 
is implemented in order to see the peril.
This misconception becomes a problem when they use \eI{mem}
in a larger piece of code and observe its execution.
%
\begin{elpicode}
main L :- code_before L, mem 1 L, code_after L.
\end{elpicode}
%
For example, in the code above, one may see \eI{code_after} being executed
multiple times: each choice point left by \eI{mem} enables the runtime to
backtrack to that point in time and continue from there. Even worse, if
\eI{code_after} is expensive and fails, one pays its cost  multiple times.

It must be said that backtracking can be very useful in some situations and
that a programmer with experience in logic programming can take advantage of
that. We want the \elpi casual user to be able to write code without mastering
all that, and simply declare that they expect \emph{their code} to
compute functions.
%
\begin{elpicode}
func main list int ~$\to$~. % the signature for main
\end{elpicode}
%
The signature starts by a keyword declaring the determinacy of
the predicate: \efunc{} for deterministic predicates, that we also call functions,
and \epred{} for any predicate, including both functions and relations.
Inputs are separated from outputs by the
arrow symbol, and in the case of \eI{main} there is no output.

\begin{elpicode}
main L :- code_before L, mem 1 L, code_after L.
%                        ^^^^^^ error: non-deterministic atom    
\end{elpicode}
%
Since \eI{main} was declared as a function, our static analysis invites the user
to discard the choice points left by \eI{mem}, for example by inserting a
\eI{!} (a \emph{cut} directive)
after it. Assuming \eI{code_after}
is a functions, this code is accepted, since the cut discards all choice
points generated by \eI{mem} and \eI{code_before L}.
% , or by using the \eI{once} higher-order predicate (see next section).

\begin{elpicode}
main L :- code_before L, mem 1 L, !, code_after L. % OK
\end{elpicode}
%
Note that the programmer may also write a functional membership test as
follows, and use it in functional code with no additional safeguard. In this case
the cut discards the second rule as soon as \eI{X = Y} succeeds.
\begin{elpicode}
func in int, list int ~$\to$~.
in X [Y|_ ] :- X = Y, !. % commit to this rule, discard the next one
in X [_|YS] :- in X YS.

main L :- code_before L, in 1 L, code_after L. % OK
\end{elpicode}
%
Statically tracking the use of backtracking is a well-known technique in
logic programming, usually referred to as determinacy
analysis~\cite{warren1989,somogy1996}. However, the literature does not
provide a detailed treatment of features that are specific to \elpi and not
available in plain \prolog, such as higher-order programming, dynamic
programming, and meta-programming.

These features were introduced in
\cref{sec:example-ho-dyn-programs} and play an important role in
determinacy. In the following three subsections, we revisit those examples
and analyze them from the perspective of determinacy.


\subsection{Higher-order programs}
\label{sec:HO-program}

A notable higher-order program is the one turning relations into functions.
% \footnote{The syntax \eI{~\PYG{k+kd}{(pred)}~}, equivalent to \eI{~\PYG{k+kd}{(pred ->)}~},
% is for fully applied predicates, i.e. for terms with neither inputs nor outputs}
% any predicate
% into a function.
%
\begin{elpicode}
func once (pred) ~$\to$~. % a function taking a fully applied predicate
once P :- P, !.       % the ! commits to the first success
\end{elpicode}


%
We say that the signature of the \eI{once} predicate marks it as \emph{unconditionally}
a function: \eI{once} leaves no choice points, no matter what it receives as
the higher-order argument \eI{P}.

An example of a \emph{conditional} function is
the predicate to map over a list:
\begin{elpicode}
func map (func A ~$\to$~ B), list A ~$\to$~ list B.
map _ [] [].
map F [X|XS] [Y|YS] :- F X Y, map F XS YS.
\end{elpicode}
%
We say that the signature of \eI{map} has a \emph{precondition}, namely
that \eI{F} is a function, and a \emph{postcondition}, namely that
\eI{map} is a function, i.e., the call \eI{map F L L'} leaves
no choice points.
If the precondition is not met the postcondition is not guaranteed to hold and we say
that \eI{map} is \emph{miscalled}. In this case we weaken its signature to%
\footnote{We explain in detail this weakining operation in \cref{sec:basic}}:
%
\begin{elpicode}
pred map (func A ~$\to$~ B), list A ~$\to$~ list B.
\end{elpicode}
%
Our static analysis tracks miscalls to functions and treats them as
relations when analyzing the surrounding code. This avoids code duplication,
since only one definition of \eI{map} is needed in the library. We illustrate
this with four scenarios involving correct calls and miscalls to \eI{map}.

\begin{elpicode}
% a function                      % a relation
func incr int ~$\to$~ int.             pred get_pdiv int ~$\to$~ int.
incr 1 2.                         get_pdiv 6 3. get_pdiv 6 2.

       % four predicates calling map or miscalling map
func p list int ~$\to$~ list int.      pred q list int ~$\to$~ list int.
p L R :- map incr L R. ~\PYG{c}{\PYGZpc{} OK}~       q L R :- map get_pdiv L R. % OK

func r list int ~$\to$~ list int.      func r1 list int ~$\to$~ list int.
r L R :- map get_pdiv L R.        r1 L R :- map get_pdiv L R, !. % OK
           % ^^^^^^^^ error: non-deterministic atom
\end{elpicode}

In this example, \eI{incr} is a function, while \eI{get_pdiv} is a relation.
In particular, \eI{get_pdiv} associates more than one result to the input
\eI{6}, making it non-deterministic.

The predicate \eI{p} is deterministic because it satisfies the precondition
of \eI{map}: the argument \eI{incr} is a function, so the call does not
introduce choice points.

The predicate \eI{q} instead contains a miscall to \eI{map}, since
\eI{get_pdiv} is a relation. As a result, the execution may leave choice
points. However, this is accepted because \eI{q} is declared as a
relation (with \eI{pred}), and therefore non-determinism is allowed.

The situation is different for \eI{r}. Its body is the same as \eI{q}, but
\eI{r} is declared as a function. For this reason, the static analysis
reports an error: a deterministic predicate cannot contain a
non-deterministic computation.

Finally, \eI{r1} has the same signature as \eI{r} and also miscalls
\eI{map}, but it explicitly removes choice points using a cut. This makes
the overall behavior deterministic, and the definition is accepted by the
analyzer. Similarly, an implementation such as
\eI{once (map get_pdiv L R)} would also be valid, since the \eI{once}
wrapper ensures that any potential choice points are discarded.



\subsection{Dynamic programs}
\label{sec:dynamic-prog}

In \cref{sec:example-ho-dyn-programs}, we pointed out the interest of dynamic
programming in a language like \elpi. In this paragraph, we point out why the
predicate \eI{copy} can be considered as a deterministic predicate.
%
\begin{elpicode}
func copy tm ~$\to$~ tm.
copy (app A B) (app C D) :- copy A C, copy B D.
copy (lam F) (lam G)     :- pi x\ copy x x => copy (F x) (G x).
\end{elpicode}
%

\eI{copy} is a function because no
two rules can apply to the same input: \eI{lam} and \eI{app}
are different constants, and each constant \eI{x} generated dynamically is
guaranteed to be fresh by the \eI{pi} operator, hence
each \eI{copy x x} rule is mutually exclusive with the other rules.

The signature of \eI{comp} infroms the checker that \eI{comp} behaves

also \eI{F} and \eI{G} must be; from that we have that
\eI{comp F G} is a function and so is \eI{map (comp F G)}.

\section{\elpi's abstract syntax and semantics}

Any static analysis aimed at ruling out non-determinism must take into account
the operational semantics of the language. In particular, the order in which
rules are applied, as well as the order in which their premises are executed,
directly affects the scope of the cut directive.

The \elpi syntax and semantics considered in this section are those presented
in \cref{sec:elpi-syntax,sec:elpi-semantics}. To simplify the presentation, we
treat \eI{pi} and \eI{=>} as a single operator. In this setting, the construct
\piImplCmd{x}{r}{a} represents the introduction of a fresh symbol $x$, which is
visible in both the rule $r$ and the atom $a$. The local rule $r$ is added to
the scope of the atom $a$.

Using the combined form \piImplCmd{x}{r}{a} does not reduce the expressiveness
of \elpi. The behavior of the \eI{pi} operator can be simulated by introducing
a dummy rule $r$ in $a$, while the \eI{=>} operator can be recovered by using a
vacuous variable \eI{x}.

We omit from the syntax the construction of data with binders, since it does
not play a relevant role in the static analysis of determinacy.

We use the following notation: $s$ ranges over symbol names (including
predicates, data constructors, and variables), $v$ over variables, $k$ over
predicate and data constructors, $a$ and $b$ over atoms, and $r$ over rules.

In summary, the algorithm proceeds as follows:
\begin{itemize}
\item it checks that each rule is mutually exclusive with the others in the program;
\item it verifies that the sequence of calls in the body consists of correctly used functional predicates;
\item it ensures that the preconditions of rules entail their postconditions.
\end{itemize}

Conversely, \eI{q} satisfies mutual exclusion: no query can trigger both
rules. Note that, since inputs are matched, a query like \eI{q X Y} has no
solution in \elpi. % Standard \prolog implementation would reject the query as

Both rules for \eI{r} match any input.
If the first rule succeeds, the \cut\ removes the alternatives
created by the call to \eI{p} and also 
discards the 
other rule \eI{r X R :- q X R}. 
If the first rule fails, the \cut is not reached hence
the second rule is not discarded.
Thus, at most one rule can succeed for \eI{q}.

since \eI{y} is fresh: each time the rule is loaded

\subsection{Checking mutual exclusion: discrimination trees}

This subsection briefly describes our implementation of mutual exclusion
verification in \elpi.

To support mutual exclusion checking in \elpi, we rely on the
discrimination tree data structure~\cite{disc-tree}, a standard mechanism for
indexing rules in logic programming systems. Discrimination trees are widely
used in \prolog-like systems to improve the efficiency of clause retrieval. Our
implementation follows, in part, the presentation given in Pfenning's
notes~\footnote{\url{\pfdt}}.

A discrimination tree is a trie-based structure. Inner nodes are labeled,
while leaves store buckets of objects. Tries represent dictionaries by sharing
common prefixes of keys. A \emph{path} is defined as the sequence of labels
encountered from the root to a leaf.

Two basic operations are supported: insertion and retrieval.
%
\begin{camlcode}
  type retrive trie ~$\to$~ key ~$\to$~ option elt.
  type insert  trie ~$\to$~ key ~$\to$~ elt ~$\to$~ unit.
\end{camlcode}

To insert an
element $e$ with key $k$, the algorithm traverses the trie symbol by symbol,
starting from the root. For each symbol, it follows the corresponding edge,
creating a new node if necessary. Once all symbols have been consumed, the
element $e$ is stored in the resulting leaf. Retrieval works similarly: the key
is read symbol by symbol, and the tree is traversed accordingly. If the path
exists, the elements stored in the corresponding leaf are returned.

In \prolog systems, the indexed objects are the rules of the database, and the
head of each rule serves as its key. In \cref{fig:disc-tree}, taken from~\cite{disc-tree},
the database
(left) and its corresponding discrimination tree (right) are shown. Leaves are
annotated with the rules stored in each bucket. The purpose of the tree is to
enable fast clause retrieval.

Variables are represented in an approximate way. In particular, they are encoded
as generic symbols that match any term. For instance, in
\cref{fig:disc-tree}, rules 1 and 2 share the same path and are stored in the
same bucket. Differently from \cite{disc-tree},
retrieval must take modes into account. For example, if the
predicate \eI{g} has one input and one output argument, the query \eI{g X Y}
returns only rules 7 and 8. If both arguments are outputs, then rules 7, 8, and 9
are returned.

For efficiency, terms are encoded as sequences of integers, where each integer
represents multiple pieces of information at the bit level. Modes are included
in this encoding, allowing the system to determine whether a rigid term should
be matched or unified during retrieval.

Unification in the discrimination tree is only an approximation of the full
\elpi unification algorithm, which is more expensive. By construction, the set
of rules returned by the tree is a superset of the rules that actually match the
query. A second phase applies the full \elpi unification to filter out
non-applicable rules.

We also optimize the encoding of query paths. In practice, query terms are
often larger than the terms stored in the database, so encoding them entirely
is not useful. Instead, we use a hit map to decide which subterms should be
encoded and at which depth.

Moreover, to avoid complex unification, terms headed by a $\lambda$-symbol are
treated as variables. For example, \eI{x\ X x} may unify with \eI{id} or with
\eI{(x y\ true)}, but all such terms are encoded as variables in the tree. As a
result, in our implementation of discrimination trees, the following program
does not satisfy mutual exclusion:

\begin{elpicode}
func isfunc (func int ~$\to$~ int) ~$\to$~.
isfunc id.
isfunc (x y\ true).
\end{elpicode}

The argument of the second rule for the predicate \eI{isfunc} contains a
$\lambda$-abstraction, so the whole argument is encoded as a variable in the
discrimination tree. To make the checker accept this program, a \cut must be
added to the body of the first rule.

Discrimination trees are effective for indexing rules in the \elpi database,
making retrieval faster in many cases. In this chapter, however, their main role is
to support mutual exclusion checking.

During compilation, an auxiliary discrimination tree is built. Each rule of a
deterministic predicate is inserted into this structure. When a new rule is
added, the tree is queried to retrieve the set of potentially overlapping rules
$r$. By invariant, $r$ is an ordered (possibly empty) list in which all rules,
except possibly the last one, contain a \cut. The mutual exclusion check then
verifies that the new rule is inserted either at the end of the list; otherwise
it should contain the \cut operator.

\subsection{Operations on signatures}
\label{sec:static}
% In order to be able to detect miscalls 
We compare signatures using the standard subtyping relation of functional
languages. In particular, we compare inputs contravariantly and outputs
covariantly. It is similar to
\cite{hanus2025}, except for the absence of the \texttt{Any} terminal.
% We compare signature using
% the relation  \mySub\ that is weaker than syntactic equality.
% It is defined by the rules below.
\detI is smaller than \relI since functions generate a ``smaller number
of results'' than relations.
%
% \vspace{-5pt}
$$
\begin{array}{cr}
\star \mySub \star \qquad \detI \mySub \detI \qquad \relI \mySub \relI \qquad\detI \mySub \relI & \text{base cases} \\
\rho \toI \tau \mySub \rho' \toI \tau'  \mathrm{~~iff~~} \rho' \mySub \rho \land \tau \mySub \tau' & \text{covariance}\\
\rho \toO \tau \mySub \rho' \toO \tau'  \mathrm{~~iff~~} \rho \mySub \rho' \land \tau \mySub \tau' & \text{contravariance}  
\end{array}
$$
%
The static analysis needs often to keep the stronger or weaker signature among
two. We hence derive from \mySub\ a \minT and \maxT operators defined below.
%
$$
\begin{array}{l}
\minT\ \star\ \star = \star\\
\minT\ \relI \ \relI = \relI \\
\minT\ \relI \ \detI = \detI \\
\minT\ \detI \ \relI = \detI \\
\minT\ \detI \ \detI = \detI \\
\minT\ (\rho \toI \tau)\ (\rho' \toI \tau') = \maxT\ \rho\ \rho' \toI \minT\ \tau\ \tau' \\
\minT\ (\rho \toO \tau)\ (\rho' \toO \tau') = \minT\ \rho\ \rho' \toO \minT\ \tau\ \tau'
\end{array}
\;
\begin{array}{l}
\minT\ \star\ \star = \star\\
\minT\ \relI \ \relI = \relI \\
\minT\ \relI \ \detI = \relI \\
\minT\ \detI \ \relI = \relI \\
\minT\ \detI \ \detI = \detI \\
\maxT\ (\rho \toI \tau)\ (\rho' \toI \tau') = \minT\ \rho\ \rho' \toI \maxT\ \tau\ \tau'\\
\maxT\ (\rho \toO \tau)\ (\rho' \toO \tau') = \maxT\ \rho\ \rho' \toO \maxT\ \tau\ \tau'
\end{array}
$$
%
When a predicate is miscalled we need to weaken its signature. 

% in order to accept, as its first argument, a relation.
We define \minimize and \maximize as follows:
%
$$
\begin{array}{l}
\minimize\ \star = \star\\
\minimize\ \relI = \detI \quad
\minimize\ \detI = \detI\\
\minimize\ (\rho \toI \tau) = \maximize\ \rho \toI \minimize\ \tau\\
\minimize\ (\rho \toO \tau) = \minimize\ \rho \toO \minimize\ \tau
\end{array}
\;\;\;
\begin{array}{l}
\maximize\ \star = \star\\
\maximize\ \detI = \relI\quad
\maximize\ \relI = \relI \\
\maximize\ (\rho \toI \tau) = \minimize\ \rho \toI \maximize\ \tau \\
\maximize\ (\rho \toO \tau) = \maximize\ \rho \toO \maximize\ \tau 
\end{array}
$$
%
The set of signatures that only differ by a leaf in \func[] form a lattice
w.r.t. the order relation \mySub, the join operator \maxT and meet operator
\minT. The infimum of the lattice is computed by \minimize and the supremum
is computed by \maximize.

In~\cref{sec:HO-program} we have weakened the signature of \eI{map}
from $\tau = (\star \toI \star \toO \detI) \toI \star \toI \star \toO \detI$
to $(\star \toI \star \toO \detI) \toI \star \toI \star \toO \relI$.

One could define the supremum of $\tau$ as
$\tau' = (\star \toI \star \toO \relI) \toI \star \toI \star \toO \relI$,
which intuitively amounts to considering all $\detI$ as $\relI$, i.e., dropping
all $\detI$ in case of error. 
However, this would contradict the lattice
property: $\maxT\ \tau\ (\maximize\ \tau) = \maximize\ \tau$, since we would
have $\maxT\ \tau\ \tau' = \tau'$, but $\tau \not\mySub \tau'$. Moreover, since
we compare input signatures using \mySub, this alternative definition of 
\maximize (resp. \minimize) would not make the checker accept more
programs.

\subsection{The idea}

The static analyzer accumulates
knowledge on variables in a context $\Gamma$ initially only containing the signature
of predicates. The checking algorithm considers one rule at a time, following
their priorities.
It begins by updating \ctx using the preconditions
on the \emph{inputs} of the head, then it scans all body atoms
and finally checks the postconditions: the determinacy of the body
and the determinacy of the \emph{outputs} of the head.

For example, consider the predicates \eI{comp} and \eI{compose} below: 
\eI{comp} is a function
that takes
as input two functions \eI{F} and \eI{G}, and
calls them in sequence, whereas \eI{compose} builds a new function
from the two received in input.
%
\begin{elpicode}
func comp (func int -> int), (func int -> int), int -> int.
comp F G X Z :- F X Y, G Y Z.

func compose (func int -> int), (func int -> int) -> (func int -> int).
compose F G (comp F G).
\end{elpicode}


% We define $s_1 := (int \toI int \toO \detI)$ and $s_2 := (int \toI int \toO
% \relI)$ The static checker verifies whether the body atoms behave
% deterministically. To ensure this property, we start with a context \ctx\ in
% which all predicates have defined signatures and no variables are present.
% Consider a predicate \eI{r} with the signature $s_1 \toI s_2 \toI s_1 \toO
% \detI$. In other words, \eI{r} is a function that takes as input a function
% and a relation, and that returns a function.
At first, the checker assumes that the inputs of \eI{comp} satisfy the
preconditions given in its signature. In particular, \eI{F} and \eI{G}
are marked as functions in \ctx. Then the algorithm scans the atoms in
the body. The determinacy of the whole rule is computed as the \maxT of
the determinacies of its premises. Since both \eI{F X Y} and
\eI{G Y Z} have determinacy \detI, their \maxT is also \detI. Finally,
the analyzer verifies that the determinacy of the body is consistent
with the one declared in the signature.

For \eI{compose}, two conditions must be checked: the term
\eI{comp F G} must be a function, and \eI{compose} itself must also be
a function. The algorithm assumes again that \eI{F} and \eI{G} are
functions. The term \eI{comp F G} is a partial application, and it
returns a function when its arguments are functions. Since this holds
for \eI{F} and \eI{G}, the preconditions of \eI{comp} are satisfied,
and the result is a function.
Finally, the body of \eI{compose} is empty, so it is deterministic.
Therefore, \eI{compose} behaves deterministically.

We now move to an example that involes a miscall to a predicate, that is,
a rule wih a non-deterministic body atom.

\begin{elpicode}
func r (func int ~$\to$~ int), (pred int ~$\to$~ int), int ~$\to$~ int.
r F G X Y :- map G [X] [Z], !, compose F F H, H Z Y.
\end{elpicode}
%
After analyzing the head of the rule, the context asserts that \eI{F} (resp. \eI{G})
is a function (resp. a relation).
In the body of \eI{r}, the first atom is non-deterministic,
since \eI{G} violates the preconditions of \eI{map}. The signature of
\eI{map G [X] [Z]} is hence \maximize{}ened to \relI. Even if this atom 
could
generate multiple alternatives, the \cut\ commits to the first one
restoring the determinism of
the body of \eI{r} up to that point.
The call to \eI{compose} satisfies its preconditions, so its
postconditions apply:
the entire atom \eI{compose F F H} is considered deterministic
\emph{and}
\eI{H} is marked as a function in \ctx.
The final atom \eI{H Z Y} is also deterministic because of the knowledge
about \eI{H} accumulated so far in \ctx.

\subsection{The algorithm}
\label{sec:algo}

We present the static analyzer using derivation rules, they are
listed in \cref{fig:det-check-p1,fig:det-check-p2}.
Each procedure has an associated entails-like symbol, e.g.,
$
\text{context} \sststile{\text{name}}{\text{flag}} \text{intake} \arr \text{result}
$.
We use the equal sign to ``mode'' the rule, i.e., separate
what is given to the rule from what is generated by it.
The static analyzer is composed of seven procedures for a total of 24 rules.

The entry point is \checkc (noted \checkcInfix, \cref{fig:check-rule}). % , with type \ccC{\PROG}{\CTX}{\DATA}{\RULE}),
This procedure takes a program and a context of signatures,
it verifies if a rule validates the signature
ascribed to its predicate. The procedure stores in $\Gamma$ all the
knowledge available on variables and verifies that the precondition
made by the signature entails the postcondition.

In particular, the \checkhi procedure (noted \checkhiInfix, \cref{fig:assume-head-input})
loads into $\Gamma_1$ the information assumed from the head inputs.
This procedure is applied under the assumption that the predicate is
well-called. Hence, all variables that occur (recursively) in input
positions are assumed to satisfy the determinacy specified in the
signature.

On the other hand, the \checkho procedure
(noted \checkhoInfix, \cref{fig:check-head-output}) verifies that $\Gamma_{n+1}$ entails the
required postcondition. More precisely, the inferred type of the terms
appearing in output positions must be smaller or equal (with respect to
\mySub) than the type declared in the signature.
In addition, the determinacy of the body must also by smaller or equal than 
the expected
one. For instance, if a predicate is declared as deterministic, then the
determinacy flag inferred for its body must be \detI. Conversely, if the
predicate is declared as a relation, then the inferred determinacy flag for the
body may be either \detI or \relI.

Each of the $n$ body atoms $b_i$ is processed by \checka
(noted \checkaInfix, \cref{fig:check-atom}). This procedure updates the context, step by
step, and computes the determinacy of the whole body, producing
$\func_{n+1}$.

The \checka procedure includes specific rules to handle
\cut~($a_!$ in \cref{fig:check-atom}) and
\pi~($a_\forall$ in~\cref{fig:check-atom}), as well as rules for
predicate calls~($a_c$) and miscalls~($a_\bot$).

The \cut operator resets the current determinacy to \detI. This follows
from its semantics: once a \cut is executed, all alternative choice
points are discarded, so no nondeterminism can arise.

The \pi operator introduces a fresh symbol together with a local rule.
This rule is checked to ensure that determinacy is preserved. In
particular, it must satisfy \checkc in the current context and must
not violate mutual exclusion. Then, the underlying atom is analysed in
the program extended with this local rule.

Rule~$a_c$ checks that the preconditions of the predicate $c$ are
satisfied. This is ensured by \checkai, which verifies that the inputs
meet the expected conditions. If this holds, the postcondition is
assumed, producing an updated context $\Gamma'$. The determinacy is
updated as the maximum between the current one and that declared for
the predicate.

If the preconditions are not satisfied, the context remains unchanged
and the determinacy is set to \relI. This value reflects that, in case
of a miscalled predicate, no deterministic behaviour can be guaranteed.

The most relevant procedure is the one used to check whether the
preconditions of a predicate call are satisfied, namely \checkai
(noted \inferInfix, \cref{fig:infer}). This procedure ignores data arguments and output
arguments, and simply retrieves from the context the signature of
constants and variables~($tm_k^i$ in~\cref{fig:infer}).

Rule~$tm_\top^i$ corresponds to the standard typing rule for
application. When the input arguments match the expected signature, it
computes the resulting type and reports no miscall (i.e.\ $\top$).

Otherwise, the head or the argument contain a miscall, 
or when the argument does not match the expected signature,
rule~$tm_\bot^i$ is applied. In this case, a miscall is reported and the
resulting signature is obtained by weakening the signature inferred from the
head. Intuitively, the predicate call is treated as a relation, and the
types of the output arguments are weakened accordingly.


The procedure to update the context when an atom is found to be
a good call is \checkao~(noted \checkaoInfix, \cref{fig:check-atom-out}). %(\caoC{\CTX}{\TERM}{\TYPE}{\CTX}).
It is an iterator over output arguments:
other than ignoring input arguments ($\text{\procfont a}_i^\text{\procfont o}$)
and fetching the signature of symbols
in the context ($\text{\procfont a}_k^\text{\procfont o}$),
it calls \assume on output arguments.

The \assume procedure (noted \assumeInfix, \cref{fig:assume}) updates the context when it
encounters variables (rule $tm_X^o$). If a variable already has a
signature in the context, the stronger one is kept.

Data and output arguments are ignored, while input arguments are
traversed recursively. In this way, the signatures of variables
occurring in input positions are also updated in the context.

\begin{definition}[Checked query atom ($\isdetq~\CTX~\ATOM$)] An atom $b$
is checked against a context of signatures \ctx iff 
\vspace{-.5pt}
$$\caC{\emptyset}{\ctx}{\detI}{b}{\detI}{\_}$$

\end{definition}




\begin{theorem}[Static analysis]
  Given program \prog, a context of signatures \ctx and a query atom $b$,
  $
  \isdetp~\ctx~\prog \land \isdetq~\ctx~b \Rightarrow \isdet~\prog~b
  $.
  \label{th:1}
\end{theorem}

The proof of~\cref{th:1} has been mechanized in the \rocq proof assistant for
the first-order fragment, and is available at
\url{https://github.com/FissoreD/elpi-formalization}. The first-order
formalization is discussed in detail in~\cref{chap:mechanization}. The
mechanization of the higher-order part is still ongoing.

One key difference between our work and~\cite{warren1989,lopez2005,somogy1996,king2011,hanus2025}
is that they focus on \textit{closed}
predicates, that do not evolve during execution, while
\lprolog, hence \elpi, allows rules to be dynamically loaded.
%
For closed predicates, programs can be transformed into
\textit{super-homogeneous} form by merging all rules into one with
disjunctions. % (or equivalently the \textit{case} constructor).
This simplifies determinacy inference and may allow to compile the code to
a faster binary.
However, this transformation is not feasible in our dynamic setting (\cref{sec:dynamic-prog}).
% and in particular the check for mutual exclusion
% needs a higher degree of sophistication.

Regarding modes, \elpi's matching procedure over input arguments allows us to
dispense with explicit mode analysis -- an essential component in
\cite{warren1989,lopez2005,somogy1996,king2011}.

We differ from \redalert~\cite{king2011} in that we pick an operational semantics that
explicitly represents choice points as a list of alternatives, and that
hence is very close to the actual behavior of \elpi's runtime. They pick a
denotational semantics over the super-homogeneous form
that in turn lets them  formulate
the static analyzer as an abstract interpreter. It is unclear if a denotational
semantics can be written without transforming the program in super-homogeneous form.

Some higher-order features of \elpi are also present in \mercury~\cite{somogy1996},
although in a more restricted form ($\ddagger$). In \mercury, input modes
generally require terms to be ground (with some limited relaxation for data).
However, the predicate \eI{once} in \elpi (see~\cref{sec:HO-program}) is much
more useful when the input relation can be non-ground. For example,
\eI{once (map get_pdiv [6] L)} is a valid use case in \elpi, but it cannot be
encoded in \mercury.
% Additionally, Elpi’s strong integration with an interactive theorem prover like
% \rocq prevents us from relying on ground input terms.

We allow higher-order predicates to
be miscalled, while \mercury does not.
Instead, it requires higher-order functions to be annotated with explicit
mode and determinacy signatures for each possible behavior. As a result, \mercury
ascribes
\href{https://github.com/Mercury-Language/mercury/blob/5900de3e8c1bc1dcc75799b350b381ff9b9774f2/library/list.m#L1587C1-L1597C75}{$11$ signatures}
to the \texttt{foldr} predicate
and any call that does not match exactly one of these signatures results in a
compilation failure ($\dagger$). % For instance, \textit{list.filter\_map\_corresponding} fails
% if the higher-order function is deterministic rather than semi-deterministic.
\elpi targets less technically inclined users, more familiar with functional programming languages
than logic ones, hence we strive for simplicity,
defining only one determinacy class (in \mercury they are 
$8$) and immediately classifying wrong calls as
non-deterministic.
As a result the signature for \eI{foldr} is just
\eI{func foldr (func L, A ~$\to$~ A), list L, A ~$\to$~ A},
 familiar to our audience.
% Finally this design choice aligns
% with our query of providing static guarantees on programs rather than
% helping the compiler to produce
% efficient, specialized, machine code.

The ``determinism types'' of \curry~\cite{hanus2025} are much more similar to
our signatures, and \curry supports miscalled functions as well.
In the work of Hanus and Prott the \texttt{Any} type stands for non-determinism
and like a black hole it absorbs the determinism
of the surrounding sub-terms. This is a convenient way to capture all miscalls
and treat them uniformly. In our presentation, we have no equivalent; instead,
we use \maximize to change the signature of a term when a miscall
is detected (such as, $tm_\bot^i$ in~\ref{fig:infer} or atom
calls $a_\bot$ in~\ref{fig:check-atom}). The advantage is that \maximize
only changes the leaves (\F) of the signature while leaving its structure
intact. Although we do not analyze data in this chapter, our set of rules can be
complemented to perform full type checking (in addition to determinacy
checking) in one pass.

In \curry the \texttt{allValues} builtin
can be used to turn a relation into a function. \prolog, and also \elpi,
provide a similar \texttt{findall} builtin, but in addition to that they
also let one commit to the first result by either using \eI{once},
or by placing a \cut after the non-deterministic call.
It is this ``after the fact'' commitment that make the analysis a bit more complex.
In fact, in the body of a deterministic predicate we can have
calls to relations (or miscalled functions) and still consider the rules
valid with respect to determinacy (see $a_!$ in~\ref{fig:check-atom}).
The notion of \textit{functional context} in~\cite{warren1989}
is closely related to this difficulty.

Another difference with~\cite{hanus2025} is that, when a variable appears as the
output of a miscalled predicate, its signature may change over time. For
example, consider 
\begin{center}
  \eI{compose rel1 rel2 R, R = copy, R T1 T2}
\end{center}
\noindent
where \eI{compose} and \eI{copy} are defined in
\cref{sec:dynamic-prog,sec:meta-prog}, and \eI{rel1} and \eI{rel2} are two
relations.

The miscall to \eI{compose} initially assigns a relational interpretation to
\eI{R}. However, the subsequent assignment \eI{R = copy} refines this
information and makes \eI{R} a function. As a result, the call
\eI{R T1 T2} is treated as a function.

Our experience report confirms most of the \elpi code out there is made
of functional predicates and that the static analyzer accepts the vast
majority of it requiring no changes. The main improvement we will consider
is about \emph{mode subtyping} for higher-order arguments.
In the definition of \mySub we currently accept
only arrows that have the same input/output mode. However, it seems possible to
relax this condition. For example we could allow passing to \eI{map}
a function of type $\star \toO \star \toO \detI$, since the modes
of higher-order arguments seem to play no role in the determinacy of
code that receives and calls them.
